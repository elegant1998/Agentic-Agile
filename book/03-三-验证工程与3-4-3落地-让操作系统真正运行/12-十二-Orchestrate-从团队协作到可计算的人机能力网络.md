# 第十二章｜Orchestrate：从团队协作到可计算的人机能力网络

## 12.1 从任务列表到 Work Graph

Work Graph 可以直译为“工作图”。先不要把它想成一个高深的 AI 术语：它本质上是在回答——**为了完成这次交付，哪些工作必须发生，它们彼此依赖什么，满足什么条件才可以继续？**

假设周末要在家做一顿饭。“买菜、洗菜、炒菜、摆桌、开饭”是一张任务清单；如果进一步说明“买到菜后才能洗菜，洗菜和摆桌可以并行，菜品与餐具都准备好后才能开饭”，它才开始成为工作图。箭头不是为了好看，而是在表达一个真实条件：上游没有产生合格结果，下游就不应启动。

AI Coding 中也一样。复杂任务不是一串可以任意领取的待办事项。多个 Agent 执行得很快，如果它们不知道依赖和边界，就可能同时修改同一文件、在测试尚未可信时开始实现、拿过期产物继续工作，或者在集成验证之前宣布完成。Work Graph 把这些原本藏在人脑、会议和聊天记录里的协作关系，变成可以检查、调度和留证的结构。

### 12.1.1 一张工作图由什么组成

最小 Work Graph 包含四类元素：

1. **节点（Node）**：一项可独立执行和验证的工作，例如“生成边界测试”或“完成接口契约验证”。节点不是一句模糊任务名称，还要有输入、执行者、允许范围、输出和完成判据。
2. **边（Edge）**：两个节点之间的关系。它可能表示先后依赖、数据交接、审批放行、资源互斥或失败路由，而不只是“A 做完再做 B”。
3. **状态（State）**：节点当前是等待、可运行、执行中、通过、失败、阻塞还是需要人工裁决。状态必须来自真实执行结果，不能只靠 Agent 自报。
4. **控制条件（Control Condition）**：什么时候启动、停止、重试、回退、汇合或升级 HITL。例如“只有测试产生可信 Red，且影响分析没有发现范围外依赖，实现节点才可启动”。

因此，一张真正可执行的工作图应能回答：

- 现在有哪些节点已经具备启动条件？
- 哪些工作可以并行，哪些只是表面上可以同时开始？
- 下游正在等待谁的什么产物或证据？
- 某个节点失败后，应该重试、返回上游、回退还是交给人类？
- 哪些节点全部通过后，才允许汇合、发布或生成 Evidence Bundle？

### 12.1.2 它与任务清单、流程图和项目计划有什么不同

| 形式 | 主要回答 | 通常缺少什么 |
|---|---|---|
| 任务清单 | 有哪些事情要做 | 依赖、输入输出、失败路线和汇合条件 |
| 流程图 | 大致经过哪些步骤 | 节点执行契约、真实状态、证据和调度能力 |
| 项目计划 | 谁在什么时间完成什么 | 面向 Agent 的上下文、工具权限、停止与重试条件 |
| CI/CD Pipeline | 代码如何构建、测试和发布 | 从意图澄清到实现、裁决的完整工作关系 |
| Work Graph | 当前交付如何被分解、依赖、执行、验证和恢复 | 它不是某种固定模板，需要按契约与风险生成 |

Work Graph 可以吸收项目计划和流水线中的节点，但不等于二者。项目计划可能写“周三完成测试”，工作图则要说明测试使用哪个契约版本、消费什么输入、通过判据是什么，以及测试失败后哪个节点失效。CI/CD Pipeline 通常从代码提交开始，Work Graph 可以更早地从意图澄清、约束确认和测试设计开始，并把人工裁决也纳入图中。

### 12.1.3 为什么经常使用 DAG，但又不能只理解成 DAG

DAG 是 Directed Acyclic Graph，即“有向无环图”。“有向”表示边有方向，例如测试结果流向实现节点；“无环”表示在同一次调度里不能出现 A 等 B、B 又等 A 的死锁依赖。DAG 很适合表达一次交付的主干依赖、并行组和汇合点。

但现实中的研发会返工：验证失败后可能回到测试、约束或规格重新处理。为避免概念混乱，可以把**一次运行中的可调度依赖**保持为 DAG，把“失败后生成修复节点、重新签署并启动下一轮图”看作控制回路。这样既允许系统学习和返工，又不会把图变成无法判断何时结束的无限循环。

### 12.1.4 它与 Intent Graph 的区别

这两张图最容易混淆：

- **Intent Graph（意图图谱）**组织“为什么做、价值如何分解、哪些意图彼此关联”；
- **Work Graph（工作图）**组织“这一次怎样做、谁先谁后、产物如何交接、失败如何处理”。

例如，“降低虚假报销并保持员工体验”属于 Intent Graph；为了修改单笔金额规则而安排“澄清边界—生成测试—影响分析—实现—SIT—证据裁决”，属于 Work Graph。前者相对稳定，可以服务多个契约；后者面向一次具体交付，会随着契约、风险和执行状态变化。

### 12.1.5 费用报销案例：从清单变成可执行关系

费用报销案例可以拆成：

```text
读取契约和约束
├─ 生成边界测试
├─ 分析审批规则影响
├─ 检查数据与权限边界
└─ 准备遥测与证据结构
        ↓
实现最小规则变更
        ↓
集成验证
        ↓
Evidence Bundle
```

这张简图还只是骨架。要成为可执行 Work Graph，每个节点还要绑定契约与 AC、输入产物、负责人或 Agent、工具权限、允许修改范围、完成证据、预算和失败路线。例如：

- “生成边界测试”读取已签署的金额规则和 Example Mapping，输出处于可信 Red 状态的测试及运行记录；
- “实现最小规则变更”必须等待可信 Red 和影响分析完成，只允许修改金额策略与指定适配层；
- “集成验证”必须消费当前提交的制品，不能拿旧分支的 Green 结果冒充；
- “Evidence Bundle”只负责汇聚与核验既有证据，不能自己补造缺失证据；
- 若影响分析发现未知调用方，图进入阻塞状态并升级 OA/IO，而不是静默扩大修改范围。

只有无前置依赖、无写冲突、上下文边界明确、失败互不污染的任务才适合并行。**Work Graph 的价值不是让更多 Agent 同时开工，而是让每个 Agent 只在条件成立时开工，并让任何“已经完成”的声明都能沿图追溯到输入、规则和证据。**

## 12.2 每个 Agent 节点的执行契约

每个 Agent 节点至少需要：

- 当前目标；
- 非目标；
- 输入和预期输出；
- 相关 AC 和约束；
- 允许修改的文件；
- 禁止触碰的模块；
- 可用工具；
- 时间、Token 和重试预算；
- 完成条件；
- 停止和升级条件。

## 12.3 30 秒微检查点

30 秒微检查点是一种极轻量的方向校验：在 Agent 准备进入高成本实现或验证前，用半分钟复述自己的理解和行动边界。它借鉴了航空与医疗中的“操作前确认”思想——不是重新开一次评审会，而是在不可忽略的转折点检查大家是否正在做同一件事。

Prove 开始前，AS 向 OA 报告：

1. 我理解的目标是什么；
2. 我会修改哪些文件；
3. 我不会触碰哪些范围；
4. 我识别到哪些风险。

OA 检查的也不是代码方案是否完美，而是目标、范围和风险是否明显偏离契约。例如 AS 说“我将修改历史报销草稿以保持数据一致”，而契约 Non-goals 明确排除历史迁移，OA 可以在任何代码产生前停止这一方向。

微检查点适合放在上下文交接后、并行节点汇合前、高风险工具调用前，以及多轮修复后准备继续时。低风险、边界稳定的重复任务可以自动化比对；权限扩大、目标冲突或不可逆操作仍要进入正式 HITL。

这个检查点不是人工逐行审批。它防止的是方向性错误，而不是替代测试和 Evidence Bundle。一个好的微检查点应短、结构固定、结果可记录；如果每次都演变成长会议，说明任务契约或节点边界还不够清晰。

## 12.4 Handoff 与跨 Agent 协作

Handoff 即“工作交接”。在人类团队中，接收者会追问不清楚的地方，并凭共同背景判断上游是否遗漏；Agent 之间缺少这种默契，一句“测试已经完成，可以继续”很容易把错误假设传到下游。

Handoff 因此不是聊天总结，而是一份小型、可验证的交付契约。它应传递结构化事实：

- 已完成什么；
- 产生了哪些文件；
- 哪些检查已运行；
- 哪些失败仍未解决；
- 哪些假设尚未验证；
- 下一个 Agent 需要什么输入。

还应带上任务与契约版本、产物路径、运行命令和退出码。下游收到后先做低成本验真：文件是否存在，测试是否确实处于预期 Red 或 Green，产物是否来自当前提交，上游声明的未知项是否会阻塞自己。

例如测试 Agent 的 Handoff 不能只写“边界测试已完成”，而应说明测试文件、对应 AC、运行命令、退出码为 1 且失败原因是功能尚未实现。这样实现 Agent 才能确认这是可信 Red，而不是测试环境损坏。

Handoff 的价值是隔离错误。如果下游验证失败，系统可以把问题路由回具体上游节点，而不是让整个任务在错误基础上继续。接收方应验证输入，而不是盲信上游 Agent 的“已完成”；上游也不应传递自己的全部上下文，只传递下游完成工作所需的事实、产物和未知项。

### 一份可验证的 Handoff 示例

```yaml
task: WG-TEST-01
contract_version: T-001@sha256:8d31...
source_commit: a81f5c2
status: completed
outputs:
  - path: tests/expense-threshold.test.ts
    sha256: 6a72...
checks:
  - command: npm test -- expense-threshold
    exit_code: 1
    meaning: expected_red
    evidence: evidence/red/WG-TEST-01.txt
assumptions:
  - currency is CNY
unknowns:
  - historical drafts migration not evaluated
next:
  allowed_node: WG-IMPLEMENT-01
  precondition: coding_gate_passed
```

接收方至少校验契约版本、来源提交、产物摘要和证据文件，再判断 `exit_code: 1` 是否真是预期 Red，而非依赖缺失或环境故障。验证失败时，图应把任务退回 `WG-TEST-01`，不能让实现节点带着不可信输入继续执行。

## 12.5 资源争用、超时与死锁

多 Agent 编排首先要管理的不是“谁更聪明”，而是谁占用什么资源、占用多久，以及失败后资源怎样释放。常见故障包括同时修改同一文件、争抢测试环境、循环依赖、重试风暴、节点失败后下游继续消费陈旧结果，以及多个 Agent 互相等待人工确认。

每个节点启动前应声明三类资源：**写资源**（文件、分支、数据库表）、**独占资源**（测试环境、设备、发布槽位）和**稀缺预算**（Token、时间、并发额度）。Graph Engine 据此检查写集合冲突；无法隔离的共享写入必须串行，不能依靠 Agent 自觉避让。

一套最小控制规则包括：

- 写同一文件或状态对象的节点不得并行，除非使用独立分支并设置明确汇合节点；
- 锁必须包含 Owner、获取时间和租约，到期后进入确认或回收，不能永久占用；
- 超时要区分“仍在正常运行”“外部依赖无响应”和“节点已经失联”，不能一到时间就盲目重跑；
- 只对瞬时错误进行有限重试，规格冲突、权限拒绝和确定性测试失败不得靠重试解决；
- 节点失败后立即使其输出失效，下游只能等待、回退或改走显式降级分支；
- 图中出现循环等待，或连续两轮重调度仍无法取得资源时，停止自动编排并升级 OA。

例如测试 Agent 占用唯一集成环境超过租约时，系统应先检查心跳与当前日志；确认失联后释放环境、把未完成输出标记为无效，再决定是否重调度。直接启动第二个 Agent 可能让两个执行者同时写入环境，制造更难诊断的污染。

关键事件都应留下 Graph Event：锁的获取与释放、超时原因、重试次数、输出失效和人工解锁。否则 Dashboard 只能看到“任务变慢”，却无法判断是模型问题、资源瓶颈还是图设计错误。

## 12.6 自适应编排的边界

自适应编排允许系统根据任务类型、历史成功率、工具可用性和当前负载，调整执行者、并发度、节点顺序与重试策略。但它优化的是**已授权边界内的执行路径**，不是重新定义目标或替责任人接受风险。

可以自动调整的内容通常包括：在批准列表中选择 Agent 或模型；把无冲突节点串行或并行；根据资源状态重调度；在预算内切换工具；对已分类的瞬时故障有限重试。以下内容则必须锁定：

- 已签署的 Goal、Non-goals、Rules 和关键 AC；
- MUST 约束及其失败动作；
- 工具和数据权限上限；
- 人类批准与职责分离边界；
- Evidence Bundle 和 Verify 的独立性要求；
- 总预算、停止条件和不可逆操作门禁。

Learning Router 的新策略不应直接接管生产任务。至少要经过历史任务回放或影子评估，证明完成率、证据完整性和成本没有不可接受退化；随后在低风险范围灰度，并保留旧路由作为回退。路由依据、选择结果和回退原因都要进入遥测，避免算法逐渐形成无法解释的“黑箱管理者”。

可以用一句规则判断：**路径可以学习，边界不能自学；效率可以优化，授权不能推断。** 一旦自适应需要扩大权限、改变 AC、跳过门禁或突破预算，Graph Engine 必须暂停并请求人类裁决。

## 12.7 并行是否真的带来收益

并行收益取决于可独立任务比例、协调成本、共享资源和最终集成成本。团队可以记录：

- 串行关键路径长度；
- 可并行节点数量；
- Handoff 失败次数；
- 写冲突和重做；
- 并行带来的真实时间节省；
- 增加的 Token 和验证成本。

如果两个 Agent 需要反复同步同一文件，并行可能比串行更慢。

## 12.8 Orchestrate 常见失败

- 把任务切得太细，Handoff 成本超过收益；
- 多个 Agent 同时修改共享核心文件；
- 下游不检查上游产物；
- DAG 只描述正常路径，没有失败分支；
- 自动重试没有上限；
- 微检查点只重复用户原话；
- Learning Router 用历史成功率掩盖任务类型差异。

## 12.9 编排中的三个关键决策

### 决策一：串行还是并行

只有当任务边界稳定、共享写入较少、验收接口明确时，并行才有意义。若两个 Agent 不断修改同一核心对象，表面的并发会转化为合并冲突、上下文重载和重复验证。OA 应比较关键路径缩短量与协调成本，而不是把 Agent 数量当作生产力指标。

### 决策二：自动重试还是升级人类

网络抖动、临时资源不可用、已知幂等操作可以有限重试；目标冲突、权限不足、数据不可逆、证据自相矛盾则必须停止。重试次数、退避策略和升级条件都应预先写入 Work Graph，不能让执行 Agent 在失败后临场决定自己还可以尝试多少次。

### 决策三：共享上下文还是隔离上下文

共享上下文有利于一致性，却增加信息泄漏、锚定偏差和上下文污染；隔离上下文减少干扰，却可能产生局部最优。合理做法是共享稳定的契约、约束和接口，隔离与本节点无关的实现细节，并通过 Handoff 传递已经验证的产物。

## 12.10 一个四节点编排案例：为什么这样拆、这样连

继续使用“境内人民币差旅报销含税总额严格大于 5000 元时，增加总监审批”的任务。表面看只是把比较条件改一下，但影响可能穿过领域规则、审批状态、历史接口、回归测试和发布证据。如果直接让一个 Agent 从需求一路写到上线，它很容易同时定义判据、修改实现、解释兼容问题并宣布自己通过，责任和错误来源都会混在一起。

编排前，OA 先从契约和约束中提取四个决定：

1. `5000.00` 不触发、`5000.01` 触发，这是已经签署的业务边界，Agent 无权重新解释；
2. 历史草稿迁移属于 Non-goals，本次不能顺手修改旧数据；
3. 测试必须先产生可信 Red，实现 Agent 不得修改关键测试；
4. API 兼容性尚未被证明，发现旧语义冲突时必须升级，不能静默兼容。

这些决定说明任务至少包含四种性质不同的工作：定义挑战、改变领域行为、适配系统边界、独立汇总证据。于是得到四个节点，而不是简单地“找四个 Agent 同时干活”。

### 四个节点分别承担什么责任

| 节点 | 为什么独立 | 主要输入 | 允许修改 | 完成条件 |
|---|---|---|---|---|
| N1 规则测试 | 先固定判据，避免实现反向定义正确 | 签署契约、AC、Example Mapping、金额口径 | 边界测试与测试夹具 | 4999.99、5000.00、5000.01 形成可信 Red；失败原因确为能力尚未实现 |
| N2 领域实现 | 只负责最小业务变化，不承担接口兼容裁决 | N1 Red、领域代码切片、BEHAVE/STYLE 约束 | 金额规则与审批领域模块 | N1 由 Red 变 Green，领域回归通过，未修改测试和历史数据 |
| N3 接口适配 | 隔离 API、序列化和历史调用方风险 | 已签署接口语义、N1 边界判据、现有 API 契约 | Adapter、接口契约测试 | 新旧请求均可被明确解释；未发现静默语义变化；接口测试通过 |
| N4 证据汇总与独立验证 | 防止实现者用自己的解释宣布完成 | N1–N3 原始输出、当前提交、约束结果 | Evidence Bundle，不得修改实现与判据 | AC 与约束逐条有新鲜证据；来源一致；残余风险和回退条件清楚 |

这里有两个刻意的职责分离。第一，N1 和 N2 分开，是为了让“什么算正确”先于“怎样实现”稳定下来；第二，N4 不修代码，只核验证据，否则它发现缺口后可能顺手补一个结果，再把自己补出的东西判为通过。

### 边不是箭头，而是启动条件

这张图可以简化为：

```text
                    ┌→ N2 领域实现 ──┐
N1 可信 Red 与边界冻结                 ├→ N4 证据汇总与独立验证
                    └→ N3 接口适配 ──┘
```

但每条边都有具体语义：

- `N1 → N2`：不是“测试文件写完”，而是测试已运行、确实为 Red、失败原因与缺失行为一致，并且关键断言摘要已锁定；
- `N1 → N3`：金额边界和目标接口语义已经确定，N3 才能检查历史 API 是否兼容；
- `N2 + N3 → N4`：两个节点都完成还不够，来源提交必须能够汇合、没有写集合冲突，集成检查必须使用汇合后的当前制品。

如果边只写成 `depends_on`，却不定义这些条件，Graph Engine 最多知道前一个节点“自报完成”，不知道下游获得的输入是否可信。

### 为什么 N2 和 N3 可以并行，又为什么有时不能

本案例允许 N2 与 N3 在 N1 之后并行，前提是接口语义已经由契约冻结，并且写集合隔离：N2 只改领域规则，N3 只改 Adapter 和接口契约测试。这样两者共享稳定的边界，不共享可变实现。

若代码库把金额判断直接写在 Controller 中，或者 N2 仍可能改变接口字段与错误码，那么两节点实际上会争用同一设计决策和文件。此时正确选择不是强行增加并发，而是先串行完成领域接口抽取，再启动适配；必要时把任务改成五个节点。**节点数量不是预设答案，依赖和风险才是。**

并行前至少检查四件事：输入是否稳定、写集合是否隔离、单方失败是否污染另一方、汇合时是否有独立验证。任何一项答不上来，串行通常更便宜。

### 三类失败为什么要回到不同位置

Work Graph 的价值在失败时更明显。这个案例至少需要三条失败路由：

1. **实现错误**：N2 中 `5000.00` 仍触发总监审批。规则与测试没有冲突，返回 N2 进入有限 P⇄E，不重写 N1；
2. **接口兼容冲突**：N3 发现历史 API 一直把 `5000.00` 解释为高额报销。节点标记为 `blocked_by_rule_conflict`，保存旧接口、现契约和失败测试，返回 OA/IO 裁决。若意图改变，则生成新契约版本，并使 N1–N3 旧输出失效；
3. **证据不一致**：N4 发现领域测试来自提交 A，接口测试却来自提交 B。它不允许把两份绿色报告拼成证据包，而是退回汇合检查，在同一提交上重新运行相关验证。

还要有停止条件：N2 最多自动修复两轮；任何节点请求生产数据或扩大文件权限立即停止；规则冲突不得自动重试；N4 缺少关键 AC 证据时状态只能是 `unproven`，不能降级成“基本通过”。

### 一份最小 Work Graph 定义

```yaml
nodes:
  N1_TEST:
    outputs: [trusted_red, locked_assertions]
    write_scope: [tests/expense-threshold.test.ts, tests/fixtures/expense-*]
    exit: red_reason == feature_missing

  N2_DOMAIN:
    depends_on: [N1_TEST.trusted_red]
    write_scope: [src/domain/expense/**]
    retry: {max: 2, only: [implementation_defect]}
    on_rule_conflict: escalate

  N3_ADAPTER:
    depends_on: [N1_TEST.locked_assertions]
    write_scope: [src/api/adapters/**, tests/contracts/**]
    on_contract_conflict: block_and_escalate

  N4_VERIFY:
    depends_on: [N2_DOMAIN.green, N3_ADAPTER.green]
    require_same_commit: true
    write_scope: [governance/evidence/T-001/**]
    forbidden: [modify_source, modify_ac, modify_tests]
    on_missing_evidence: unproven
```

真实项目还会加入超时、资源锁、Tools Manifest、成本预算和恢复动作。这个最小定义已经表达了编排的核心：每个节点为什么存在、在什么条件下开始、能改变什么、必须交出什么，以及失败后返回哪里。

回看这个案例，四节点并不是一种标准模板。它展示的是一套推导方法：**先从契约和风险识别需要分离的责任，再根据可信输入建立节点，用启动条件而不是时间顺序连接节点，只对真正隔离的工作并行，最后为不同失败设计不同回路。** 读者掌握的应是这套考虑方式，而不是记住“测试—实现—接口—证据”四个名称。

## 12.11 本章小结

Orchestrate 的目标不是让更多 Agent 同时工作，而是把人类责任节点、专业 Agent、工具和依赖组织成可计算的能力网络，让合适的任务在明确上下文、权限、启动条件和停止条件下安全流动。

**本章最小实践**：为 T-001 创建 Work Graph，并完成微检查点。  
**完成证据**：DAG、节点上下文、依赖和停止条件。  
**延伸实践**：推荐学习《Agentic Agile 3-4-3 基础课：跑通第一次受控自治》，把角色、工具和交接关系组织成可验证的 Work Graph。
