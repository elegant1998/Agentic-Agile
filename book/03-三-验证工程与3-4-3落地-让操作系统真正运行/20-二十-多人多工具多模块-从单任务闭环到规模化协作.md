# 第二十章｜多人、多工具、多模块：从单任务闭环到规模化协作

单个 Agent 完成一个边界清晰的任务时，意图、上下文、写入范围和验收责任相对容易对齐。一旦多人、多工具或多模块同时进入，复杂度不再只来自任务本身，而来自它们之间的关系：谁听谁的，谁可以改什么，哪个版本才是事实，局部完成能否组成系统完成，失败后又该由谁停止和恢复。

## 20.0 组织级扩展判断

规模化不是把任务运行层的 Agent 数量扩大，而是把可验证的责任单元、协议和证据聚合到价值网络层，再由战略意图层决定是否扩展。企业级扩展至少要经过三道判断：任务闭环是否连续成立，价值流是否在相同口径下获得净收益，组织是否具备跨单元的责任、遥测和恢复能力。任何一层不成立，都应停止扩展并回到较小责任域。

这就是白皮书所说的组织级 AI First 转型：分形扩展，是从单任务自治走向组织级可信自治的扩展路径。它要求先证明可重复，再证明可迁移，最后才讨论跨价值流复制；规模越大，越不能用“更多 Agent”替代协议、证据和责任。

因此，本章不是教组织如何堆叠更多 Agent，而是讨论如何减少不必要的协调，并为无法消除的依赖建立共同控制面。

本章只处理规模化协作的工程接口：所有权、Protocol、跨模块契约、集成 DAG、Handoff、证据聚合和跨工具语义。岗位、组织单元、激励与转型治理留到下一部分，避免把工程协作协议误当成完整组织设计。

> **最好的规模化是去规模化。**

去规模化不是拒绝大型系统，也不是把团队退回个人作业，而是尽可能把大协作拆成小责任域：减少共享状态、并发写入者、共同决策者和全局上下文，让每个单元拥有明确意图、边界、责任和独立证据。只有那些不能通过拆分消除的依赖，才进入 Protocol、XC、集成 DAG 和证据聚合。

```text
规模化 ≠ 更多人 × 更多 Agent × 更多协调流程

规模化 = 更小责任单元
       × 更少耦合
       × 可独立验证
       × 必要时再集成
```

规模化风险也不是人数或模块数的简单相加，而会被协作关系放大。可以用下面的概念模型帮助团队识别危险信号：

```text
规模化风险
= 并行任务数
× 交接次数
× 接口数量
× 工具差异
× 状态变化速度
× 验证不一致程度
```

这不是用于计算精确分数的数学公式，而是一张诊断图。任一因子持续上升，都会放大其他因子的影响：更多并行任务会产生更多交接；更多接口会加快状态变化；工具差异越大，验证结果越难比较。去规模化的意义，就是优先降低这些乘数，而不是在风险已经放大后继续增加协调层。

## 20.1 先去规模化，再升级治理复杂度

面对复杂项目，OA 的第一反应不应是增加全局会议、共享群聊和统一大模型，而应先追问：任务能否缩小，责任域能否拆开，写入边界能否隔离，接口能否提前稳定，验证能否在模块内完成？

去规模化至少包含四项原则：

1. **减少共享状态**：能通过独立模块、工作树、稳定接口和版本化工件隔离的，不依赖所有人实时同步。
2. **减少并发写入者**：同一责任域在同一时间窗口内默认只有一个活跃写入者，其他人或 Agent 可以并行审查、设计测试和核验证据。
3. **减少共同决策者**：一个任务可以有多个参与者，但必须有一个明确 IO；参与讨论不等于拥有最终执行权。
4. **减少全局上下文**：模块 Agent 只获得完成任务所需的 Context Slice，不把全部聊天、代码和历史无差别注入每个 Agent。

只有去耦后仍满足下列任一条件，才应考虑升级治理复杂度：

- 项目包含两个以上独立模块；
- 两人以上并行工作；
- 同时使用两种以上 AI 工具；
- 存在跨服务接口和发布依赖；
- 模块使用不同语言或测试体系；
- 单模块证据需要汇聚为统一发布结论。

这些条件只是触发进一步判断，不表示必须启用全套治理。两个互不依赖的模块可以各自形成小闭环；两个修改同一核心模块的人，即使人数很少，也可能需要强冲突控制。治理重量应由共享状态、依赖强度、失败传播和责任冲突决定，而不是由团队人数机械决定。

单人单模块项目不需要 Protocol 和两级 OA。能够通过串行、拆分或明确所有权消除的协调，也不应为了“完整”引入额外层级。

## 20.2 三条复杂度轴

多人、多工具和多模块不是同一个问题：

| 复杂度轴 | 主要风险 | 首选治理动作 |
|---|---|---|
| 多人 | 目标解释冲突、责任不清、并发写入、验收权争夺 | 明确 IO、所有权、Change Envelope 和交接规则 |
| 多工具 | 权限不同、上下文不一致、身份与证据来源丢失 | 统一 Task ID、契约版本、Tools Manifest 和证据语义 |
| 多模块 | 接口漂移、依赖顺序、数据一致性、系统级回滚 | Protocol、XC、集成 DAG 和 Release Evidence Bundle |

三条轴可以单独出现，也会相互叠加。一个人用多个 Agent 修改同一模块，首先是多工具和并发写入问题；多人分别维护互不依赖的模块，治理反而可以很轻；多人通过多个工具修改多个强耦合模块，则需要完整的跨模块控制面。

OA 应先识别复杂度来自哪条轴，再选择最小充分控制。不要因为项目用了多个 Agent，就自动复制所有多模块工件。

### 20.2.1 九类必须解决的协同问题

多人、多工具、多模块治理需要回答九类问题。后续 Protocol、XC、DAG、Handoff 和证据聚合，都是对这些问题的具体回应。

| 问题 | 失控表现 | 最小控制 | 本章落点 |
|---|---|---|---|
| 1. 意图分裂 | 各模块局部正确，端到端价值失败；后来的口头要求覆盖已签署目标 | 全局意图、模块契约、唯一 IO、变更版本 | 18.4、18.14 |
| 2. 并发写入冲突 | 多人或多批 AS 修改同一责任域，Git 可合并但业务语义互相覆盖 | 所有权、Change Envelope、单写入者、合并验证 | 18.3、18.18 |
| 3. 上下文不一致 | 不同人和工具使用不同契约、接口、记忆或代码版本 | 仓库事实源、Context Slice、版本标识、UNKNOWN | 18.13—18.15 |
| 4. 模块边界漂移 | 职责外溢、共享模型被多方修改、接口语法一致但含义不同 | 模块所有权、Protocol、XC、跨模块不变量 | 18.5、18.6 |
| 5. 依赖与顺序失控 | 下游基于推测开工、迁移先于兼容版本、失败后无法判断阻塞范围 | 集成 DAG、检查点、超时、失败路由和系统级回滚 | 18.7、18.17 |
| 6. 多工具治理失配 | 权限、能力和输出不同；工具升级后行为变化；证据来源丢失 | Tools Manifest、统一 Task ID、Handoff 和证据协议 | 18.8、18.13、18.15 |
| 7. 局部证据无法组成整体 | 模块全部 GREEN，系统仍不能发布；UNKNOWN 被汇总页面隐藏 | XC 验证、集成测试、Release Evidence Bundle | 18.9—18.11 |
| 8. 责任悬空 | 多人都能发指令，却无人拥有最终意图、接口或发布责任 | 两级责任、唯一签署人、接口所有者、异常裁决人 | 18.4、18.14、18.18 |
| 9. 规模化没有净收益 | Agent 越多，等待、返工、验证和监督成本越高 | 协同成本遥测、去规模化、动态选择自治级别 | 18.19 |

九类问题并不要求九套独立流程。最好的控制通常同时解决多个问题：稳定 XC 可以减少边界漂移、上下文争议和重复交接；单写入者可以同时降低写入冲突、状态变化和验证不一致；唯一 IO 可以同时解决意图分裂与责任悬空。

### 20.2.2 协同场景矩阵

治理应从真实协同拓扑出发，而不是看到“多人”或“多 Agent”就启用相同流程。

| 协同场景 | 主要矛盾 | 推荐默认 | 关键治理资产 |
|---|---|---|---|
| 不同项目、没有依赖 | 几乎没有共享状态 | 完全独立闭环 | 各自的 Intent Contract 与 Evidence |
| 多个项目共享平台、治理资产或组织目标 | 指标口径、共享依赖和改进政策可能跨项目传播 | 项目独立执行，组织层只汇聚可比信号 | 度量契约、可比群组、组织 Dashboard、证据下钻 |
| 同一项目、不同模块、无依赖 | 并行工作但不存在系统冲突 | 独立并行，最后做基础集成 | Task ID、独立 Change Envelope |
| 同一项目、不同模块、有接口依赖 | 文件不冲突，但语义、版本和顺序冲突 | 受约束并行 | XC、集成 DAG、端到端验证 |
| 同一项目、不同模块、共享数据或配置 | 状态一致性和迁移顺序 | 分阶段执行 | 数据所有权、迁移计划、补偿与系统级回滚 |
| 同一项目、相同模块 | 并发写入和共享不变量冲突 | 默认单写入者，其他人并行验证 | 所有权、写入边界、合并验证 |
| 同一任务、多种 AI 工具接力 | 上下文、权限和证据来源不一致 | 统一任务身份后 Handoff | Tools Manifest、Task ID、契约版本、证据协议 |
| 多语言、多测试体系 | 测试框架不同，结果难以聚合 | 不统一工具，统一证据语义 | checks、AC/Constraint ID、Evidence Bundle |
| 大型既有系统跨模块变更 | 隐性依赖、历史行为和未知模块 | 先 Recon，再限定变更围栏 | Baseline、Preserve、UNKNOWN、Change Envelope、Characterization Test |
| 客户、FDE、总部和供应商共同交付 | 上下文可见性、商业边界和外部证据可信度 | 按组织边界分层授权 | Protocol、责任矩阵、证据来源、商业与数据边界 |
| 多人共享聊天、单一 IO | 多人参与，但执行权可明确 | 协作平面与执行平面分离 | 消息分类、唯一 IO、Task ID、Context Slice |
| 多人共享聊天、多个 IO | 多个意图主体争夺同一批 AS | 默认停止，先裁决责任 | 意图冲突记录、HITL、独立任务或 Amendment |
| 跨模块紧急事故 | 正常 DAG 失效，各模块自行恢复可能扩大事故 | 单一事故指挥，冻结非必要写入 | Incident Work Graph、权限撤销、证据保全、系统级恢复 |

其中三个场景需要特别强调：

- **大型既有系统**不能从理想模块图出发，必须先 Recon。未发现的依赖应保留为 UNKNOWN，不能因为 Code Map 没显示就断言“不受影响”。
- **跨组织和 FDE 交付**不仅是模块协作，还涉及谁能看到什么、谁有权接受外部证据、现场例外如何回流产品治理，以及商业责任在哪里停止。
- **跨模块事故**不能继续沿用正常并行节奏。应指定单一事故指挥者，暂停无关 Work Graph，冻结非必要写入，统一判断隔离、回滚和恢复顺序，防止各模块分别“恢复成功”却造成系统级二次故障。

## 20.3 团队内多人协同的三种拓扑

“多人共同开发同一个项目”至少包含三种完全不同的场景。

### 20.3.1 不同模块、没有实质冲突

例如 A 修改前端页面，B 修改独立报表服务，C 补充文档；三者不共享接口、配置、数据迁移和发布顺序。这是最适合并行的场景。

每项工作只需要独立 Task ID、Intent Contract、Change Envelope 和本地证据。最终进行基础集成检查即可，不必让所有参与者共享完整上下文，也不必为不存在的依赖建立 XC。

### 20.3.2 不同模块、存在语义或依赖冲突

例如 A 修改服务端接口，B 修改前端消费者，C 修改数据库结构。三者可能没有修改同一个文件，但字段语义、数据状态、兼容窗口和发布顺序互相影响。这类问题可以概括为：**文件不冲突，系统仍然会冲突。**

治理必须从文件边界上升到系统边界：先签署 XC，明确接口语义、幂等性、错误处理和版本策略；再用集成 DAG 规定实现、迁移、验证和发布顺序；最后通过端到端证据证明局部结果可以组成系统结果。

### 20.3.3 相同模块、存在并发写入冲突

例如 A 修复支付模块，B 同时重构支付模块，C 又要求调整相同异常逻辑。Git 没有文本冲突，并不代表没有语义冲突：一个修改可能删除另一个修改依赖的不变量，两组测试可能分别通过，合并后却不再满足任何一份完整意图。

默认策略应是：

> 相同模块、相同责任域、相同时间窗口，只允许一个活跃写入者。

其他参与者可以并行进行测试设计、安全审查、反例生成和 Evidence 核验。如果确实要并行写入，必须先把模块进一步拆成不重叠的 Change Envelope，并证明它们不存在共享不变量。不能完成这种拆分时，串行执行比增加协调工具更可靠。

| 团队内场景 | 默认执行方式 | 最小治理 |
|---|---|---|
| 不同模块、无依赖 | 并行独立闭环 | Task ID + 独立 Change Envelope |
| 不同模块、有接口依赖 | 受约束并行 | XC + 集成 DAG + 端到端验证 |
| 不同模块、共享数据或配置 | 分阶段并行 | 所有权 + 迁移顺序 + 系统级回滚 |
| 相同模块、相同责任域 | 默认串行写入 | 单写入者 + 并行验证 |
| 相同模块、可进一步拆分 | 隔离并行 | 不重叠 Change Envelope + 合并验证 |

## 20.4 全局 OA 与模块 OA

全局 OA 负责：

- 全局意图和约束；
- 模块边界；
- Protocol；
- 跨模块契约；
- 集成 DAG；
- 证据聚合和发布裁决。

模块 OA 负责：

- 模块任务契约；
- 模块上下文和工具；
- 本地约束与测试；
- 模块 Evidence Bundle；
- 向全局 OA 报告真实状态和未知项。

两级 OA 不是天然必须存在的管理层级。只有跨模块依赖无法通过去耦消除时，才需要全局 OA；模块能够独立闭环时，全局 OA 只管理共同边界和集成事实，不介入模块日常执行。

## 20.5 Protocol：跨主体治理协议

Protocol 至少定义：

- 模块清单与所有者；
- 共享术语；
- 跨模块接口；
- 版本兼容；
- 集成顺序；
- 每种语言的 checks；
- Handoff 格式；
- 失败升级路径；
- 发布证据要求。

它不是替代所有模块文档，而是建立跨模块最小共同语言。

## 20.6 跨模块契约 XC

模块内部测试通过，不代表集成成立。XC 应定义：

- 请求和响应模式；
- 必填字段；
- 错误语义；
- SLA；
- 兼容策略；
- 破坏性变更规则；
- 上下游验证证据。

XC 还应说明业务语义、幂等性、事件顺序、数据所有权、迁移责任、补偿动作和旧版本退出条件。字段结构一致只能证明语法兼容，不能证明两个模块对“审批完成”“付款成功”或“允许重试”的理解一致。

## 20.7 集成 DAG 与发布顺序

集成 DAG 是一张描述跨模块交付依赖的有向无环图。每个节点代表能够判断完成与否的工作单元，箭头表示“后一个节点必须等待前一个节点的有效产物”。“无环”意味着依赖不能形成 A 等 B、B 又等 A 的死锁。

任务清单能说明有什么工作，却不能说明顺序、并行机会和失败影响。一个接口升级可能同时涉及服务端兼容、前端适配、数据迁移、集成测试和灰度发布。若迁移先于兼容版本上线，或者消费者尚未准备就删除旧字段，所有单项任务即使都完成，系统仍会失败。

```text
XC 接口契约签署
 ├─ 服务端兼容实现与证据
 ├─ 前端新字段适配与证据
 └─ 数据迁移脚本及回滚演练
          ↓
跨模块集成测试
          ↓
灰度发布与观测
          ↓
确认旧接口下线条件
```

每个节点需要输入、输出、责任人、AC、超时、失败路由和证据位置。发布节点不能只检查上游状态为“完成”，还要验证上游证据属于同一契约版本，并且所有 MUST 门禁通过。

发布顺序本身就是风险控制。常见策略包括“先兼容生产者，再升级消费者，最后移除旧接口”；数据迁移则可能采用“先双写、再回填、后切读、最后停旧写”。具体顺序取决于系统，但必须显式化并可回滚。

当某个节点失败时，DAG 帮助 OA 判断哪些并行节点仍可继续、哪些下游必须阻塞、回滚会不会破坏已经完成的工作。回滚前还需要分析下游依赖和数据兼容，避免一个模块安全回滚却破坏整个系统状态。

## 20.8 多语言 checks

不同模块可以使用不同工具，但必须把结果转换为统一证据语义：

```text
command
exit_code
result
artifact
timestamp
constraint_or_ac_id
```

统一的不是测试框架，而是证据协议。

## 20.9 证据聚合

每个模块生成自己的 Evidence Bundle。全局 OA 聚合：

- 模块契约版本；
- 跨模块 XC 结果；
- 集成测试；
- 全局 MUST 约束；
- 模块未知项；
- 合并遥测；
- 统一回退方案。

最终产生 Release Evidence Bundle，供发布裁决使用。

聚合不能把模块状态简单相加。Release Evidence Bundle 至少要证明：各模块满足局部责任，模块之间满足 XC，端到端系统满足全局意图和 MUST，系统级回退能够成立。任何模块的 UNKNOWN、证据过期或契约版本不一致，都不能在汇总页面中被绿色平均值掩盖。

## 20.10 跨项目价值与效能视图

这个视图不等于另一个项目管理大屏，更不是对个人工作量的监控。它面向人机协同研发系统，展示：

- 当前意图和任务状态；
- 五道门通过情况；
- MUST 失败；
- HITL 等待项；
- 模块和跨模块证据；
- 单任务与累计遥测；
- 风险、例外和失效时间；
- 发布建议和依据。

它的目标是让价值流、系统能力、治理状态和残余风险透明，使管理者能够判断哪里值得扩大自治、哪里需要补强工程系统、哪里必须由人承担决策责任。

## 20.11 一个跨模块失败案例

报销前端、规则服务和财务接口分别通过了本地测试，但集成时发现规则服务返回字段 `approverRole`，财务接口仍读取 `approver_role`。三个模块都声称完成，系统却无法运行。

根因不是测试不足，而是缺少跨模块契约和统一发布证据：

- 模块契约只描述内部行为；
- 没有 XC 定义字段和兼容策略；
- 集成 DAG 没有安排契约验证；
- 模块 Evidence Bundle 没有汇聚；
- 下游相信了上游的完成声明。

加入 XC 后，字段、版本、错误语义和破坏性变更规则成为可验证对象。模块仍然可以自主开发，但接口不能自主漂移。

## 20.12 两级约束

多模块项目通常同时存在：

**全局约束**：安全、数据、发布、审计、公共技术标准。

**模块约束**：语言、框架、局部性能、模块目录和测试方式。

模块 OA 可以维护局部约束，但不能降低全局 MUST。发现冲突时必须升级给全局 OA 和责任人。

## 20.13 多工具治理

团队可能同时使用 Codex、Claude Code、IDE Agent、CI Bot 和内部平台。治理不能依赖某个工具的对话记忆，而应落在仓库资产中：

- 同一意图契约；
- 同一约束矩阵；
- 同一 Tools Manifest；
- 同一 Evidence Bundle 语义；
- 不同工具各自适配执行接口。

工具可以替换，治理责任和证据链不能随工具消失。

多工具接力同一任务时，每一次 Handoff 都应携带 Task ID、契约与约束版本、已修改范围、测试状态、开放 UNKNOWN、下一步动作和证据位置。新工具不能把上一工具的聊天摘要当作唯一事实源，也不能因为自己具备更高权限就自动扩大执行范围。

## 20.14 多人共享一个聊天窗口：多主控制问题

一种看似自然的协同产品，是让两人或多人共同面对一个聊天窗口：A 提出需求，等待 AS 完成；B 接着要求修改；C 又提出新需求；随后 A 认为方向不对，再要求改回。底层始终是同一批 AS、同一上下文和同一个工作目录。

这不是普通的多人协同，而是“多意图主体共享同一执行会话”的**多主控制问题**。它最先冲突的不是代码，而是意图和授权：

- A、B、C 谁是当前任务的 IO；
- 后续消息是澄清、正式变更、新任务，还是未经确认的建议；
- 谁能修改非目标、扩大 Change Envelope 或改变优先级；
- 已完成的测试和 Evidence 对应哪一版要求；
- 多人意见冲突时，AS 应停止还是自行折中；
- 最终由谁验收并承担结果。

“多人能够参与同一对话”是真实需求；“多人可以直接向同一批 AS 连续发出执行指令”通常是伪需求。团队真正需要的往往是共同可见、共同讨论、专业意见输入和决策透明，而不是所有人同时握住执行方向盘。

共享会话应被拆成两个逻辑平面：

| 平面 | 参与者可以做什么 | 不能自动产生什么 |
|---|---|---|
| 协作平面 | 提建议、补充上下文、提出风险与反例、评论证据 | 不直接改变已签署意图和执行范围 |
| 执行平面 | 由当前任务授权 IO/OA 创建任务、确认变更、启动 AS、批准不可逆动作 | 不接受无责任身份的最后一句话覆盖当前契约 |

### 20.14.1 多主会话的最小规则

如果产品确实要支持多人共享一个 Agent 会话，至少需要遵守以下规则：

1. **保留身份与角色**：每条消息必须记录发送人、时间和角色，不能把多人输入压缩成无来源的统一 Prompt。
2. **每个任务只有一个 IO**：可以有多名参与者、专家和审核人，但当前任务必须有唯一的意图责任人。
3. **普通消息默认是建议**：非当前 IO/OA 的消息默认进入协作平面，不能直接触发代码修改、工具调用或范围变化。
4. **执行前先做消息分类**：系统必须区分建议、澄清、正式变更、新任务和讨论，不能把每一句话都解释为新命令。
5. **变更已签署意图时暂停执行**：涉及目标、非目标、AC、优先级或 Change Envelope 的变化，必须停止当前 AS，等待 IO 确认并形成新版本或 Amendment。
6. **每批 AS 绑定明确执行快照**：执行必须绑定 Task ID、契约版本、约束版本、Change Envelope 和 Context Slice，不能跟随聊天窗口持续漂移。
7. **执行上下文与完整聊天隔离**：AS 只接收裁剪、确认后的执行上下文；争论、猜测、玩笑、撤回意见和未确认方案不进入执行 Prompt。
8. **新任务不得混入运行中的任务**：新需求应获得独立 Task ID、契约和证据链，不能悄悄追加到正在执行的任务中。
9. **冲突时停止，不由模型折中**：多人意见冲突、责任不清或批准边界为 UNKNOWN 时，AS 必须暂停并触发 HITL，不能依据最后发言、职位高低或表达强度自行选择。
10. **验收权必须明确**：任务完成、发布和不可逆动作只能由预先定义的责任人裁决；群聊中的沉默、点赞或无人反对不构成签署。
11. **撤回和替代必须传播**：被撤回、拒绝或 superseded 的要求必须退出 Context、Memory、任务队列和后续 Handoff，不能继续暗中影响 AS。
12. **全链路可以追溯**：最终产物必须能够回答谁在何时提出、谁确认、基于哪份契约执行、哪些 AS 参与、产生了什么证据，以及谁作出最终裁决。

这 12 条规则的目标不是让共享聊天变成审批系统，而是确保“多人可以参与”不会退化成“任何人都可以随时改变机器正在执行的意图”。如果产品无法提供身份、唯一 IO、版本快照、暂停机制和可追溯性，就不应把共享会话直接连接到具有写入权限的 AS。

所有消息进入执行前，应先分类为“建议、澄清、变更、新任务或讨论”。建议进入候选区；澄清由 IO 确认后写回当前契约；正式变更产生新版本或 Amendment；新任务获得独立 Task ID；讨论内容不进入 AS 的执行 Context Slice。

```text
多人发言
→ 消息分类：建议 / 澄清 / 变更 / 新任务
→ IO 确认
→ 形成稳定契约版本或独立任务
→ 绑定一批 AS 与 Change Envelope
→ 执行、验证、验收
→ 再切换下一意图
```

多人共享窗口在结对编程、Mob Programming、方案评审、跨专业咨询和教学工作坊中可以有价值，但必须有一个明确 Driver 或 IO。多人意见发生冲突时，系统应暂停执行并请求责任裁决，不能让模型依据消息顺序、表达强度或“综合判断”选择方向。

每批 AS 必须绑定明确 Task ID、契约版本和上下文快照。AS 不直接消费未经裁剪的全部聊天历史，已撤回意见也必须退出后续上下文。否则共享聊天只是在用界面便利掩盖责任和状态混乱。

## 20.15 Handoff 摩擦

多 Agent、多模块和多工具会产生交接摩擦。可以观察：

- 上游输出被下游退回次数；
- 因字段或版本不一致造成的失败；
- 重复读取和重复验证；
- 等待人工澄清时间；
- 交接后新发现的未知项；
- 跨模块返工比例。

这些数据帮助团队判断问题来自执行能力，还是协议和上下文设计。

有效 Handoff 不是“我做完了”的自然语言声明，而是一个可验证的状态转移。下游应能确认上游产物属于正确契约版本、相关 MUST 已通过、未知项未被隐藏、证据仍在有效期内。条件不满足时，Handoff 应被拒绝，而不是由下游默默补齐上游责任。

## 20.16 跨项目视图反模式

- 把每个 Agent 的 Token 排名作为绩效；
- 只显示绿色状态，不显示 UNKNOWN；
- 模块自己上传“已通过”文本；
- 跨项目视图与真实仓库工件不同步；
- 例外到期后仍显示通过；
- 大屏很漂亮，却不能追溯到原始证据；
- 管理层用自动化率替代价值和风险判断。
- 把更多并行 Agent 数量当作规模化成功；
- 允许多人在共享会话中以最后一条消息覆盖当前意图；
- 同一模块存在多个活跃写入者，却只依赖 Git 解决语义冲突。

## 20.17 跨模块变更的治理链

以“报销审批结果同步到财务付款”为例，变更可能同时影响报销服务、审批服务、财务接口和审计日志。全局契约定义端到端结果与不可妥协边界，各模块契约定义局部责任，XC 定义接口字段、时序、幂等性和错误语义。

某个模块的单测全绿，只能证明局部实现满足局部假设。集成门还必须验证：审批完成事件不会重复付款，失败重试不会丢失审计信息，旧版本消费者能够处理新增字段，任何模块失败时端到端状态可恢复。最终 Evidence Bundle 必须保留模块证据来源，不能只给出“集成成功”的汇总结论。

## 20.18 所有权比工具统一更重要

组织可能同时使用 Codex、Claude Code、GitHub Copilot、内部 Agent 和传统脚本。治理目标不应是强迫所有人使用同一个界面，而是要求不同工具服从共同协议：读取同一份签署契约，遵守同一约束来源，产生可识别 Handoff，接受统一门禁，并把证据写回任务目录。

真正需要统一的是任务身份、责任、协议和证据语义。工具可以替换，治理链不能因为换了模型就断裂。

## 20.19 规模化的经济边界

多 Agent 不总是更便宜。组织应同时计算执行成本、上下文准备成本、冲突与重试成本、验证成本以及人类监督成本。只有当任务可分解、接口稳定、验证可自动化并且失败影响可控时，自治规模化才会产生净收益。

对于高度探索、意图频繁变化或责任无法拆分的任务，小团队与单一 Agent 可能更有效。成熟度不是永远增加自治，而是能够根据风险动态选择自治级别。

组织评估规模化收益时，不应只统计 Agent 产出或并行任务数，还应计算上下文准备、协议维护、等待、冲突、重复验证、证据聚合和人工监督成本。如果增加一个 Agent 节省了十分钟编码，却带来一小时协调和返工，它不是扩展了能力，只是扩大了队列。

真正成熟的规模化表现往往不是中央大屏上运行着最多 Agent，而是大量任务已经被拆成彼此独立的小闭环，只有少数真实依赖需要全局协调。组织级视图的成功，应体现为协调需求下降，而不是协调活动增加。

## 20.20 跨项目遥测：可以汇聚，但不能直接排名

第十四章建立了“单契约 → 单项目”的双层遥测。进入多人、多工具、多模块和多项目环境后，组织还需要第三层视角：项目组合与组织级遥测。它用于识别跨项目风险、共同瓶颈和治理资产复用机会，但不能把不同项目的数字直接放在一起排名。

```text
单契约遥测：这次任务发生了什么
        ↓
单项目遥测：这一类任务是否正在改善
        ↓
跨项目遥测：哪些模式具有组织意义
```

跨项目汇聚最难的不是把 JSON 合并，而是保证比较有意义。一个高风险金融项目和一个内部演示工具，即使都显示“首次成功率 80%”，其失败后果、验证成本和 HITL 责任也完全不同；一个遗留系统的改动可能只涉及几十行代码，却需要大量 Recon 和兼容验证；一个新项目的高自动化率，也可能只是因为没有历史约束。

因此，跨项目比较必须先建立可比群组。至少按以下维度分群：

- 任务类型：探索、功能交付、缺陷修复、迁移、事故恢复；
- 治理 Profile：explore、delivery、high-risk、legacy、multi-module；
- 风险与影响：内部可逆、用户影响、资金或敏感数据、安全关键；
- 工程基础：新项目、既有小项目、大型遗留系统；
- 技术与执行环境：语言、测试体系、工具、模型和运行环境；
- 观察窗口：相同周期、相似样本量和同一指标版本。

没有分群时，不做横向排名；没有共同口径时，不计算组织平均值；没有来源和样本量时，不把趋势解释成事实。

### 20.20.1 跨项目度量契约

每个准备进入组织级 Dashboard 的项目，都应声明一份最小度量契约：

| 字段 | 作用 |
|---|---|
| project_id / owner | 标识项目和解释责任人 |
| task taxonomy | 说明任务怎样分类，避免混合不同工作 |
| governance profile / risk class | 说明治理重量和失败后果 |
| metric definition version | 标识公式、分母和阈值版本 |
| source / evidence link | 能从汇总数字下钻到任务与原始证据 |
| baseline / comparison cohort | 说明与谁比较、为什么可比 |
| sample size / time window | 防止小样本和时间错位造成误判 |
| tool / model / environment | 解释工具和环境变化带来的影响 |
| data quality / UNKNOWN | 暴露缺失、估算、过期和采集失败 |
| access / retention | 约束谁能看到、保留多久、怎样删除 |

度量契约发生变化时，组织应保留版本边界。不能把不同公式、不同任务分类或不同风险口径的数据无标记地画成一条连续趋势线。

### 20.20.2 哪些信号值得跨项目观察

跨项目遥测的目标不是寻找“最强团队”，而是识别系统性问题和可复用改进机会。适合观察的信号包括：

- 目标准确率与首次成功率在同类任务中的分布；
- 发布后缺陷、回滚和事故率；
- 验证成本是否随风险合理增长；
- HITL 是否发生在价值、异常和不可逆边界，而不是被当作补锅；
- UNKNOWN 被发现、裁决和关闭的时间；
- Handoff 退回率、跨模块返工和集成等待；
- 相同约束失败是否在多个项目重复出现；
- 共同 Skill、模板、测试模式和治理政策是否真正提高复用效果；
- Token、时间和人工投入是否换来了质量或风险改善。

Token 总量、测试数量、覆盖率、自动化率和 Agent 数量不能脱离任务价值与风险单独排名。低 Token 可能来自上下文不足，高覆盖率可能没有覆盖关键行为，高自动化率也可能意味着必要 HITL 被绕过。

### 20.20.3 汇聚必须能够下钻和反向传播

组织级 Dashboard 上的每个结论，都应能够沿下面的链路下钻：

```text
组织趋势
→ 可比项目群组
→ 单个项目
→ 单份 Intent Contract
→ Evidence Bundle
→ 原始测试、约束与遥测来源
```

汇聚也必须支持反向传播。如果多个项目反复出现同一类接口漂移、权限误用或验证缺口，治理委员会可以提出组织级约束、共享测试、Protocol 或 Skill 候选；但从“共同现象”晋升为“统一政策”，仍需验证适用范围、反例和副作用，不能由 Dashboard 自动修改所有项目。

跨项目遥测应帮助组织判断哪些复杂度可以被消除。例如多个项目都因同一种 Handoff 失败而返工，最佳行动可能不是增加一个跨项目协调角色，而是稳定接口、统一证据字段或进一步拆小责任域。遥测最终应服务于去规模化。

### 20.20.4 跨项目遥测的反模式

- 用首次成功率、Token 或自动化率直接给项目和团队排名；
- 把不同风险、任务类型和工程基础的数据计算成一个平均值；
- 只展示百分比，不展示分母、分布、时间窗口和 UNKNOWN；
- 指标公式升级后，仍把新旧数据画成连续趋势；
- 汇总数字无法下钻到契约和 Evidence Bundle；
- 为追求统一口径，删除项目真正需要的行业与风险差异；
- 把治理成本转移给 QA、运维、客户或供应商，却仍宣称研发效率提升；
- 组织级 Dashboard 收集了敏感代码、客户数据或个人绩效信息，却没有访问和删除边界；
- 发现跨项目问题后，第一反应是增加审批层，而不是减少耦合和共享状态。

跨项目遥测的正确问题不是“哪个项目数字最好”，而是：在相同风险和任务类型下，哪些控制真正减少了失败、返工和决策成本；哪些做法只是在本地看起来高效，却把风险转移给了其他模块、项目或人。

## 20.21 本章小结

多人、多工具、多模块治理的目标，不是让更多人和 Agent 同时进入同一个上下文，而是通过去规模化减少必须协调的部分。不同模块无依赖时各自闭环；存在接口和数据依赖时使用 XC 与集成 DAG；相同责任域默认保持单写入者；多人共享聊天时把协作权与执行权分开，并为每批 AS 绑定唯一意图和责任主体。

Protocol、XC、集成 DAG、Handoff 和证据聚合，是为无法消除的依赖建立共同控制面。它们最终要证明的不是“所有模块都说自己完成了”，而是局部结果能够组成端到端价值，失败能够被阻断和恢复，发布结论能够追溯到真实责任与独立证据。

跨项目遥测把单契约与单项目信号提升为组织学习，但必须先分群、统一度量契约并保留证据下钻。它的目的不是排名团队，而是发现系统性风险、验证共同治理资产，并判断哪些协调和耦合可以继续被消除。

**本章最小实践**：把报销案例拆成前端、规则服务和财务接口三个模块，先判断哪些协作可以通过去规模化消除，再为剩余依赖设计所有权、XC、集成 DAG 和多人消息分类规则。  
**完成证据**：协同拓扑与单写入边界、Protocol、两个 XC、Handoff 记录、共享会话执行权规则、Release Evidence Bundle，以及一份带可比群组和证据下钻的跨项目度量契约。  
**延伸实践**：推荐学习《Agentic Agile 组织转型进阶：构建人机协同研发操作系统》，判断什么时候可以从单任务闭环扩展到价值网络，什么时候必须停止扩张。
