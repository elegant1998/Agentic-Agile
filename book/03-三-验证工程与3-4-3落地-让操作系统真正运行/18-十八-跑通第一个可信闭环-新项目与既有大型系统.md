# 第十八章｜跑通第一个可信闭环：新项目与既有大型系统

## 18.1 两条并行落地路径

3-4-3 面对新项目和既有大型系统时，使用的是同一套治理原则，却不能采用同一条进入路径。

新项目通常缺少历史包袱，团队可以从意图、约束和测试开始塑造系统；既有大型系统已经包含大量真实行为、隐性规则和历史责任，团队必须先认识并保护现实，再改变其中一小部分。前者是 **Governance by Design（治理先行）**，后者是 **Governance by Change（变更驱动治理）**。

| 维度 | 新项目路径 | 既有大型系统路径 |
|---|---|---|
| 起点 | 新的业务意图 | 下一次真实变更 |
| 主要不确定性 | 目标与方案尚未成形 | 现状、依赖与历史规则不完整 |
| 首要动作 | 澄清契约、建立约束和测试骨架 | Recon、现状基线和影响分析 |
| 主要风险 | 过度设计、需求漂移、治理过重 | 隐性耦合、规格漂移、破坏未知行为 |
| 边界工具 | Intent Contract、Constraint Matrix | Baseline、Preserve/Unknown、Change Envelope |
| 验证重点 | 新行为是否符合签署意图 | 新行为成立且关键旧行为未被破坏 |
| 扩展方式 | 从 T-001 复用到后续任务 | 从第一座治理岛扩展邻接保护区 |

两条路径是并行选择，不是成熟度先后。新项目不必先经历遗留系统治理，既有系统也不必等到“完全重构成新项目”才开始使用 3-4-3。

## 18.2 新项目：从零建立第一个可验证治理闭环

新项目路径适合边界较清晰的新能力、内部工具、独立服务或可隔离模块。这里的“新”不是指整个企业从零开始，而是指本次交付可以在没有大量未知历史行为的前提下建立新的契约、约束和验证基线。

### 18.2.1 不从平台建设开始

组织第一次实践 3-4-3 时，最容易犯的错误是先规划一个庞大的 Agent 平台、治理门户和指标中心。更可靠的方式是选择一个真实、边界清楚、可自动验证、可安全回退的小任务，跑通完整闭环。

第一个闭环的目标不是证明 AI 无所不能，而是证明：

- 模糊需求能够被校准；
- 人类责任能够被明确；
- Agent 能在约束下执行；
- 失败能够被发现和修复；
- 完成能够被证据证明；
- 数据能够反哺下一次任务。

### 18.2.2 选择第一个任务

推荐特征：

- 对业务有真实价值；
- 规则边界可以说清；
- 影响范围可控；
- 有现成测试环境；
- 可以回退；
- 能在较短周期完成；
- IO 能够及时作出决策。

不推荐把生产数据删除、核心资金链路重构、跨十几个团队的大型迁移作为第一个任务。

### 18.2.3 初始化治理目录

```text
governance/
├── Intent_Graph.md
├── Constraint_Matrix.md
├── constraints.yaml
├── AI_Coding_Guide.md
├── contracts/
│   └── Intent_Contract_T-001.yaml
├── evidence/
│   └── EB-T-001.md
└── telemetry/
    └── runs/
```

从开源 Skill 复制模板，而不是从零发明格式。

### 18.2.4 T-001：费用报销规则

#### Specify

IO 提出：“超过 5000 元的报销，增加总监审批。”

经过 Grill-Me 后确认：

- 按报销单含税总额计算；
- 严格大于 5000 元触发；
- 本任务只处理境内人民币差旅；
- 5000 元及以下保持现有路径；
- IO 审阅并签署完整契约。

#### Constrain

设置：

- 禁止读取生产数据；
- 只允许修改审批规则模块和对应测试；
- 现有 5000 元及以下路径必须回归通过；
- 必须先写失败测试；
- 任何生产发布需人类批准。

#### Orchestrate

工作图包含：影响分析、测试生成、实现、回归、证据和遥测。测试与影响分析可以并行，实现必须等待测试骨架完成。

#### Prove

先运行 5000.01 元和 5000.00 元边界测试，看到预期 Red；再完成最小实现，使测试 Green；最后重构重复条件。

#### Evolve

故意注入一个 `>= 5000` 的错误，确认 AC-02 能拦截；修复为 `> 5000`，重跑同一测试并记录教训。

#### Verify

运行 AC、Harness、全量测试、构建和回归，生成 EB-T-001。

#### Telemetry

采集单任务遥测，更新项目累计数据和仪表板，回写意图图谱。

### 18.2.5 五道机械门

```bash
# 1. 前置门：契约、签署、约束与 AC
python scripts/gate_check.py --gate pre --task T-001 --project-dir .

# 2. 编码门：TDD Red
python scripts/gate_check.py --gate coding --task T-001 --project-dir .

# 3. 验证门：TDD Green、AC、构建与证据
python scripts/gate_check.py --gate prove --task T-001 --project-dir .

# 4. 收尾门：证据、遥测、仪表板与图谱
python scripts/gate_check.py --gate closing --task T-001 --project-dir .

# 5. Bug 回溯门：完成后发现问题时使用
python scripts/gate_check.py --gate bug --task T-001 --project-dir .
```

门禁的价值是把“应该做”变成“没有做到就无法通过”。

### 18.2.6 第一个闭环的验收标准

- IO 真实签署契约；
- 至少一项运行时 AC；
- 有真实 Red 和 Green；
- MUST 约束全部通过；
- Evidence Bundle 完整；
- 单任务遥测存在；
- 图谱完成回写；
- 人类裁决有范围、条件和依据。

### 18.2.7 第一次实践的角色配置

最小团队不需要新增正式岗位，但必须明确三种责任：

- IO：由真正拥有报销规则解释权的人承担；
- OA：由能理解业务、代码、测试和治理工具的人承担；
- AS：可以是一个主 Agent，也可以是测试与实现两个 Agent。

财务、安全或运维专家按风险参加，不需要全程参与所有执行。

### 18.2.8 第一个闭环的工作节奏

#### 启动

选择任务、确认 IO/OA、检查测试环境和回退条件。时间可以很短，但不能跳过。

#### 契约形成

通过 Grill-Me 解决真正会改变结果的歧义。OA 起草，IO 独立签署。

#### 受控执行

AS 按 Work Graph 完成 Red、Green、Refactor 和约束检查。OA 只在微检查点和异常时介入。

#### 证据裁决

Evidence Bundle 先由 OA 审查完整性，再由 IO 作价值和风险裁决。

#### 复盘反哺

采集遥测，识别下次最值得改善的一个环节。不要第一次就追求全面平台化。

### 18.2.9 失败也可以是有效结果

第一个任务可能没有通过发布门。只要系统成功发现了不清晰规则、越权工具、无效测试或不可恢复风险，这次实践仍然产生价值。

评估首个闭环时，应问：

- 是否更早发现了问题？
- 是否限制了影响范围？
- 是否明确了责任？
- 是否保留了真实证据？
- 是否形成了下一次可复用资产？

不要为了证明试点成功，降低门禁获得一次虚假的全绿。

### 18.2.10 首次实践的常见陷阱

- 选择过大或不可逆任务；
- IO 没有时间参与，实际由 OA 代替决策；
- 直接使用完整模板，产生大量空字段；
- 没有真实测试环境；
- 只演示正常路径；
- 把“Agent 自动修复了很多次”当作成熟；
- 为制作汇报手工美化遥测；
- 试点结束后治理资产无人维护。

### 18.2.11 从 T-001 到 T-002

第二个任务不应简单重复。它应使用 T-001 沉淀的图谱、约束和模式，验证系统是否真的学习：

- Grill-Me 问题是否更少、更准确；
- 上下文是否更精简；
- 首次成功率是否改善；
- 约束是否更早拦截问题；
- Evidence Bundle 是否更容易生成；
- 人类介入是否更集中在真正的价值判断。

只有跨任务改善，才能说明组织开始形成能力。

### 18.2.12 一次完整的 T-001 决策记录

假设业务提出：“员工报销超过 5000 元需要总监审批，明天上线。”团队不直接把这句话交给 Agent，而是依次形成可判定事实。

Specify 阶段澄清金额口径、币种、税费、等于 5000 元的处理、历史草稿和紧急回退；Constrain 阶段写入禁止修改历史已审批单、禁止访问生产凭证、数据库迁移必须人工批准；Orchestrate 阶段把测试、领域规则、接口和证据节点组成 DAG；Prove 阶段先用三个边界例子看到 Red，再完成最小实现；Evolve 阶段处理一次旧接口语义冲突并保留修复证据；Verify 阶段汇总构建、测试、约束、差异和残余风险。

最终裁决可能不是简单的“上线”，而是：“新建报销单规则通过；历史草稿迁移不在本次范围；先对财务测试账号启用，观察两小时；异常率超过阈值自动关闭开关。”这就是从一句话需求到可控制发布的完整转化。

### 18.2.13 试点复盘应该讨论什么

第一次复盘不要只问 AI 节省了多少时间。更值得讨论的是：

- 哪个歧义如果未被追问，会造成错误交付？
- 哪条约束真正阻止了越界？
- 哪份证据改变了上线决定？
- 哪次人工介入不可替代，哪次可以自动化？
- 哪个工件下次可以复用，谁负责维护？
- 为了治理增加的成本，是否换来了更早的风险发现？

团队应保留原始数据和失败过程。一次看起来不够顺畅、却真实揭示问题的试点，比精心排练的自动化演示更有价值。

## 18.3 既有大型系统：从真实变更建立可验证治理岛

前面的 T-001 案例接近一项边界清楚的新能力：团队可以先写意图契约，再建立测试和实现。但企业真实环境中，大量 AI Coding 工作发生在运行多年、几十万甚至上百万行代码的既有系统里。文档不完整，模块相互耦合，现有测试薄弱，业务规则藏在代码、数据库、配置和人员记忆中；某些看似多余的逻辑，可能承担历史兼容或监管责任。

这时如果要求团队先治理整个系统、重建全部文档、补齐全部测试，再允许 Agent 开始修改，3-4-3 会变成一个没有终点的大工程。反过来，如果把整座遗留系统直接交给 Agent，让它“先理解再修改”，高速生成又会把未知依赖迅速放大。

因此，既有大型系统需要采用不同于新项目的落地策略：

> **新项目适合治理先行；既有系统适合变更驱动、增量接管。不是先治理全部代码，而是先治理下一次变化。**

### 18.3.1 不追求先理解整个系统

百万行系统不可能在一次会话、一次扫描或一次架构梳理中被完整理解。代码也不等于真实业务意图：文档可能过期，配置可能改变行为，线上数据可能触发隐藏分支，实际流程可能依赖人工补偿，生产运行结果还可能与设计不一致。

以下做法看似系统，实际风险很高：

- 一次性把整个仓库塞给模型；
- 自动生成全局架构图并当作事实；
- 为所有历史模块补写意图契约；
- 先重构遗留代码，再处理当前需求；
- 给全部业务路径补齐测试后才开始试点；
- 建设统一 Agent 平台以后才允许真实交付。

正确目标不是“Agent 已经理解全部代码”，而是：

> **在当前变更的影响半径内，团队已经获得足以安全行动的理解，并明确标出了仍然不知道什么。**

这意味着治理深度由变化和风险驱动，而不是由代码库体积驱动。一项只涉及一个报表字段的低风险修改，不需要先解释全部支付系统；一项涉及资金计算和历史数据迁移的三行修改，却可能需要跨模块、数据和运行时证据。

### 18.3.2 从项目初始化转向 Change-Driven Governance

新项目通常从治理资产向实现展开：

```text
意图图谱
→ 全局约束
→ 第一份意图契约
→ Work Graph
→ 新实现与证据
```

既有系统则从一次真实变化进入：

```text
真实变更请求
→ 找到业务与代码入口
→ 探测影响半径
→ 固化当前行为
→ 签署局部意图与兼容责任
→ 建立变更围栏
→ 在局部运行 SCOPE-V
→ 用前后证据证明结果
→ 将新知识回写局部图谱
```

这可以称为 **Change-Driven Governance（变更驱动治理）**。治理对象不是百万行代码本身，而是每一次进入系统的变化：为什么改、允许影响什么、必须保持什么、哪些区域仍未知、用什么证据证明没有破坏，以及本次发现怎样降低下一次变化的风险。

变更驱动不等于被动打补丁。每次任务都会增加一小块经过验证的系统知识，多个任务逐步把局部治理岛连接起来，最终形成真实而非想象出来的系统治理地图。

### 18.3.3 Recon：进入 Specify 前的认知侦察

新项目可以直接从 Specify 开始；既有系统通常需要在 S 之前增加一个轻量的 Reconnaissance，即**认知侦察**。Recon 不是 SCOPE-V 的第七个控制面，也不是无限期架构研究，而是为了让本次 Specify 有足够事实基础。

```text
Recon
→ Specify
→ Constrain
→ Orchestrate
→ Prove ⇄ Evolve
→ Verify
→ Telemetry
```

Recon 至少调查六类信息：

1. **代码结构**：入口、模块、共享库、关键类和静态依赖；
2. **运行关系**：API、消息、数据库、批处理、配置和外部系统；
3. **现有行为**：生产日志、脱敏样本、测试、监控、缺陷和人工补偿；
4. **变更历史**：相关 Commit、事故、回滚和反复修改区域；
5. **知识所有权**：谁真正理解规则，谁维护模块，谁能批准变化；
6. **未知项**：哪些关系尚未证明，错误假设会产生什么影响。

AI 可以承担代码搜索、依赖抽取、接口枚举、调用链摘要和 Git 历史聚类，但其输出只能作为候选知识。候选关系应尽量用静态分析、运行时 Trace、真实样本、现有测试和领域专家交叉验证。

Recon 应有时间盒。低风险局部变更可能只需两小时；高风险跨系统任务可能需要数天和专门验证。如果时间盒结束仍无法确认关键依赖，正确结果是缩小范围、增加保护或停止，而不是让 Agent 自动补齐缺失事实。

### 18.3.4 三层地图：业务能力、系统结构和变更影响

既有系统需要地图，但不需要在第一次任务中绘制一张声称完整的企业架构全景图。建议按三个层次逐步建立。

第一层是业务能力图，回答系统对外提供什么价值：

```text
费用管理
├─ 报销申请
├─ 审批路由
├─ 预算控制
├─ 支付
└─ 财务归档
```

这一层主要来自业务负责人、用户流程、制度和真实运营，不应只从包名或数据库表推导。

第二层是系统与模块图，回答能力由什么承载：

```text
报销申请
├─ Web / Mobile
├─ expense-service
├─ employee-service
├─ approval-engine
├─ notification-service
└─ finance-ledger
```

第三层是当前任务的变更影响图，只展开本次需要理解的关系：

```text
T-101：修改 5000 元审批边界
├─ expense-service / amount-rule
├─ approval-engine / route-policy
├─ Web / approval-hint
├─ expense_submitted 事件
├─ 历史草稿兼容
└─ 财务审批 Dashboard
```

业务能力图保持方向，系统图提供粗粒度导航，影响图才是 Agent 的主要 L3 Context。三张图都应标注来源、版本、责任人和可信度，避免“图画出来了”被误解为“关系已经证明”。

| 关系 | 主要来源 | 状态 |
|---|---|---|
| 报销服务调用审批引擎 | 运行时 Trace | VERIFIED |
| 历史草稿可能复用当前规则 | 老员工访谈 | HYPOTHESIS |
| 通知失败不影响审批提交 | 静态代码分析 | PARTIALLY_VERIFIED |
| 外币使用独立规则 | 生产样本＋测试 | VERIFIED |

### 18.3.5 四类行为必须分开

遗留系统最危险的假设，是把代码里的行为、业务想要的行为和生产真实行为当成一回事。至少要区分四种状态：

- **Intended Behavior**：业务和制度希望系统怎样运行；
- **Observed Behavior**：在生产、测试或样本中实际观察到什么；
- **Implemented Behavior**：静态代码和配置看起来实现了什么；
- **Verified Behavior**：当前证据能够可靠证明什么。

例如制度规定“严格超过 5000 元进入总监审批”，这是 Intended；生产样本显示 5000.00 元有时进入总监审批，这是 Observed；代码中某个模块使用 `>=`、另一个模块使用 `>`，这是 Implemented；经过指定版本、数据和链路测试后能够确认的新建人民币报销行为，才是 Verified。

四者不一致时，Agent 不能自行选一个看起来更合理的答案。OA 负责把差异整理成可决策问题，IO 或领域责任人决定要保持现状、修复行为、兼容一段时间，还是修改制度和契约。

这也是既有系统中 Intent Graph 的特殊之处：一部分从业务意图向下展开，另一部分通过真实变更、运行证据和专家确认逐步恢复。恢复出来的不是“代码的故事”，而是带来源和可信度的系统知识。

### 18.3.6 遗留契约要增加 Baseline、Preserve 和 Unknown

新项目契约主要说明目标、Non-goals、规则和 AC。既有项目还要承担兼容责任，因此建议增加三组内容。

**Current Behavior Baseline** 记录已经观察到的事实：

```text
BASE-01：5000.00 元当前进入普通审批
BASE-02：历史草稿打开后不会自动重算审批链
BASE-03：旧版移动端仍调用 v1 提交接口
```

Baseline 不是对现状的价值认可，只是说明修改前系统怎样运行。

**Preserve List** 说明本次必须保持的行为：

```text
PRESERVE-01：不得改变历史草稿已有审批结果
PRESERVE-02：v1 消费方继续获得兼容响应
PRESERVE-03：现有财务导出字段与口径不变
```

**Unknown List** 明确尚未证明的区域：

```text
UNKNOWN-01：外币离线批处理是否复用同一金额规则
UNKNOWN-02：某地区定制模块是否依赖旧错误码
```

UNKNOWN 不能默认等于安全。若变更可能触及它，应补充侦察、缩小范围、增加灰度和监控，或进入 HITL。把未知显式写入契约，比让 Agent 用高置信度语言填补空白更可靠。

### 18.3.7 Characterization Test：先冻结现实，再改变现实

对于新功能，TDD 的 Red 表示新能力还没有实现；对于遗留系统，团队经常连“现有行为究竟是什么”都不确定。这时需要在新 AC 测试前建立 Characterization Test，通常译为**特征测试或现状刻画测试**。

它不证明现有行为正确，而是把今天观察到的行为固定下来，防止 Agent 修改一处逻辑时无意改变其他历史行为：

```text
修改前现状
├─ 4999.99 → 普通审批
├─ 5000.00 → 普通审批
├─ 5000.01 → 总监审批
├─ 历史草稿 → 保留原审批链
└─ v1 接口 → 返回旧字段结构
```

随后建立四类证据：

```text
Characterization Test：证明哪些旧行为保持不变
Contract Test：证明提供方与消费方仍兼容
New AC Test：证明新意图已经实现
Regression / SIT：证明影响半径内没有产生组合破坏
```

现状刻画可以来自确定性测试、脱敏 Golden Master、接口响应、数据库快照差异或生产流量回放。Golden Master 只能用于发现变化，不能让 AI 自动更新期望值消除失败。每一项变化仍需判断是预期修正、兼容风险还是测试噪声。

### 18.3.8 Change Envelope：为 Agent 建立变更围栏

百万行系统不应把整个仓库默认为 Agent 的可写空间。Constrain 应围绕本任务建立 Change Envelope：

```text
允许修改
├─ expense-service/rules/**
├─ approval-adapter/**
└─ web/expense/approval-hint.tsx

只读参考
├─ employee-service/**
├─ finance-export/**
└─ shared-money/**

禁止触碰
├─ production-migrations/**
├─ legacy-settlement/**
├─ region-custom/**
└─ archived-contracts/**
```

围栏还应定义是否允许新增依赖、改变公共接口、修改数据库、运行生产工具、自动解决冲突，以及最大文件数、Token、时长和重试次数。路径只是第一层，更重要的是数据、接口、行为和发布权限边界。

一个实用默认是将功能变化与大规模重构分开。如果 Agent 声称为了三行规则必须先重构二十七个类，OA 应把它视为风险信号。可以先通过适配器、防腐层或 Feature Flag 局部实现；结构性重构另建契约，单独说明价值、影响和回退。

### 18.3.9 治理岛、邻接保护区与未知遗留区

既有系统可以被划分为三个动态区域：

```text
┌────────────────────────────────────┐
│ 已治理岛                           │
│ 契约、约束、测试、证据和责任已建立 │
├────────────────────────────────────┤
│ 邻接保护区                         │
│ 依赖已识别，只读或受严格限制       │
├────────────────────────────────────┤
│ 未知遗留区                         │
│ 尚未充分理解，默认不允许自动修改   │
└────────────────────────────────────┘
```

第一座治理岛可能只包含一个接口、一个规则模块、三条 AC、五个现状测试、一条跨系统契约和一份 Evidence Bundle。下一次相关变化到来时，在已有知识上扩展：

```text
T-101 金额规则
    ↓
T-117 外币换算
    ↓
T-136 审批委托
    ↓
T-152 历史草稿兼容
```

这与遗留系统改造中的 **Strangler Fig Pattern（绞杀榕模式，也常简称 Strangler Pattern）** 相似。这个名字来自热带雨林中的绞杀榕：它先在一棵宿主树上生长，逐渐向下扎根、向上获得阳光；当自身能够独立生存后，原来的宿主可能逐步退出。Martin Fowler 用这个自然现象比喻遗留系统现代化：不进行一次高风险的“大爆炸替换”，而是在旧系统周围建立新的能力，将一小部分行为逐步导向新实现，让新旧系统在过渡期共存，最后再安全退出已被替代的部分。[Martin Fowler 对 Strangler Fig 的解释](https://martinfowler.com/bliki/StranglerFigApplication.html)

它通常包含四个关键思想：

1. **先找接缝（Seam）**：找到能够隔离流量、接口、数据或业务能力的边界；
2. **小块替换**：先迁移一个可独立验证的能力，而不是复制整个旧系统；
3. **新旧共存**：通过路由、适配器、防腐层或代理，让旧实现和新实现同时运行；这里的防腐层是一个翻译边界，用来把旧系统的数据和语义转换成新系统能够接受的模型，避免旧设计继续渗透到新能力内部；
4. **逐步切换与退役**：新能力经过真实流量和业务验证后，再扩大范围并关闭相应旧路径。

例如，团队需要改造遗留结算系统中的“退款审核”。大爆炸方案是重写整个结算平台；Strangler Fig 方案则可能先在旧系统入口前增加路由层，只把一个地区、一个退款类型或少量灰度流量导向新的审核服务。新服务稳定后，再逐步迁移其他退款类型，最终让旧审核模块退出，而总账、对账和其他尚未迁移的能力继续留在旧系统中。

治理岛借用了这种“从小边界开始、允许共存、用证据逐步扩大”的思想，但替换对象不完全相同：

| Strangler Fig Pattern | 3-4-3 治理岛 |
|---|---|
| 逐步替换旧代码或旧服务 | 逐步替换依赖个人记忆、口头约定和偶然测试的治理方式 |
| 用路由和适配层隔离新旧实现 | 用 Change Envelope、权限和 Work Graph 隔离可改与不可改区域 |
| 用运行结果证明新实现可以接管 | 用契约、现状测试、Evidence Bundle 和遥测证明治理范围可信 |
| 最终目标通常是退役旧实现 | 目标是扩大可信治理范围，旧代码可以继续存在 |

因此，治理岛并不要求每次都把旧模块重写成新服务。一个旧模块即使暂时不重构，只要关键行为已被识别、约束、测试、证据和责任覆盖，也可以进入已治理岛。治理岛的边界由证据决定，不由团队主观宣布。

### 18.3.10 两级或三级 OA：让知识靠近系统

百万行项目不可能由一个全局 OA 理解所有代码和业务。大型既有系统可以采用三级责任结构：

```text
全局 OA
├─ 全局 MUST、系统能力图、跨域协议与发布证据标准
└─ 发布级 Evidence Bundle 与重大风险升级
      │
领域 OA
├─ 领域意图图谱、业务规则和跨模块影响
└─ 领域级兼容与风险审查
      │
模块 OA
├─ 模块上下文、接口、现状测试和 Change Envelope
└─ Agent 任务裁剪与模块证据
```

全局 OA 不是百万行代码的总审核员。它治理跨域关系、全局底线和发布裁决；领域 OA 对业务能力与规则负责；模块 OA 让局部知识、代码和验证靠近真正维护者。一个人在小型组织中可以承担多层职责，但关键变更必须知道当前由哪一层作决定。

当知识所有者已经离职时，不能用 Agent 自动总结替代所有权。组织需要指定临时责任人，以运行证据、历史缺陷和受控实验逐步恢复知识，并将不确定性保留在工件中。

### 18.3.11 遗留 Work Graph 要包含探索和基线节点

新项目的 Work Graph 可以较快进入测试和实现；既有系统的工作图应显式安排侦察、基线和兼容审查：

```text
业务规则校准
      ↓
代码与运行时侦察
      ↓
影响半径确认
      ↓
Current Behavior Baseline
      ↓
Characterization / Contract Test
      ↓
Preserve 与 Unknown 签署
      ↓
新 AC Red
      ↓
局部实现
      ↓
回归＋SIT＋NFR
      ↓
新旧行为差异审查
      ↓
Evidence Bundle
      ↓
灰度与生产验证
```

探索节点必须有产物和停止条件，例如“输出已验证调用方列表、两项未知和一张影响图”；不能写成“让 Agent 研究代码直到理解”。基线节点则要说明哪些现状已经被运行证据固定，哪些只来自静态推断。

若实现过程中出现新依赖，Work Graph 应回流到影响确认，而不是让 Agent 静默扩大范围。既有系统的 O 不只是安排执行顺序，更承担控制认知扩张和变化半径的责任。

### 18.3.12 遗留 Evidence Bundle 要证明“改变了什么，也保住了什么”

新项目证据包主要证明新能力满足 AC；遗留系统还需要证明现有责任没有被意外破坏。建议增加：

- 变更前行为基线；
- 静态依赖和运行时调用链；
- 受影响模块、数据和消费方；
- 修改文件、只读区域和禁止区域；
- Characterization Test 前后结果；
- 新增 AC、接口契约、回归和 SIT 结果；
- Schema、数据迁移和配置差异；
- 新旧版本行为差异；
- 未验证区域与残余 UNKNOWN；
- 灰度、监控、回退和领域专家确认。

证据映射可以写成：

| 裁决结论 | 主要证据 |
|---|---|
| 新规则已经实现 | New AC Test |
| 历史行为没有被意外改变 | Characterization Test |
| 现有消费方仍兼容 | Contract Test＋SIT |
| 影响范围没有静默扩大 | 依赖图＋文件差异＋工具审计 |
| 未触碰未知高风险区域 | Change Envelope 检查 |
| 可以有限发布 | 灰度条件＋回退演练＋人类裁决 |

“全量回归通过”如果无法说明覆盖哪些历史责任，证明力仍然有限。Evidence Bundle 应同时显示已证明、未证明和明确接受的风险。

### 18.3.13 不测全量代码覆盖率，测治理变化覆盖率

百万行系统不可能短期全面治理，也没有必要用全项目代码覆盖率衡量 3-4-3 成熟度。更有意义的是观察从现在开始的变化是否被治理：

```text
变更治理覆盖率 =
纳入契约、约束和证据的 AI 参与生产变更数
÷ AI 参与生产变更总数
```

还可以观察：

- 高风险变更的契约覆盖率；
- 关键业务链路的治理岛覆盖率；
- 高频变更区域的 Characterization Test 覆盖；
- 新增代码和接口的治理覆盖率；
- 跨模块契约覆盖率；
- UNKNOWN 的新增、关闭与逾期趋势；
- Agent 越界修改和静默扩域次数；
- 逃逸缺陷能否归属原契约；
- 经过验证并复用的遗留知识数量。

首要目标不是“一年治理完一百万行”，而是：

> **从某个时间点开始，所有 AI 参与的重要变化不再制造新的治理盲区，并持续减少最危险的旧盲区。**

这可以理解为先遏制治理债务增长，再通过真实任务偿还高价值、高风险区域的存量债务。

### 18.3.14 如何选择第一座治理岛

第一个遗留系统试点不应选择核心结算重构、跨十几个系统的架构升级、全局权限替换、不可回退的数据迁移，或业务部门尚未形成共识的历史规则。

更适合的任务通常具备：

- 有真实业务价值和近期交付需求；
- 变更入口能够定位；
- 影响约一到三个模块；
- 有领域专家或真实证据可用于确认；
- 能够构造当前行为样本；
- 主要 AC 可以自动验证；
- 可以灰度、关闭或快速回退；
- 所在区域未来还可能继续变化，治理资产能被复用。

典型任务包括：已有接口增加校验、高频缺陷修复、审批边界调整、旧接口兼容、关键报表字段修正或局部性能瓶颈治理。它们足够真实，又不会把第一次实践拖入全系统改造。

### 18.3.15 客户现场可直接使用的七步试点

第一步，选择一项正在排期的真实变化，而不是为演示虚构需求。

第二步，用两小时到半天完成第一轮 Recon。让 AI、维护人员、代码、Trace、样本和历史缺陷共同形成局部影响图，并明确 UNKNOWN。

第三步，建立现状基线。补少量高价值 Characterization Test、接口样本和生产指标，不追求覆盖整个模块。

第四步，形成增量 Intent Contract。除目标和 AC 外，签署 Baseline、Preserve List、Unknown List、Non-goals 和回退要求。

第五步，建立 Change Envelope。限制 Agent 可写模块、文件、接口、数据、工具、依赖和重试预算。

第六步，运行完整 SCOPE-V。完成新 AC Red、局部实现、回归、SIT/NFR、差异审查、Evidence Bundle 和独立 V。

第七步，把本次确认的业务关系、接口、约束、测试、未知与教训回写，形成第一座治理岛，并观察下一次相关任务是否真正复用。

第一次成功的标准不是开发速度最快，而是：

> **团队能够证明 Agent 在没有理解整个百万行系统的情况下，仍然安全完成了一次真实变化。**

### 18.3.16 一个大型既有系统案例

假设客户拥有运行十年的费用平台，约八十万行代码，包含 Web、移动端、六个服务、两套审批引擎和多个地区定制模块。业务要求将人民币报销的总监审批阈值从 5000 元调整为 8000 元。

如果只搜索 `5000` 并替换，可能触及展示文案、旧数据校验、财务报表和地区特殊规则；如果要求先重构全部审批系统，任务又会失控。

团队先进行 Recon：静态搜索发现三个阈值定义，运行时 Trace 证明新建报销走 `approval-engine-v2`，生产样本显示历史草稿保留旧路由；但外币夜间批处理是否复用公共金额库仍未知。领域专家确认本次只改变境内人民币新建报销，历史草稿、外币和地区定制全部保持。

于是契约写入：

```text
目标：人民币新建报销严格超过 8000 元进入总监审批
Baseline：当前阈值为 5000 元
Preserve：历史草稿保持原审批链；v1 接口结构不变
Unknown：外币批处理与公共金额库关系尚未证明
Non-goals：外币、历史数据迁移、地区定制、审批引擎重构
```

Change Envelope 只允许修改 v2 金额策略、对应接口适配和 UI 提示；公共金额库只读，外币批处理和迁移目录禁止修改。Work Graph 先建立 4999.99、5000、5000.01 等现状测试，再为 7999.99、8000、8000.01 建立新 AC Red。Contract Test 固定旧移动端响应，SIT 验证审批引擎与通知链路，数据检查证明历史草稿未重算。

实现完成后，Evidence Bundle 不只写“8000 元测试通过”，还展示现状基线、影响图、文件范围、接口兼容、UNKNOWN 未触碰证明、灰度计划和回退开关。IO 最终批准只对两个部门灰度；生产遥测观察审批分布、错误率和历史草稿异常。任务完成后，已验证的 v2 调用关系、历史草稿规则和外币 UNKNOWN 被写入领域图谱。

这次实践没有治理八十万行代码，却在一个高频业务区域建立了第一座可信治理岛，为下一次外币或委托审批变化提供了可复用起点。

### 18.3.17 既有系统落地的常见失败

- 把 AI 自动生成的架构图直接当作系统事实；
- 为了“上下文完整”向 Agent 注入整个仓库和生产数据；
- 没有 Current Behavior Baseline 就开始修改；
- Characterization Test 将历史行为一律视为正确；
- 只写新 AC，不写 Preserve 和 Unknown；
- 允许 Agent 以顺手重构为由扩大二十多个模块；
- 只看静态依赖，不验证运行时、配置和数据关系；
- UNKNOWN 在汇报中被隐藏或默认视为 PASS；
- 全量回归全绿，却无法说明关键历史责任是否被覆盖；
- 以全项目代码覆盖率衡量试点，导致治理工程无限膨胀；
- 全局 OA 试图审核所有模块，成为新的瓶颈；
- 第一座治理岛完成后没有回写图谱和资产，下一次仍从零开始；
- 为证明 AI 成功，选择精心搭建的新模块而回避真实遗留变化。

### 18.3.18 既有系统专题的验收问题

团队可以用一项真实变更检查：

1. 是否明确区分 Intended、Observed、Implemented 和 Verified Behavior？
2. 是否有时间盒 Recon、影响图、证据来源和 UNKNOWN？
3. 契约是否包含 Baseline、Preserve List 与 Unknown List？
4. 是否在新 AC 前建立了必要的 Characterization Test？
5. Change Envelope 是否能机械限制 Agent 的写入、工具和依赖范围？
6. Work Graph 是否包含探索、基线、差异审查和回流节点？
7. Evidence Bundle 是否同时证明新行为成立和关键旧行为未被破坏？
8. 生产遥测是否能关联本次契约、版本和灰度条件？
9. 新确认的知识是否回写图谱、约束、测试或模块指南？
10. 下一次相关变化是否能够复用这座治理岛，而不是重新扫描全部系统？

如果这些问题能够由真实工件和机器结果回答，3-4-3 就已经进入既有系统；不需要等到百万行代码全部被重新解释以后才宣布开始。


## 18.4 两条路径的共同底座与选择原则

新项目与既有系统的起点不同，但进入执行后都必须回到同一套治理底座：

```text
可判定意图
→ 明确约束与权限
→ 有边界的 Work Graph
→ 真实测试与机器证据
→ Evidence Bundle 支持独立裁决
→ Telemetry、知识与记忆反哺
```

两条路径都不允许跳过 IO 签署、MUST 门禁、Evidence Bundle 和遥测；差异主要发生在 Specify 之前和 Prove 的证据结构中。新项目需要证明“设计出来的新行为正确”，既有系统还要证明“被保留的现实没有遭到破坏”。

团队可以用下面四个问题选择入口：

1. 当前能力是否已经在生产环境中运行并承担真实责任？
2. 现有行为能否由可靠契约、测试和文档完整解释？
3. 本次变化是否可能触碰未知依赖、历史数据或兼容责任？
4. 如果取消本次变化，是否仍需要先恢复大量系统认知？

如果多数答案指向“否”，可以采用新项目路径；如果多数答案指向“是”或 UNKNOWN，应采用既有系统路径。对于大型系统中新建的隔离服务，可以局部采用新项目路径，但它与旧系统的接口、数据迁移和发布仍要接受既有系统路径的保护。

| 共同检查点 | 新项目的证据 | 既有系统的附加证据 |
|---|---|---|
| Specify | 目标、非目标、AC、IO 签署 | Intended/Observed/Implemented/Verified、UNKNOWN |
| Constrain | 权限、质量、安全、成本和回退 | Preserve List、历史责任、Change Envelope |
| Orchestrate | 实现、测试、证据和发布 DAG | Recon、基线、影响分析和回流节点 |
| Prove/Evolve | TDD、边界测试、自愈记录 | Characterization Test、差异审查、邻接保护 |
| Verify | 契约与约束证据完整 | 新旧行为双重证明、灰度与生产观察 |

两条路径最终都通过真实任务积累治理资产。区别不是哪条更先进，而是哪条更诚实地面对当前系统的未知。

## 18.5 本章小结

第一个可信闭环不需要宏大平台。新项目可以从意图与约束向实现展开；既有大型系统则从下一次真实变化开始，通过 Recon、现状基线、变更围栏和治理岛逐步恢复可见性、限制影响并积累证据。一个最小 Intent Graph、一份签署契约、一套可执行约束、一份 Evidence Bundle，以及进入慢外环的真实遥测，足以让团队从“会用 AI”迈向“会运行人机协同研发系统”。

**本章最小实践**：完整运行 T-001，或在既有系统中完成一个有变更围栏的真实任务。  
**完成证据**：通过 closing gate 的治理目录、影响范围与可回退交付。  
**延伸实践**：推荐学习《Agentic Agile FDE 进阶：从客户现场到企业级生产交付》，在新项目与既有系统中练习 Recon、变更边界、保留行为和分层验证。
