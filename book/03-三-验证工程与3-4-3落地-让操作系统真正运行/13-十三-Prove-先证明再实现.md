# 第十三章｜Prove：先证明，再实现

## 13.1 AC 不是事后检查清单

在 Agentic Agile 中，AC 是驱动实现的可执行规约。Prove 不是等代码完成后再“看看是否符合”，而是先把签署后的 AC 转成能够否定错误实现的挑战，再让实现围绕这些挑战收敛。

```text
签署 AC → 生成测试与断言 → 运行并确认可信 Red
        → Green：最小实现使测试通过
        → Refactor：不改变行为地改善结构
```

以“严格大于 5000 元进入总监审批”为例，Prove 至少应在实现前固定 `5000.00` 不触发、`5000.01` 触发两个相邻边界。若只从已有代码生成一个“6000 元审批成功”的测试，Agent 即使误写成“大于等于”也能通过，测试数量增加了，业务歧义却没有被消除。

测试先行也不代表一次性写完全部测试。可以先选择当前风险最高、能够区分正确与错误实现的最小 AC 集合。关键是测试来源于契约和风险，而不是从实现结构反向猜测；签署后的关键断言要受版本保护，AS 不能为了 Green 自行修改。

## 13.2 编码门：先证明 Red 可信

编码门的目标不是确认“有一个红色结果”，而是确认测试已经成为可信挑战。它至少检查：

- 测试文件真实存在并已执行；
- 测试对应当前契约版本和明确 AC；
- 失败发生在业务断言，而不是语法、依赖或环境初始化；
- 当前代码如果缺少目标行为，测试确实会失败；
- Red 记录包含命令、退出码、时间、提交和原始输出；
- 关键测试与断言摘要已锁定，后续变更会触发漂移检查。

```bash
python scripts/gate_check.py --gate coding --task T-001 --project-dir .
```

可以把 Red 分为三类：`expected_red` 才允许进入实现；`environment_red` 应先修复环境；`spec_red` 表示 AC 互相冲突或无法判定，必须返回 Specify。把后两类失败误当作 TDD 起点，只会让实现 Agent 围绕错误信号反复试错。

编码门通过后，应输出一张小型“Red 凭证”：AC ID、测试路径、失败断言、契约摘要和允许进入的实现节点。没有这张凭证，Work Graph 不应释放编码节点。

## 13.3 最小实现：只改变足以让证据收敛的部分

最小实现不是追求最少代码行，而是完成当前签署意图所需的**最小语义变化和最小影响半径**。AS 应先说明当前 Red 的原因、计划修改的最小位置和预期影响，再开始 Green。

实现过程中要守住五条边界：

- 不顺手重构无关模块或升级无关依赖；
- 不添加尚未签署的“顺便功能”；
- 不扩大数据、网络、目录和工具权限；
- 不修改契约、AC 或关键测试来适配错误代码；
- 不用 Mock、skip、降低阈值等方式绕过真实依赖和失败。

例如金额边界错误来自领域策略中的比较条件，最小实现应修改该规则并运行相关回归，而不是同时迁移历史草稿、重写审批引擎或调整接口返回结构。若 Green 必须跨出允许文件范围，应暂停并回到影响分析或契约裁决，不能把范围扩大伪装成实现细节。

Green 后的 Refactor 也要与新增行为分开观察：测试保持全绿、对外行为不变、差异可解释。否则团队无法判断新的失败来自业务实现还是结构调整。

## 13.4 AI Coding 时代的多层验证工程

接口测试、UI 测试、SIT、UAT、性能测试都是软件工程中的成熟实践。AI Coding 到来以后，它们不会消失，也不只是“交给 AI 自动生成”这么简单。真正发生的变化是：测试从开发完成后的质量检查，转变为约束 Agent 行为、驱动 P⇄E 收敛、并为上线裁决提供依据的多层证据系统。

传统测试讨论常围绕“谁来测试”“开发后第几阶段测试”“自动化率是多少”。在 Agent 可以分钟级生成代码、测试和报告之后，更关键的问题变成：

- 每条业务意图需要什么证据才能被相信？
- 测试是否来自签署后的 AC，还是从现有实现反推？
- 哪些层由 AI 自动执行，哪些需要独立 Agent 复核？
- 哪些结果属于事实验证，哪些仍需要业务价值判断？
- 当 AI 同时生成实现和测试时，如何防止同一个误解自证正确？
- 测试结果怎样进入 Evidence Bundle，而不是停留在流水线的绿色图标里？

这一整套问题，就是 AI Coding 时代的多层验证工程。

### 13.4.1 最大风险不是“没有测试”，而是同源误判

假设 Agent 把“超过 5000 元需要总监审批”错误理解为“达到 5000 元就需要总监审批”。如果它先按这个理解编写实现，再根据自己的实现补测试，就可能生成“5000.00 元必须升级审批”的断言。实现和测试完全一致，覆盖率很高，流水线全部绿色，但交付结果仍然违背真实意图。

```text
错误理解意图
    ↓
生成错误实现
    ↓
根据错误实现生成一致的测试
    ↓
测试全部通过
    ↓
错误地宣布可以上线
```

这就是同源误判：需求解释、实现、测试和结论来自同一个认知源，错误假设贯穿整条链路，没有任何异质证据能够将其打断。AI 生成更多测试只能提高执行量，不能自动提高结论可信度。

3-4-3 用三种方式降低这种风险：

1. 测试首先从 IO 签署的 Intent Contract 和 AC 生成，而不是从实现代码反推；
2. 关键规则使用不同测试层、不同技术路径或独立 Agent 交叉证明；
3. P 和 E 可以由 Agent 高频循环，但最终 V 审查证据来源、覆盖、独立性和新鲜度，不能由执行 Agent 仅凭“全绿”自我放行。

独立性不是要求每个测试都换一个人写。它要求关键结论不能只依赖同一个未经校准的假设。对于低风险任务，从签署 AC 生成测试并保留可信 Red 可能已经足够；对于资金、权限、安全和不可逆操作，则应增加独立环境、第二验证主体、真实样本或人工审查。

### 13.4.2 从测试金字塔转向验证证据组合

测试金字塔仍然有意义：底层测试通常执行快、定位准、成本低，端到端测试数量应更少。但仅用“单元测试多、UI 测试少”已经无法回答一个具体任务能否上线。它没有说明某条 AC 由谁证明，也没有说明接口兼容、跨系统协作、性能约束和业务接受是否得到覆盖。

因此，本书引入 **Verification Portfolio（验证证据组合）**：针对一份 Intent Contract，依据 AC、约束、风险和影响范围，预先选择一组足以支撑裁决的验证方式。

验证证据组合不是要求每个任务都执行所有测试，而是为每条关键意图回答七个问题：

1. 这条 AC 最适合由哪一层测试证明？
2. 一个测试层是否足够，是否需要交叉证明？
3. 哪些步骤可以由 AI 自动生成和执行？
4. 哪些结果需要独立 Agent、独立环境或人工复核？
5. 哪些问题属于业务价值判断，不能交给 AI 决定？
6. 证据的环境、版本、时间和有效期是什么？
7. 上线以后由什么遥测继续验证？

一份最小组合可以写进 Intent Contract 或 Work Graph：

| AC/约束 | 风险 | 验证层 | 执行主体 | 独立性要求 | 通过判据 | 证据位置 |
|---|---|---|---|---|---|---|
| AC-01 金额边界 | 高 | 单元＋接口 | 测试 Agent | 从签署 AC 生成 | 5000.00 通过，5000.01 拒绝 | `evidence/ac-01/` |
| AC-02 审批链路 | 高 | SIT | 集成 Agent | 独立测试环境 | 总监节点仅在超额时出现 | `evidence/ac-02/` |
| C-PERF-01 响应时间 | 中 | 性能 | 性能 Agent | 固定数据和负载模型 | 200 并发下 p95≤300ms | `evidence/perf/` |
| AC-03 提示可理解 | 中 | UI＋UAT | AI 执行、财务确认 | 业务代表裁决 | 用户能理解且完成处理 | `evidence/uat/` |

这张表把“应该测什么”从测试人员的隐性经验，转化为任务开始前可审查、执行后可追溯的证明设计。

### 13.4.3 单元与组件测试：证明局部规则和不变量

单元测试验证函数、类或领域规则在隔离条件下是否满足预期。组件测试则把若干内部对象组合起来，在不连接全部外部系统的情况下验证一个较完整的业务能力。它们运行快、失败定位清晰，是 P⇄E 快内环的主要反馈来源。

AI 很适合根据 AC 生成正常、边界、异常和组合样例，也适合在失败后定位最小修复范围。但不能只把当前实现翻译成测试。测试设计应优先读取契约中的业务样例、不变量和 Non-goals。

费用规则至少应验证：

- 4999.99、5000.00、5000.01 三个边界；
- 零金额、负数、空值和非法精度；
- 人民币与外币换算发生在比较之前还是之后；
- 金额超限时不得静默截断；
- 历史草稿是否属于本次 Non-goals。

除了示例测试，还可以使用 Property-Based Testing 生成大量输入验证不变量，例如“任何超过阈值的合法金额都不能进入普通审批路径”。它能发现人类没有手工列出的边界，但属性本身仍须来自业务意图；如果属性写错，生成再多数据也会证明错误规则。

### 13.4.4 接口测试：证明服务契约，而不只是 HTTP 200

接口测试验证系统边界上的请求、响应、鉴权、错误、幂等和兼容性。AI 可以读取 OpenAPI、Schema、消费者契约和历史流量样本，生成用例、构造数据、执行回归并解释差异。这比人工逐条编写正常路径高效得多。

但接口通过不能只看状态码。一个可信的接口证据至少应覆盖：

- 请求字段、类型、必填项和取值边界；
- 响应结构、业务状态和错误语义；
- 身份认证、租户隔离和数据权限；
- 重复请求的幂等行为；
- 超时、重试、限流和降级；
- 版本兼容以及已有消费者是否被破坏；
- 数据写入后的状态，而不只是返回报文。

例如报销提交接口对 5000.01 元返回 `200`，但后台仍创建了普通审批单，仅在响应中附加一条警告，这在网络层“成功”，在业务层却失败。接口测试必须把 AC 连接到数据库状态或下游事件，才能证明真实行为。

AI 还可以做 Contract Testing：由消费方声明自己依赖的字段和语义，提供方在变更时自动验证。对于多 Agent 并行修改前后端的场景，这种可执行接口契约尤其重要，因为它能在集成前发现两个 Agent 各自合理、合在一起却不兼容的问题。

### 13.4.5 UI 测试：证明关键用户旅程，而不只是页面能打开

UI 测试可以包含三个不同目标：功能性端到端测试证明用户能够完成任务；视觉回归证明布局和样式没有异常变化；可访问性检查证明键盘、读屏和对比度等基本要求得到满足。三者不能用一张截图互相替代。

AI 在 UI 测试中的优势包括：根据用户旅程生成脚本、为页面元素选择更稳定的语义定位、自动准备数据、分析失败截图、比较视觉差异，并将自然语言场景转换为浏览器操作。多模态模型还可以发现遮挡、溢出、按钮不可见等传统 DOM 断言不易描述的问题。

与此同时，UI 自动化非常容易产生脆弱测试：坐标、动态文案、随机等待和复杂 CSS 选择器都会使脚本在没有真实缺陷时失败。AI 如果面对失败只会不断增加等待时间或改写选择器，就会制造“自动修复成功”的假象。因此 UI Harness 应要求：

- 优先使用角色、标签、测试 ID 等稳定语义定位；
- 等待业务状态而不是固定休眠；
- 测试关键旅程，不把所有组合都堆到 UI 层；
- 将视觉差异阈值、浏览器和屏幕尺寸固定；
- 失败时保存截图、视频、控制台和网络证据；
- 不允许 Agent 在没有审查的情况下自动更新 Golden Screenshot。

费用案例的 UI 测试不只是确认输入框存在，而应证明员工可以提交 5000.00 元、5000.01 元被明确引导到正确审批路径、错误提示可理解，并且系统没有产生重复申请。

### 13.4.6 SIT：证明多个系统在真实契约下共同工作

SIT 通常指 System Integration Testing，即系统集成测试。它验证的不是某个接口孤立可用，而是多个服务、数据库、消息队列、身份系统和第三方能力连接以后，端到端协作是否成立。

这正是 AI Coding 容易暴露问题的地方。不同 Agent 可以分别把报销服务、审批服务和通知服务实现得“局部正确”，却可能在字段含义、事件顺序、超时策略或幂等键上不一致。单元测试和 Mock 接口全部通过，也不能证明真实系统能够协作。

AI 可以帮助 SIT：

- 从 Work Graph、跨模块契约和调用链生成集成场景；
- 建立测试数据和环境依赖清单；
- 为暂不可用的外部系统生成 Stub 或服务虚拟化；
- 对日志、Trace、消息和数据库状态进行链路归因；
- 在失败后识别是提供方、消费方、数据还是环境问题；
- 根据影响图选择需要回归的跨系统路径。

但 Stub 只能证明双方符合约定，不能永久替代真实集成。关键链路在发布前仍应进入受控的真实或高保真环境。SIT 证据必须记录参与系统版本、接口 Schema、环境配置、测试数据、Trace ID 和外部依赖状态，否则“昨天 SIT 通过”无法证明今天这一批构建仍可集成。

费用案例的 SIT 至少要证明：报销服务产生正确审批请求；审批系统按金额路由；身份系统返回的角色被正确解释；审批结果能够回写；通知失败不会导致重复提交；同一业务单据重放时保持幂等。

### 13.4.7 性能测试：证明在明确负载下满足 NFR

“接口很快”“页面没有卡顿”“测试套件三秒跑完”都不是性能证据。性能测试必须同时说明环境、数据规模、负载模型、持续时间、指标和阈值。例如：在指定硬件、十万条历史报销数据和 200 个并发用户下，审批接口持续 15 分钟的 p95 响应时间不超过 300ms，错误率低于 0.1%。

AI 可以根据系统拓扑生成负载脚本，分析慢查询、调用链和资源瓶颈，比较基线与当前版本，并建议下一项诊断实验。它也可以根据代码影响图判断某次修改是否触发局部基准、容量测试、压力测试、稳定性测试或完整性能回归。

但这里有三条硬边界：

1. 普通单元测试或 `pytest` 总耗时不能替代专用性能基准；
2. Agent 不得为了获得全绿而擅自降低并发量、缩短持续时间或放宽阈值；
3. 性能结论必须带基线和环境，不能把共享测试环境的一次波动直接归因于代码。

性能测试的目的也不只是在发布前拦截。趋势遥测可以发现每次变化只有 3% 的退化，但连续十次后系统已经明显变慢。单契约 Dashboard 应保存本任务的基准差异，全局 Dashboard 则观察跨任务的性能债务。

### 13.4.8 安全、可靠性与数据验证：不能藏在“其他测试”里

一些团队把接口、UI 和 SIT 全部通过后就视为质量完成，把安全、可靠性和数据正确性留给最后一次扫描。这在 Agent 能够调用工具、修改配置和操作数据以后尤其危险，因为风险不只来自业务代码，还来自 Agent 的行动方式。

安全验证应覆盖依赖漏洞、密钥泄露、鉴权、越权、注入、租户隔离和工具调用审计；可靠性验证应覆盖超时、重试、熔断、降级、恢复和故障注入；数据验证应覆盖 Schema、迁移、精度、完整性、隐私和回滚后的状态一致性。

AI 能够生成攻击样例、扫描代码、设计故障实验并分析异常，但高风险安全结论不应只依赖同一个 LLM 的判断。确定性扫描、独立工具、受控攻击验证和人工安全审查应共同构成证据。对于生产凭证、删除数据和权限提升等不可逆行为，Harness 应在测试之外直接阻止，而不是等安全测试发现。

#### SAST 与 DAST 分别证明什么

SAST 是 Static Application Security Testing，即静态应用安全测试。它在程序不运行时分析源代码、字节码或构建产物，寻找不安全 API、污点传播、注入路径、硬编码凭证和危险编码模式。它适合在 IDE、提交和 CI 早期高频运行，反馈快、定位通常接近代码，但可能产生误报，也无法证明真实部署后的认证、配置和运行行为。

DAST 是 Dynamic Application Security Testing，即动态应用安全测试。它从外部向正在运行的应用发送请求和攻击载荷，根据响应发现注入、认证、授权、会话、输入输出校验和服务器配置等问题。它不需要读取源码，更接近攻击者视角，但必须具备可运行环境、有效身份、足够的攻击面覆盖和受控测试数据；扫描结果也未必能直接定位到代码。[OWASP 对 SAST、DAST 在 DevSecOps 流水线中位置的说明](https://owasp.org/www-project-security-culture/v10/7-Security_Testing/)；[OWASP DAST 说明](https://owasp.org/www-project-devsecops-guideline/latest/02b-Dynamic-Application-Security-Testing)

二者不是二选一，也不能互相证明完全安全：

```text
SAST：不运行程序，从内部寻找可疑实现
DAST：运行程序，从外部挑战真实行为
SCA：检查第三方依赖与已知漏洞
Secret Scan：检查凭证和敏感信息泄漏
IaC / Image Scan：检查基础设施配置与容器制品
IAST：在运行和测试过程中结合内部执行信息定位风险
```

#### SAST/DAST 怎样进入 P⇄E 快内环

最典型的循环是：

```text
P：SAST 发现未过滤输入进入 SQL 执行
→ E：在授权文件范围内采用参数化查询
→ P：重跑同一规则、单元安全测试与回归

P：DAST 在测试环境证明普通用户可以读取他人报销单
→ E：修复对象级授权并补充审计日志
→ P：使用原身份、原对象和原攻击请求重新验证
```

但“扫描发现”不应直接等于“代码一定有漏洞”，扫描全绿也不等于安全完成。进入 E 前需要对发现去重、确认适用性和风险；修复后必须重跑原检查，不能通过加入全局忽略、降低严重级别或缩小扫描范围获得绿灯。误报可以被抑制，但抑制需要规则 ID、理由、责任人、范围和到期时间，并进入 Evidence Bundle。

并不是所有 DAST 都适合秒级内环。局部 API 安全用例和轻量扫描可以跟随每次候选构建；全站爬取、认证复杂的 DAST、性能敏感攻击、渗透测试和生产前安全评估通常属于较慢的 P⇄E 循环，需要专用环境、数据复位、速率限制与测试授权。高破坏性载荷不得由 Agent 因“需要更多证据”自行对生产运行。

#### 红队、蓝队、紫队与高频对抗是什么关系

“高频对抗”是更广义的控制机制，红蓝对抗是其中一种安全实现，但不能把两个概念完全画等号。

- **红队（Red Team）**站在攻击者视角，尝试绕过预期控制、串联弱点并实现攻击目标；它关注的不只是单个漏洞，还包括身份、流程、人员、Agent 工具和检测盲区；
- **蓝队（Blue Team）**负责预防、检测、阻断、调查、恢复和修正规则；在 SCOPE-V 中，蓝队响应主要进入 E，但其修复结果必须回到 P 接受重新攻击；
- **紫队（Purple Team）**不是简单的第三支队伍，而是一种协作方式：把红队攻击路径转化为蓝队能够复现的检测、测试、约束、遥测和恢复资产。

应用安全红队与 Agent 红队也应区分。前者攻击业务应用、API、身份和基础设施；后者还会测试 Prompt Injection、越权工具调用、数据外泄、Memory Poisoning、目标劫持、停止条件和人类接管。一次成熟演练可以同时覆盖两层：恶意 Issue 中的间接 Prompt Injection 是否能诱导编码 Agent 读取凭证并调用外部工具，以及 Harness 是否会发现、阻断并保存证据。

红蓝循环可以表达为：

```text
P / 红队：提出攻击假设并保存攻击证据
        ↓
E / 蓝队：修复代码、配置、检测、权限或恢复机制
        ↓
P / 红队：沿原攻击路径重新验证
        ↓
紫队：把攻击与防御沉淀为测试、约束、告警和演练剧本
        ↓
V：独立审查覆盖、残余风险和是否允许放行
```

NIST SP 800-115 将安全测试视为需要设计、实施、分析发现并形成缓解措施的完整评估活动，而不是只运行扫描器。这与 P 产生攻击事实、E 修复、P 重验、V 独立裁决的职责划分一致。[NIST SP 800-115：信息安全测试与评估技术指南](https://csrc.nist.gov/pubs/sp/800/115/final)

#### 哪些安全结果不能留在自动快内环里

以下情况必须停止自动修复并进入 OA、安全负责人或 V：

- 发现可能已被真实利用、涉及数据泄漏或生产凭证；
- 修复需要改变认证模型、信任边界、加密方案或网络分区；
- 需要接受高危漏洞、关闭安全规则或扩大扫描豁免；
- DAST、渗透测试或红队攻击可能破坏数据、账户或服务可用性；
- 扫描工具之间结论矛盾，或关键攻击面无法覆盖；
- 修复会改变已签署业务规则、兼容性或监管义务；
- 红队与蓝队由同一 Agent、同一 Prompt 和同一上下文产生，缺少必要独立性。

因此，正确关系不是“安全扫描属于 Verify”，也不是“SAST/DAST 全部由 Agent 自动修到绿”。更准确的分工是：**C 定义安全门槛和禁止动作，O 编排扫描与攻击节点，P 产生独立安全事实，E 完成受控修复，V 判断证据覆盖与残余风险，Telemetry 观察漏洞复发、误报、修复时长和攻击检测能力。**

### 13.4.9 UAT：AI 可以执行场景，但不能代替业务接受

UAT 是 User Acceptance Testing，即用户验收测试。它回答的不是“软件是否按照技术规格运行”，而是“交付结果是否真正满足业务意图，业务是否愿意接受并承担上线后果”。因此 UAT 是 AI Coding 时代最不应该被错误全自动化的环节。

AI 可以承担大量 UAT Execution：

- 从意图契约生成业务语言的验收场景；
- 准备账号、订单、审批单等测试数据；
- 自动执行确定性操作并保存过程；
- 汇总接口、UI、SIT 和性能证据；
- 标记规则冲突、开放问题和需要业务判断的差异；
- 生成供业务代表快速审阅的演示与摘要。

但 UAT Acceptance 仍应由业务责任人完成。AI 不能代替财务负责人决定提示是否容易理解、审批政策是否公平、操作摩擦是否可接受，也不能替 IO 承担资金规则上线后的责任。

```text
UAT Execution：AI 可以大量准备和执行
UAT Acceptance：业务负责人作价值裁决
```

业务人员也不应只是点击“同意”。UAT 记录至少包含场景、预期业务结果、实际结果、未解决问题、接受范围、限制条件、签署人和时间。如果业务代表发现 5000.01 元确实进入总监审批，但提示语会让员工误以为报销被拒绝，那么技术测试可能全绿，UAT 仍然有充分理由不接受。

### 13.4.10 生产验证：上线不是证据生命周期的终点

测试环境只能证明在已知条件下的行为。真实用户、真实数据分布、并发模式和第三方波动会暴露新的问题。因此验证证据组合还应声明上线后观察什么，以及什么信号触发回退、降级或 Bug 回溯。

AI 可以持续分析错误率、延迟、业务转化、异常审批比例和用户反馈，将异常关联到具体契约和发布版本。生产验证可以采用灰度、影子流量、金丝雀、Feature Flag 和合成监控等方式，在控制影响范围的同时取得真实证据。

但遥测不能被用来为未经验证的高风险发布开脱。上线后观察是对发布前证据的延续，不是“先上线再说”的替代方案。一旦发现逃逸缺陷，必须回到对应契约：修正首次成功状态、追加 Evidence Bundle、重新采集遥测并把教训回写 Intent Graph。

### 13.4.11 不同测试层在 SCOPE-V 中怎样分工

一个常见误区，是把单元、接口、UI、SIT、性能和 UAT 全部放到 Verify 最后执行。这样不仅反馈慢，也会把 V 重新变成传统测试阶段。SCOPE-V 将它们分布在不同控制层：

#### S 与 C：先定义证明责任

Specify 把业务意图写成可判定 AC；Constrain 把性能、安全、数据和恢复要求写成可执行边界。此时就应为关键 AC 选择验证层、执行主体和通过判据，而不是等代码写完再问“怎么测”。

#### O：把验证节点编入 Work Graph

Orchestrate 决定哪些测试先行，哪些可以并行，哪些等待真实环境，哪些结果是实现节点或发布节点的前置条件。接口契约测试可以在服务实现前产生 Red；性能环境准备可以与功能开发并行；UAT 必须等待关键业务链路具备可演示状态。

#### P⇄E：高频产生事实并驱动收敛

单元、组件、接口和局部 UI 测试通常进入高频快内环。SIT、性能、安全和可靠性测试也可以在条件具备后进入 P，失败则由 E 分类、修复并使用同一判据复验。每轮都要保存原始结果、修复动作和退出原因。

#### V：独立审查，而不是重新生产全部证据

Verify 判断各层证据是否覆盖签署意图和 MUST 约束，来源是否独立，环境和版本是否一致，证据是否新鲜，UAT 是否由正确责任人接受，以及回退条件是否成立。V 可以触发补测，但不能替 P 制造缺失证据，也不能因为时间紧而降低判据。

#### Telemetry：验证真实价值和长期趋势

上线后的质量、性能、成本、HITL 和业务结果进入契约级 Dashboard，再聚合到全局 Dashboard。慢外环将重复缺陷、脆弱测试、性能退化和高成本验证反馈给下一轮 S/C/O。

```text
Intent Contract / Constraint Matrix
              ↓
      Verification Portfolio
              ↓
     Work Graph 中的验证节点
              ↓
        P ⇄ E 快速收敛
              ↓
 Evidence Bundle 汇聚多层证据
              ↓
       V + UAT 独立裁决
              ↓
  生产遥测与双层 Dashboard
              ↓
   反馈 Intent Graph / 约束 / Skill
```

### 13.4.12 一个完整案例：5000 元规则需要哪些证据

假设签署意图是：“单笔人民币报销金额不超过 5000 元时进入普通审批；超过 5000 元时进入总监审批；不得修改历史草稿。”其验证证据组合可以这样设计：

| 验证层 | 要证明的事情 | 代表场景 | 主要执行者 | 输出证据 |
|---|---|---|---|---|
| 单元/组件 | 金额比较和币种规则正确 | 4999.99、5000.00、5000.01 | 测试 Agent | Red/Green、断言结果 |
| 接口 | 提交契约、鉴权和持久化正确 | 5000.01 返回正确审批级别 | 接口 Agent | 请求响应、数据库断言 |
| UI | 员工能完成提交并理解结果 | 边界金额提示与审批展示 | UI Agent | 视频、截图、网络日志 |
| SIT | 报销、身份、审批、通知协作正确 | 总监节点、回写、幂等重放 | 集成 Agent | Trace、事件、系统状态 |
| 性能 | 规则变化未破坏容量目标 | 200 并发、十万历史记录 | 性能 Agent | 基线、p95、错误率 |
| 安全/数据 | 无越权和历史数据副作用 | 普通员工越权、历史草稿检查 | 安全/数据 Agent | 扫描、审计、数据差异 |
| UAT | 规则和交互得到业务接受 | 财务代表完成关键旅程 | AI 辅助＋财务负责人 | UAT 记录与签署 |
| 生产验证 | 真实审批分布与体验正常 | 异常审批率、错误率、延迟 | 遥测系统＋OA | 契约 Dashboard |

这不意味着每个低风险修改都要运行八层验证。如果变更只修正一处无业务影响的展示错别字，Context 和影响图可能将组合裁剪为 UI 快照、可访问性检查和人工浏览；如果变更触及金额计算、权限或数据库迁移，即使代码只有三行，组合也必须升级。

验证成本应服从风险，而不是服从代码行数。

### 13.4.13 AI 参与测试的四级成熟度

团队可以用四级模型判断自己是否真正完成融合：

1. **AI 生成测试**：AI 根据代码补用例，主要改善编写效率；
2. **AI 按契约设计测试**：测试从 AC 和约束生成，开始建立意图追溯；
3. **AI 按风险编排验证**：系统依据影响图、历史缺陷和约束动态选择验证证据组合；
4. **AI 治理证据闭环**：多层结果进入 Evidence Bundle 和 Dashboard，V 独立裁决，生产反馈能够反哺图谱、约束和测试策略。

第一层容易演示，却可能只是“更快地补测试”；第四层才意味着测试成为 AI 研发治理系统的一部分。

### 13.4.14 多层验证的常见失败

- 同一个 Agent 解释需求、写实现、补测试并宣布完成；
- 测试从当前代码反推，与 Intent Contract 没有映射；
- 接口测试只断言 HTTP 200，不检查业务状态和数据副作用；
- UI 自动化大量依赖坐标、固定等待和脆弱选择器；
- SIT 长期使用 Stub，从未验证真实跨系统契约；
- 将普通测试套件耗时冒充性能基准；
- AI 自动更新 Golden Set 或截图，以消除失败；
- 把 UAT 执行自动化误认为业务已经接受；
- 所有测试全绿，却无法证明来自哪个提交和环境；
- Evidence Bundle 只附报告，没有建立 AC—约束—证据映射；
- 为了追求自动化率，把价值判断和不可逆批准也交给 AI；
- 上线后发现 Bug，没有回到原契约修正证据和遥测。

### 13.4.15 多层验证方法工具箱

除了按系统层次划分验证，还可以根据问题性质选择不同测试方法：

- **Example-Based Testing** 用具体样例验证典型与边界路径；
- **Property-Based Testing** 用大量生成输入验证业务不变量；
- **Differential Testing** 比较新旧版本、两个实现或两个模型的差异；
- **Metamorphic Testing** 在缺少标准答案时验证输入变化与输出变化的关系；
- **Mutation Testing** 主动制造代码变异，检查现有测试能否识别错误；
- **Golden Set** 使用经过人工校准的稳定样本验证模型或规则输出；
- **Contract Testing** 验证服务提供方与消费方的接口约定；
- **Chaos Testing** 注入故障，验证降级、恢复和可观测性；
- **Exploratory Testing** 由人或 AI 基于风险线索探索未预先列出的异常；
- **A/B、灰度与影子验证** 在受控生产条件下观察真实行为。

这些方法不是越多越好。团队应先识别本任务最可能出错、出错后损失最大、又最难由单一路径发现的部分，再选择证明力最强且成本合理的组合。

最终需要记住的不是测试类型清单，而是一条治理原则：

> **AI Coding 与测试融合的终点，不是让 AI 生成更多测试，而是让每项业务意图都拥有一组可信、独立、可追溯、与风险匹配的上线证据。**

## 13.5 LLM-as-Judge 的边界

LLM-as-Judge 适合评价难以用单一断言表达的内容，例如解释是否完整、文案是否符合语气、方案是否覆盖给定维度、开放性回答是否与材料相关。它不适合替代金额计算、权限判断、状态转换、性能阈值和安全规则等可以确定性验证的事实。

| 问题 | 首选验证者 |
|---|---|
| `5000.00` 是否触发审批 | 运行时断言或数据库检查 |
| 未授权用户是否被拒绝 | 接口与权限测试 |
| 页面说明是否清晰、完整 | Judge 初评加人工校准 |
| 是否可以接受残余业务风险 | 有责任的人类 |

使用 Judge 时至少要固定评分 Rubric、输入材料、模型与提示版本，并准备一组人工已判定的校准样本。对同一输入可重复运行或使用第二评审路径，观察结论稳定性；只给分数不提供命中依据的结果，不应进入高风险发布裁决。

Judge 的输出应被视为一种有不确定性的证据，而不是事实本身。高风险结论必须由确定性检查、独立环境或人工责任人兜底；模型不能因为自信度很高就获得价值裁决权。

## 13.6 Proof-Carrying Delivery

Proof-Carrying Delivery 可以译为“携证交付”：交付物到达下一责任主体时，同时携带支持其结论的证据。朴素地说，**不要只说完成了，要把别人能够复查的依据一起交出来。**

一份合格证据需要具备四个属性：

- **可追溯**：能够从 Goal、AC 和约束找到对应证据；
- **真实**：保存原始命令、退出码和输出，而不是 Agent 的转述；
- **新鲜**：证据对应当前契约、当前提交和指定环境；
- **可复现**：接收者知道使用什么数据和步骤重新验证。

最小携证交付至少说明契约版本、代码与配置差异、每项 MUST AC 的检查、约束结果、环境与时间、未验证事项、残余风险、回退方式和例外批准。证据需要建立映射：`AC-01` 对应哪条测试，`C-SEC-02` 对应哪项扫描，回退结论对应哪次演练。

以报销规则为例，代码差异只是交付的一部分。Evidence Bundle 还要证明 5000.00 与 5000.01 的边界、异常人工队列、权限限制和功能开关关闭路径。若外币场景未验证，应明确标为 `unproven`，不能让“全部测试通过”掩盖验证范围。

携证也不等于附上一大包日志。接收者应能先看到结论与缺口，再沿 ID 下钻到原始依据。完成不再是执行者认为工作结束，而是结果和证据已经达到下一责任主体可裁决的状态。

## 13.7 验证门：不是只有通过和失败

验证门至少检查：测试全绿且测试数大于 0；AC 逐条有结果；编译或类型检查通过；Evidence Bundle 对应当前提交；关键约束没有失败；关键测试未被删除、skip 或削弱。

```bash
python scripts/gate_check.py --gate prove --task T-001 --project-dir .
```

门禁结果不应只有布尔值，至少区分四种状态：

- `passed`：判据满足且证据完整、新鲜；
- `failed`：已有证据明确证明不满足；
- `unproven`：缺少证据、环境不可用或映射不完整；
- `exception`：未满足但存在有效的人类批准、补偿控制和到期时间。

`unproven` 尤其重要。没有性能环境不能被解释为“性能默认通过”，测试报告来自旧提交也不能进入当前裁决。验证门只决定结果是否具备进入 Verify 的资格，不代替 IO 对价值、残余风险和上线作最终决定。

## 13.8 测试的独立性

让同一个模型根据自己的实现生成测试，可能把同一误解复制到代码和断言中。独立性不是简单换一个 Agent 名称，而是让验证至少在**判据来源、执行上下文或验证技术**上与实现拉开距离。

可以按风险选择三档：低风险任务由同一 Agent 执行，但测试必须来自签署 AC 并保留 Red；中风险任务由独立上下文或独立 Agent 生成关键反例；高风险任务再增加人工领域审查、Golden Set、不同技术路径或独立环境复核。

常用方法包括：

- 测试从签署 AC 和不变量生成，而不是阅读实现后反推；
- 关键测试文件对实现节点只读；
- 使用脱敏生产样本或历史事故建立 Golden Set；
- 用属性测试、数据库断言和外部接口观察交叉验证；
- 保留 Red、Green 及测试差异，检查断言是否被移动；
- 对高风险行为使用第二模型或人工设计反例。

独立性不要求所有工作都由不同的人完成。它要求关键结论不能只依赖产生该结果的同一条认知路径。

## 13.9 什么是无效全绿

绿色只能证明“被运行的检查没有报告失败”，不能自动证明意图已经实现。以下情况都属于无效或可疑全绿：

- 测试从未出现可信 Red，或者 Red 来自环境损坏；
- 测试没有有效断言，关键用例被 skip、only 或条件排除；
- 为适应实现修改了期望值、边界或 Mock；
- Mock 掉了真正需要验证的数据库、权限或外部契约；
- 只检查字符串、函数名或文件存在，没有验证运行行为；
- 测试数据绕开了关键边界和失败路径；
- 测试环境、制品或配置与发布目标不同；
- 编译、测试和证据来自不同提交。

验证门可以做一次“绿色审计”：比较 Red 到 Green 之间测试文件与断言差异，统计 skip/only，核对测试数量是否异常下降，检查 Evidence Bundle 的提交摘要和环境指纹，并随机重跑一条关键 AC。若绿色无法回答“证明了哪条 AC、使用了什么输入、在什么版本上运行”，它只是一个界面颜色。

## 13.10 Prove 常见失败

Prove 的失败大致来自四类：判据失真、执行失真、证据失真和责任失真。

- **判据失真**：先写完实现再补测试；AC 从代码反推；只覆盖快乐路径；
- **执行失真**：Red 来自环境损坏；用 Mock 绕过真实依赖；性能需求只看普通测试总耗时；
- **证据失真**：只保存最终绿色结果；测试与制品不是同一提交；Judge 没有记录版本与 Rubric；
- **责任失真**：实现 Agent 修改关键断言；为赶时间删除失败测试；机器替业务责任人接受风险。

遇到这些问题，正确动作不是继续增加测试数量。应先判断错误发生在哪一层：AC 不清回到 Specify，约束缺失回到 Constrain，节点权限或职责不清回到 Orchestrate，环境损坏先修复验证基础设施，证据不一致则重新取证。Prove 只有在判据和验证环境可信时才有意义。

## 13.11 从测试数量转向证明强度

一百个与风险无关的单元测试，可能不如三个直击关键边界的测试有价值。证明强度至少取决于五个维度：

1. **相关性**：是否直接对应已签署 AC、约束或关键风险；
2. **区分力**：是否能够让一个常见错误实现失败；
3. **独立性**：是否避免与实现共享同一错误假设；
4. **真实性**：环境、数据、依赖和制品是否接近裁决对象；
5. **可追溯性**：结果是否可回到命令、版本、输入和责任人。

覆盖率只能说明哪些代码被执行，不能说明业务语义正确。对于“严格大于 5000 元”的规则，4999.99、5000.00、5000.01 三个边界测试，比大量随机正常值更有区分力；再加一条真实接口路径和一条数据库状态断言，证明强度又高于只在函数层重复同一判断。

团队可以在 Evidence Bundle 中为关键 AC 简单标记上述五维的强、中、弱，用于暴露证据短板，而不是计算一个看似精确的总分。改进目标是补最薄弱的证据维度，不是机械增加用例数。

## 13.12 谁来验证验证者

当同一个 Agent 同时解释需求、编写实现、生成测试并总结结果时，偏差可能贯穿整条链。验证者也必须受到约束和抽查，但不能因此陷入“无限再找一个验证者”的递归。

可以建立三层终止结构：第一层由确定性工具验证事实，如编译器、断言、数据库检查和安全扫描；第二层由独立 Agent 或独立上下文检查 AC—测试—证据映射、寻找反例和识别证据矛盾；第三层只把价值判断、例外授权和不可逆风险交给有责任的人类。三层职责不同，不是简单重复执行同一测试。

对验证者本身，应检查：它使用的契约和提交是否正确，是否拥有修改被验证对象的权限，是否保存原始输出，是否存在跳过项，以及结论能否由另一条路径抽查。高风险规则可以定期注入已知错误或使用 Mutation Testing，确认验证系统真的能够抓住失败。

独立性的目标不是制造更多流程，而是打断“同一个错误假设自我证明”的闭环。当确定性证据充分、独立映射检查通过且责任边界明确时，验证链就可以终止；不需要让 Agent 无休止地互相评审。

## 13.13 本章小结

Prove 让“写代码”从中心动作变成验证循环中的一个步骤。Agent 不只是生成实现，还必须产生能够否定错误实现的测试和证据。

**本章最小实践**：为 T-001 从 AC 生成测试，记录 Red，再实现 Green。  
**完成证据**：Red 与 Green 两次真实运行结果。  
**延伸实践**：推荐学习《Agentic Agile 3-4-3 基础课：跑通第一次受控自治》，先定义证明路径，再让 Agent 进入实现，避免把生成结果当成完成。
