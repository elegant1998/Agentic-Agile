# 第三部分｜验证工程与 3-4-3 落地：让操作系统真正运行

如果说 3-4-3 定义了治理系统的角色、工件和运行机制，那么 SCOPE-V 解决的是这些要素怎样在一次真实任务中持续运转。它把“**目标要明确、风险要受控、结果要验证**”从原则变成控制回路，使 Agent 的每一次行动都能找到方向、边界、执行关系、证明方式、修复路径和最终裁决依据。

SCOPE-V 不是另一套六步瀑布流程，而是六个持续运行的控制面：Specify 控制方向，Constrain 控制可行动空间，Orchestrate 控制协作关系，Prove 产生可检查证据，Evolve 根据失败诊断、修复和重证，Verify 保持独立视角并决定证据支持什么行动。Prove 与 Evolve 构成高频快内环，Verify 后的 Telemetry 构成慢外环，把真实质量、风险、成本和价值反馈到下一轮 S、C、O。

本部分分为两组。A 组“SCOPE-V 运行时控制”依次展开规格校准与显式签署、约束工程、Work Graph 与多 Agent 编排、TDD 与多层测试、失败驱动的演进、独立验证与上线裁决；随后把度量、遥测、契约级与全局 Dashboard 纳入反馈系统，并连接现有 CI/CD、分支、版本、构建、发布和回滚机制。B 组“3-4-3 工程化落地与扩展”再进入新项目与既有系统、Knowledge & Memory Engineering，以及多人、多工具、多模块协作。

读完本部分，读者不只应当“知道 SCOPE-V 的六个字母”，还应能够为一个任务建立可签署契约、可执行约束、可失败的验证、可收敛的修复回路和可审计的 Evidence Bundle，并理解为什么测试全绿、扫描通过或模型自评良好，都不能单独等同于可信发布。
