# 附录 I｜四大动态工件实战指南

四大动态工件不是四份彼此独立的文档，而是同一条治理链的不同视图。Intent Graph 提供全局关系，Intent Contract 锁定单任务承诺，Constraint Matrix 定义不可突破的边界，Evidence Bundle 汇总事实并支持裁决。任何工件脱离其他三者，都容易退化为静态材料。

“动态”至少意味着四件事：有明确所有者、有可识别状态、有内容版本、有真实事件触发更新。文件格式只是实现手段，Markdown、YAML、数据库或平台对象都可以承载工件；只要语义、责任和追溯关系稳定，不同 AI 工具就能参与同一条运行链。

| 工件 | 主要所有者 | 典型状态变化 | 主要触发事件 |
|---|---|---|---|
| Intent Graph | IO 对意图负责，OA 维护结构与新鲜度 | 假设 → 已验证；活跃 → 过期或替代 | 战略变化、任务完成、事故、依赖确认 |
| Intent Contract | IO 签署，OA 检查可执行性 | 草拟 → 签署 → 关闭；实质变更后重新签署 | 目标澄清、边界变化、裁决完成 |
| Constraint Matrix | 规则责任人批准，OA 工程化 | 草拟 → 生效 → 修订或废止 | 风险变化、例外、误报漏报、事故教训 |
| Evidence Bundle | 执行者生成，OA 聚合，Decision Owner 裁决 | 持续积累 → 可裁决 → 归档或更正 | 验证运行、人工批准、发布、回退、Bug |

Telemetry 不在这张表里，因为它不是第五个动态工件。四大工件承载任务运行中的意图、边界和事实；Telemetry 从已验证事实中派生跨任务信号，进入慢外环，用来调整规则、能力投资和组织设计。

### I.1 Intent Graph：不要从画一张宏大地图开始

意图图谱的最小节点可以只有五类：业务目标、能力、模块、任务和证据。边描述“为什么依赖”“由谁负责”“依据什么判断”。团队应从一个真实任务向外扩展，而不是先把整个企业建模。

以报销规则为例：

```text
降低违规付款风险（业务目标）
  └─ 审批路由能力（能力）
      ├─ 报销领域服务（模块）
      ├─ 组织关系服务（模块）
      └─ T-001 高额报销总监审批（任务）
          ├─ IC-T001（契约）
          ├─ AC-01..05（验收）
          └─ EB-T001（证据）
```

每次任务完成后，只回写经验证的新关系：字段语义、真实依赖、已确认风险和可复用规则。未经验证的推测可以记录，但必须标为假设，不能与事实混在一起。

图谱需要解决新鲜度问题。模块所有者、规则生效时间、最后验证任务和可能失效条件都比漂亮的可视化重要。一条两年前建立、无人负责的依赖关系，可能比没有图谱更危险，因为它会制造错误信心。

#### 图谱质量检查

- 能否从任务追溯到业务目标？
- 能否找到约束与证据来源？
- 关键节点是否有责任人？
- 事实与假设是否可区分？
- 变更后是否有回写机制？
- 过期节点能否被发现和淘汰？

### I.2 Intent Contract：不是把需求写得更长

契约应把会改变实现或裁决的内容写清楚。典型字段包括：

- 业务背景与目标；
- 可观测成功结果；
- 非目标；
- 业务规则与边界例子；
- MUST/SHOULD/MAY 验收标准；
- 已知假设和待决问题；
- 风险与回退要求；
- 数据、工具和权限边界；
- IO/OA 身份、版本和签署时间。

目标写成“优化审批体验”仍然不可判定。更好的写法是说明受影响对象、期望状态和观察方式，例如：“在不改变 5000 元及以下报销路径的前提下，对中国区新提交且含税本位币金额大于 5000 元的差旅报销增加成本中心总监审批节点。”

非目标不是附属字段。它防止 Agent 出于“顺手优化”修改历史数据、重构无关模块或扩大业务范围。对于高速执行系统，明确不做什么与明确做什么同样重要。

签署也不是在文件末尾写一个名字。有效签署至少绑定内容摘要、版本、身份和时间；契约发生实质变更后，旧签署应失效。OA 不能因为“IO 已经口头同意”而代替其完成签署。

#### 契约质量检查

- 两名不同执行者是否会得到相近理解？
- 每个 MUST 是否有判定方法？
- 边界值、异常路径和回退是否明确？
- 非目标是否足以阻止范围蔓延？
- 假设是否有验证人或失效条件？
- 最终版本是否由真实 IO 签署？

### I.3 Constraint Matrix：从原则到可执行边界

约束矩阵至少区分五类边界：业务规则、数据与隐私、架构与依赖、工具与权限、运行与发布。每条约束应说明强度、适用范围、检查方式、失败动作、例外批准人和证据位置。

“注意数据安全”无法执行；“Agent 不得读取生产客户明细，测试数据必须来自已脱敏数据集，检查失败立即停止并通知安全责任人”才开始具备治理意义。

MUST 代表违反后不能继续；SHOULD 允许在记录理由和责任人后例外；MAY 是可选优化。团队应谨慎使用 MUST：过多不可执行的硬规则会造成约束疲劳，成员最终学会绕过全部门禁。

约束冲突需要显式优先级。例如业务希望快速灰度，安全政策要求生产权限人工批准，项目预算限制额外环境。OA 不能选择最方便的一条，而应展示冲突、影响和备选路径，由具有相应责任的人裁决。

#### 约束质量检查

- 是否说明适用对象和阶段？
- 能否由脚本、策略或明确人工动作检查？
- 失败后是阻断、降级、回退还是告警？
- 是否存在隐含的例外通道？
- 例外是否有时限、责任人和复核？
- 规则是否定期根据误报、漏报和事故更新？

### I.4 Evidence Bundle：把事实组织成决策材料

Evidence Bundle 的读者不是只有工程师。IO 需要知道目标是否实现和哪些风险仍存在；OA 需要检查治理链是否完整；开发与测试需要复现结果；安全和审计需要追踪权限与批准。

一份有效证据包通常包括：

- 任务和契约版本；
- 代码与配置变更摘要；
- 每项 AC 对应的检查与结果；
- 原始命令、环境、退出码和时间；
- 构建、测试、安全、依赖和约束结果；
- 人类批准、例外和关键 Handoff；
- 未验证事项与残余风险；
- 回退方案及验证结果；
- 可追溯的遥测采集入口；
- 推荐裁决，但不替代责任人决定。

证据强度存在层级。Agent 声称“已经测试”是低强度陈述；保存命令和退出码更强；在隔离环境中由独立流水线复现更强；与真实但受控的业务样本、回退演练和运行监控结合，才能支持更高风险的发布。

证据包也必须允许得出“不发布”。如果模板只允许填写成功结果，团队会隐藏未知项。成熟的 Evidence Bundle 应把失败、跳过和不适用区分开，把“没有证据”与“证据证明失败”区分开。

#### 证据质量检查

- 每个 MUST 是否能找到对应证据？
- 证据来自原始系统还是人工转述？
- 执行环境和时间是否可识别？
- 跳过项是否有理由和责任人？
- 残余风险是否能被非开发角色理解？
- 发布后发现 Bug 时，原证据能否被修正和追溯？

### I.5 四大动态工件的一致性检查

最常见的问题不是某个工件缺失，而是彼此矛盾：图谱仍指向旧模块，契约已经变更，约束检查使用旧规则，Evidence Bundle 却把全部 AC 标为通过。

一致性检查至少覆盖：

```text
目标一致：Contract 的目标来自 Graph 中有效意图
边界一致：Contract 的规则被 Matrix 覆盖
验证一致：每项 MUST AC 都映射到 Evidence
版本一致：签署、检查和证据针对同一版本
责任一致：批准者与授权矩阵匹配
回写一致：经验证的新知识返回 Graph 和规则资产
```

这也是五道机械门存在的原因。人类很难在高速交付中持续手工核对所有关系，必须让脚本和结构化标识承担重复一致性检查，把人的注意力留给价值冲突与异常判断。

跨 AI 工具协作时，真正需要稳定的不是某个产品的会话记录，而是任务 ID、契约版本、约束 ID、AC ID、证据引用、状态枚举和签署身份。工具可以更换，模型可以升级，运行事实不能因此失去语义。任何只在某个 Agent 私有记忆中存在、无法被下一工具读取和复查的信息，都还没有成为组织资产。

### I.6 工件的轻量化与升级条件

低风险修正文案时，契约可以很短，约束可以继承仓库默认值，证据可能只包含快照测试和差异；涉及支付、权限、隐私或跨模块发布时，工件必须更完整。升级条件可以包括：

- 存在不可逆数据变更；
- 使用生产凭证或敏感数据；
- 影响两个以上模块或团队；
- 引入新工具、模型或外部依赖；
- 业务规则存在法律、财务或安全责任；
- 回退时间超过组织可接受窗口；
- 自动验证无法覆盖关键判断。

轻量化不是删除责任，而是减少与当前风险无关的字段；升级也不是增加文档页数，而是提高边界和证据强度。
