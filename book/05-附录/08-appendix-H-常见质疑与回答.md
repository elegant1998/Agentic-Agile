# 附录 H｜常见质疑与回答

### H.1 “这不就是把敏捷流程重新命名吗？”

不是。Agentic Agile 继承快速反馈、增量交付和持续改进，但它处理了新的执行现实：概率性 Agent 能调用工具、修改多个文件、并行协作并快速放大错误。因此治理对象从人类协作流程扩展到意图、权限、上下文、机器门禁、证据和自治边界。它不是否定敏捷，而是为 Agent 参与交付补齐控制系统。

### H.2 “小需求也要写这么多文档吗？”

不需要。治理重量应与风险匹配。低风险单模块任务可以只保留最小契约、核心约束、可执行 AC 和 Evidence Bundle；高风险、多模块、不可逆任务才需要更完整的 Protocol、Work Graph、跨模块契约和批准链。关键不是模板页数，而是目标、边界、证据和责任不能缺席。

### H.3 “模型越来越强，以后还需要这些吗？”

更强模型会减少部分实现错误，却不会自动拥有组织授权，也不能替人类承担法律、伦理和商业责任。能力越强、作用范围越大，越需要知道它能做什么、何时停止、如何证明和如何恢复。治理方式会更自动化，但治理问题不会自动消失。

### H.4 “TDD 会不会拖慢 AI Coding？”

在简单演示中，先写测试似乎增加步骤；在真实交付中，它减少的是错误方向上的高速实现和事后争论。可信 Red 证明测试能发现缺失行为，AC 建立业务语义，回归测试保护已有能力。真正需要优化的是测试分层和执行速度，而不是取消证明环节。

### H.5 “Evidence Bundle 会不会变成新的形式主义？”

会，如果它由人手工拼接、只展示漂亮截图、与 AC 和原始命令无映射。有效 Evidence Bundle 应尽量自动采集，保留来源、时间、退出码和适用范围，并坦诚列出未验证事项。它服务于裁决，不服务于表演。

### H.6 “为什么 IO 必须本人签署？”

因为目标、非目标和残余风险属于价值责任。OA 可以澄清和起草，AS 可以执行，二者都不应替业务责任人决定“做什么值得”和“哪些风险可以接受”。允许代理签署会让治理看似完整，实则责任空心化。

### H.7 “多 Agent 一定比单 Agent 快吗？”

不一定。并行收益受任务独立性、共享资源、接口稳定度和验证成本限制。不可分解任务强行并行，会产生冲突与上下文开销。Orchestrate 的目标是优化端到端流动，而不是最大化同时在线的 Agent 数。

### H.8 “发生 Bug 是否说明证据包失效？”

证据不是绝对正确保证，而是对特定范围、特定时间和特定环境的可复查证明。Bug 可能来自遗漏 AC、环境差异、测试盲区或证据失真。成熟系统会立即修正原证据、控制影响、追溯根因并更新治理资产，而不是用“当时测试通过”维持虚假结论。

### H.9 “我们已经有 DevOps、CI/CD 和平台工程，还需要 3-4-3 吗？”

这些能力是重要基础，但它们通常不会自动回答业务意图由谁签署、Agent 的权限如何裁剪、跨 Agent 交接如何验证、残余风险由谁接受。3-4-3 可以复用现有流水线、策略引擎和观测平台，把它们连接到意图与责任，而不是推倒重建。

### H.10 “怎样证明这套方法值得投入？”

先选一个低风险但真实的任务做基线对比。不要只测开发时长，同时记录歧义发现时点、返工、越权阻断、首次成功率、验证成本、发布后缺陷和人工介入质量。若治理成本没有换来更早风险发现、更少返工或更清晰决策，就应调整，而不是为了维护方法正确而美化数据。
