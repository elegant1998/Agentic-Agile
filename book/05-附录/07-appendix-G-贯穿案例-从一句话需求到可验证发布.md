# 附录 G｜贯穿案例：从一句话需求到可验证发布

本附录把全书方法压缩到一个连续案例中。它不是唯一正确答案，而是一份可以对照真实项目修改的治理样本。

### G.1 原始需求

周四下午，业务负责人提出：

> 员工报销超过 5000 元，需要总监审批。这个需求很急，希望明天上线。

传统做法很容易立即进入估时和编码。Agent 也可能迅速找到审批逻辑，修改判断符号，补一两个测试，然后报告完成。但这句话至少隐藏着以下问题：

- “超过”是否严格大于，等于 5000 元怎么办？
- 金额按含税、未税还是本位币折算后计算？
- 总监是申请人的直属总监、成本中心总监还是财务总监？
- 历史草稿、审批中单据和已完成单据是否受影响？
- 总监缺席时是否允许代理？
- 规则是否适用于全部费用类型和全部组织？
- 明天上线是全量启用还是具备灰度与回退？

高速度不会消除这些问题，只会让某一种未经签署的解释更快进入系统。

### G.2 Specify：把自然语言转成判定规则

OA 通过 Grill-Me 与 IO 校准，形成以下关键决定：

- 仅适用于中国区差旅报销；
- 金额按含税人民币总额判断；
- 5000.00 元不触发，5000.01 元触发；
- 审批人为申请人所属成本中心总监；
- 只影响规则启用后新提交的单据；
- 历史草稿迁移明确列入非目标；
- 若无法解析成本中心总监，禁止自动通过，转人工财务队列；
- 首日采用功能开关，仅对两个试点部门启用。

IO 阅读目标、非目标、规则、AC 和风险后完成独立签署。OA 可以起草，不能代签；Agent 可以帮助澄清，不能承担业务责任。

可执行 AC 至少包括：

1. 给定含税总额 5000.00 元，提交后不增加总监审批节点；
2. 给定含税总额 5000.01 元，提交后增加成本中心总监节点；
3. 给定无法找到成本中心总监，提交进入人工财务队列且不得自动通过；
4. 给定规则启用前已存在草稿，再次保存时审批链不被静默改写；
5. 关闭功能开关后，新提交单据恢复旧路径。

### G.3 Constrain：把底线从文字变成门禁

Constraint Matrix 同时记录业务、数据、技术、工具和发布约束：

- 禁止修改已审批单据；
- 禁止读取或输出生产个人报销明细；
- 禁止 Agent 获取生产发布凭证；
- 数据库结构变更必须由 DBA 审批，本任务原则上不得引入迁移；
- 单次自动修复不超过三轮；
- 任何 AC 失败都不得生成“可发布”结论；
- 功能开关、回退步骤和负责人必须在发布前验证；
- Evidence Bundle 必须包含测试原始输出、代码差异、约束检查和残余风险。

其中能自动执行的规则进入 YAML 和 CI，不能完全自动判断的规则绑定责任人和批准记录。约束不是一份“注意事项”，而是执行环境的一部分。

### G.4 Orchestrate：让工作有依赖、有交接、有停止条件

OA 创建 Work Graph：

```text
N1 生成并运行规则测试，确认可信 Red
 ├─ N2 实现领域审批规则
 └─ N3 准备功能开关与回退验证
N2 + N3 → N4 接口与集成测试
N4 → N5 约束检查与 Evidence Bundle
N5 → N6 IO 发布裁决
```

每个节点只获得所需上下文。测试节点读取契约和接口，不读取候选实现；实现节点读取签署契约、测试和编码约束；证据节点读取原始检查输出，不允许仅采用执行 Agent 的自然语言总结。

若发现旧系统对 5000 元使用 `>=`，节点必须停止并报告规则冲突。它不能以“保持兼容”为由自行修改新契约，也不能悄悄改变旧数据。

### G.5 Prove：先证明测试会失败

测试 Agent 先提交边界和异常测试，并在未实现新规则时运行。预期 Red 不是形式动作：团队检查失败原因确实是缺少新行为，而不是环境损坏、断言错误或测试根本未执行。

实现 Agent 只完成使测试通过的最小改动。随后执行：

- 领域单元测试；
- 审批链集成测试；
- 功能开关关闭后的回退测试；
- 权限和敏感数据检查；
- 全量回归中与审批相关的测试；
- 构建与静态检查。

若测试与实现由同一模型生成，关键边界还需由 OA、第二模型或既有业务样本交叉检查，避免同一误解同时写进代码和测试。

### G.6 Evolve：失败如何形成组织能力

第一次集成测试发现，代理总监配置会产生两个候选审批人。AS 没有权限决定业务优先级，因此停止并提交：触发输入、候选人列表、当前规则、测试结果和两个可选方案。

IO 决定“优先使用当前生效代理；同时存在多个代理时转人工财务队列”。契约和 AC 更新并重新签署，AS 再完成测试与实现。这个经验随后写回意图图谱和约束矩阵，下一次涉及组织代理关系的任务会主动提出同类问题。

系统学习的不是一句空泛的“注意代理人”，而是一条具有适用范围、证据来源、责任人和失效条件的治理资产。

### G.7 Verify：证据支持哪一种行动

Evidence Bundle 最终显示：

- 5 项业务 AC 全部通过；
- 回归、构建和安全检查通过；
- 未使用生产数据和生产凭证；
- 功能开关关闭路径已验证；
- 历史草稿迁移未验证，且明确属于非目标；
- 多代理冲突规则已由 IO 重新签署；
- 首日监控负责人和异常阈值已登记。

IO 据此作出有边界的裁决：批准两个部门灰度启用；若人工财务队列异常增长或审批链错误率超过阈值，自动关闭功能开关；次日复核遥测后再决定是否扩大。

这里真正重要的不是“Agent 一天写完了”，而是团队能说明它理解了什么、被禁止做什么、如何证明结果、还有什么没有证明，以及为什么当前发布范围可接受。

### G.8 发布后 Bug 回溯

灰度期间发现一张外币报销单被错误按原币数值判断。团队立即关闭开关，保留事件与日志，修正 Evidence Bundle 中原有的发布结论，并启动 Bug 回溯门。

根因分析发现，契约虽然写了人民币含税总额，但测试样本全部为人民币，接口字段中“本位币金额”与“原币金额”命名相近。改进不只是一行代码：

- 增加外币和汇率缺失 AC；
- 在约束中要求金额判断必须引用标准化本位币字段；
- 更新字段语义到意图图谱；
- 增加静态检查或类型封装，降低字段误用；
- 更新遥测和事故记录，不保留虚假的首次全绿。

Bug 没有证明治理无用，反而检验治理是否诚实：能否快速限制影响、纠正证据，并把失败转化为下一次更强的系统能力。
