# 第四章｜Agentic Agile 五条宣言：先有价值取舍，再有方法

方法论需要价值观，因为工具无法替组织回答“发生冲突时更重视什么”。同一套 Agent、测试和流水线，可以被用来追求短期速度，也可以被用来建立长期可信交付。五条宣言为 3-4-3 的设计和取舍提供共同方向。

宣言中的“胜过”沿用敏捷宣言的表达方式。它不意味着右项没有价值，而是在两者发生冲突时，左项应获得更高优先级。

在新的全书结构中，五条宣言不只指导一次 AI Coding 任务，也指导四维转型中的组织取舍：

| 宣言 | 四维转型中的典型冲突 | 优先保护什么 |
|---|---|---|
| 意图锚定 | 工具采用率、自动化率与真实业务结果冲突 | 可观察的价值意图与人类责任 |
| 多模态涌现协作 | 固定岗位边界与动态人机能力组合冲突 | 能力按意图组合，同时保留责任归属 |
| 算法规则与架构韧性 | 更多审批与更快、更稳定的机器控制冲突 | 可执行边界、恢复能力与必要的人类裁决 |
| 实时遥测与闭环对抗 | 漂亮汇报、个人排名与真实系统反馈冲突 | 可行动的系统事实与反指标 |
| 基于验证的系统工程 | 演示速度、生成数量与可信交付冲突 | 与风险相称的独立证据 |

五条宣言并不为所有冲突给出唯一答案。它们提供的是优先级：当短期产出与长期系统能力、机器自治与人类责任、局部速度与端到端价值发生冲突时，团队知道哪些东西不能为了看起来更快而被牺牲。

## 4.1 意图锚定，胜过详尽规约

### 为什么提出

传统需求管理常在两个极端之间摆动：一端只有一句模糊诉求，另一端试图在执行前穷尽所有细节。前者让 Agent 自由猜测，后者则容易产生大量很快过期的文档。

Agent 的危险不只是“听不懂”，还包括过度字面服从。它可能完美执行一句不完整指令，却偏离真正业务目标。

### 真正含义

意图锚定要求系统始终知道：

- 为什么做；
- 要改变什么业务结果；
- 什么不能被牺牲；
- 当前只做什么；
- 什么明确不做；
- 怎样判断完成。

意图不是一句愿景口号。它必须经过契约化，成为 Goal、Non-goals、Rules 和 AC。

### 不意味着什么

- 不意味着不写规格；
- 不意味着可以用模糊目标代替验收标准；
- 不意味着 IO 只说方向，所有细节都由 AI 决定；
- 不意味着签署后契约永远不能版本化。

意图决定方向，规格提供执行精度，两者不是敌人。

### 如何落地

1. 从意图图谱定位长期目标和依赖；
2. OA 对字面需求进行批判性校准；
3. 通过 Grill-Me 逐项确认关键决策；
4. 形成意图契约；
5. IO 审阅完整契约并显式签署；
6. 所有任务、测试和证据映射回契约。

### 费用报销案例

“超过 5000 元增加总监审批”不是完整意图。真正意图可能是降低高额差旅风险，同时不增加普通员工报销摩擦。这个意图会直接影响边界值、例外和成功指标。

如果只执行字面规则，系统可能把所有币种、所有报销类型和历史单据都纳入修改；经过意图锚定后，本次契约可以只处理境内人民币差旅，并明确不修改 5000 元及以下路径。

### 四维转型中的冲突

管理层可能把“AI 工具激活率达到 80%”“生成代码占比达到 50%”设为转型目标，平台团队据此推动所有岗位使用同一工具。指标很明确，却没有说明企业要改善哪条价值流、缩短什么周期、减少什么成本，也没有说明谁对业务结果负责。

意图锚定要求把工具采用降回手段：先签署要改善的业务结果和非目标，再决定人员任务怎样迁移、组织授权怎样调整、流程堵点怎样消除、工具能力怎样接入。采用率可以作为实施信号，但不能取代价值意图。

### 常见误区

- 把意图图谱做成巨大的知识库，却无法裁剪到任务；
- 把一句愿景当成契约；
- AC 只有“功能正常”“体验良好”；
- Grill-Me 完成后由 OA 自动代签；
- 实现失败后修改契约以获得通过。

### 价值观检查

> 如果 Agent 完全按字面完成需求，业务目标是否一定实现？如果答案是否定的，意图还没有锚定。

## 4.2 多模态涌现协作，胜过仅依赖跨职能人类团队

### 为什么提出

传统跨职能团队通过把产品、开发、测试和运维能力放进稳定团队，减少职能墙和交接。这一原则依然有效。但当 Agent 能够承担检索、分析、生成、测试和运行任务时，能力单元不再只由固定岗位提供。

文本、代码、图像、日志、指标和终端输出可以被不同 Agent 处理，多种候选方案也可以并行产生。这为协作带来新的组合空间。

### 真正含义

“涌现”不是让许多 Agent 自由聊天，而是让具备不同能力的执行单元，在共同意图、约束和证据标准下产生单一主体难以获得的结果。

有效涌现需要：

- 角色化能力；
- 独立或互补视角；
- 明确 Work Graph；
- 结构化 Handoff；
- 冲突和停止机制；
- 统一验证标准。

### 不意味着什么

- 不意味着人类团队不再重要；
- 不意味着 Agent 越多越好；
- 不意味着可以让多个 Agent 同时修改同一范围；
- 不意味着多数投票就是真相；
- 不意味着模型之间的互评可以替代真实测试。

### 如何落地

将一个复杂任务拆成真正独立的视角。例如：

```text
规则分析 Agent：识别业务边界
测试 Agent：从 AC 生成反例
实现 Agent：完成最小修改
安全 Agent：检查数据和权限
证据 Agent：汇总真实结果
```

并行只发生在没有依赖和写冲突的节点。每个节点只获得最小必要上下文，输出必须带来源和状态。

### 费用报销案例

规则分析 Agent 发现“5000元是否包含边界”尚未明确；测试 Agent 生成 4999.99、5000.00、5000.01 三个反例；安全 Agent 确认测试不得访问生产报销数据。三种视角共同提高结果质量，但最终业务口径仍由 IO 决定。

### 四维转型中的冲突

动态 Agent 网络可以跨越开发、测试、安全和运维边界，但固定岗位仍承载长期专业能力、产品责任和组织承诺。如果组织只强调“能力随意组合”，就可能出现任务由多个 Agent 完成，却没有人对意图、例外和发布负责；如果只守住岗位边界，Agent 的跨专业并发能力又会被重新切回人工接力。

宣言优先支持按意图组合能力，但不支持责任漂移。人员维度明确不可转移的人类责任，组织维度建立责任节点，流程与工具负责让 Agent 能力按契约、依赖和证据协作。动态的是执行组合，稳定的是价值与风险责任。

### 常见误区

- 为展示多 Agent 而人为拆分简单任务；
- 多个 Agent 共享全部上下文，造成隐私和噪声扩散；
- 上游只输出“已完成”，下游无法验证；
- Agent 互相认同后，跳过确定性测试；
- 没有 Token、时间和重试预算。

### 价值观检查

> 新增一个 Agent 后，是否增加了独立能力或证据？如果只增加了对话轮次，它不是有效涌现。

## 4.3 算法规则与架构韧性，胜过仅依赖流程纪律与仪式

### 为什么提出

人类流程依赖记忆、培训和纪律。团队可以规定“必须先写测试”“不得提交密钥”“发布前必须有回退方案”，但在压力下，这些规则常被遗忘、误解或绕过。

Agent 不会因为读过制度就稳定遵守。规则必须进入它的上下文、权限和执行环境。

### 真正含义

算法规则是机器能够检查的约束，架构韧性是系统在失败时限制影响、降级、恢复和升级的能力。

它们包括：

- 约束矩阵（constraints.yaml）；
- 工具约束清单（Tools Manifest）；
- AI Coding Guide；
- 机械门禁；
- 超时、重试、熔断和补偿；
- 回滚安全；
- 例外有效期；
- HITL 触发条件。

### 不意味着什么

- 不意味着取消所有流程和会议；
- 不意味着所有规则都能自动化；
- 不意味着有门禁就不会发生事故；
- 不意味着可以用僵化规则替代价值判断；
- 不意味着通过检查就等于业务正确。

无法自动化的规则仍需明确责任人和人工证据。

### 如何落地

把“注意事项”改写为：

```text
适用范围
检查方式
失败动作
证据位置
例外批准人
有效期
恢复方式
```

优先把少量高风险规则变成 MUST，而不是一次写出上百条低质量约束。

### 费用报销案例

“不要影响旧审批流程”应转化为 5000 元及以下路径的回归测试；“不要使用生产数据”应转化为数据环境约束；“上线前要小心”应转化为发布需人类批准和可执行回退。

### 四维转型中的冲突

面对 Agent 风险，一种常见做法是在原流程上增加 AI 审查表、治理委员会和更多人工签字。风险看似得到控制，结果却是每个机器动作重新等待人，组织既没有获得速度，也没有提升控制质量。

算法规则与架构韧性要求把重复、明确、可检查的控制交给工具运行，把会议和审批留给价值冲突、约束例外与不可逆风险。它不是取消流程纪律，而是让人员不再反复充当机械检查器，让组织决策集中在机器不应自行决定的地方。

### 常见误区

- 约束只有自然语言，没有检查命令；
- 所有规则都设为 MUST，导致团队只能绕过；
- 例外没有失效时间；
- 门禁只检查文件存在，不检查真实内容；
- 为追求自动化率，把不可逆操作也交给 Agent。

### 价值观检查

> 如果换一个从未参与项目的人或 Agent，这条关键规则还能被稳定执行吗？如果不能，它仍然只是隐性纪律。

## 4.4 实时遥测与闭环对抗，胜过仅依赖阶段性复盘

### 为什么提出

阶段性复盘能够帮助人类总结经验，但它通常发生在大量执行之后。Agent 可以在一次任务中完成多轮尝试，如果失败、重试、权限阻断和成本只在最后被汇总，团队会失去最有价值的过程信号。

### 真正含义

实时遥测关注任务正在怎样运行，闭环对抗关注不同验证机制怎样主动发现偏差。

需要观测：

- 目标是否命中；
- 首次是否成功；
- 哪些约束失败；
- 哪些失败被自动修复；
- 人类为何介入；
- 使用了多少时间和 Token；
- 哪些模式值得沉淀；
- 上线后价值是否出现。

### 不意味着什么

- 不意味着取消人类复盘；
- 不意味着采集越多指标越好；
- 不意味着用指标评价个人；
- 不意味着 LLM 生成的数字可以当遥测；
- 不意味着只关注 Token 成本。

遥测是为了改进系统，不是为了制造监控焦虑。

### 如何落地

每个契约 Verify 后采集单任务遥测，同时更新项目累计数据。测试数来自真实运行，Token 优先实测，无法实测时标记 estimated。团队定期观察趋势，而不是只看单次漂亮结果。

### 费用报销案例

如果 T-001 经历四次修复才通过，团队不应只记录“最终成功”。这可能说明边界规则不清、测试生成不足或审批模块技术债较高。下一轮应针对根因改进，而不是庆祝 Agent 终于完成。

### 四维转型中的冲突

当管理者用 Token 最少、自动化率最高、HITL 最低或生成代码最多给个人和团队排名时，度量会立即改变行为：必要的人类介入被隐藏，失败被拆到新任务，验证成本被转移给下游，团队开始优化仪表板而不是价值流。

实时遥测应评价人、Agent、上下文、流程和工具共同构成的生产系统，并用相互制衡的指标揭示成本转移。人员维度保护员工免受粗暴监控，组织维度根据趋势调整授权，流程与工具保证数据来自真实事件。遥测必须能够触发改进，也必须有反指标防止被单一目标劫持。

### 常见误区

- 手工填写 100% 通过率；
- 只展示成功任务；
- Bug 出现后另开新任务，保留原任务首次成功；
- 仪表板很多，但没有任何治理动作；
- 将人类介入一律视为失败。

### 价值观检查

> 指标变化后，团队知道应修改意图、约束、编排、验证还是模型吗？如果不知道，遥测只是装饰。

## 4.5 基于验证的系统工程，胜过随性提示与氛围编程

### 为什么提出

提示词能够改善模型输出，却无法单独建立可靠交付。模型可以生成看起来合理的代码、测试和解释，甚至可以自信地宣布任务完成。正式工程需要独立于生成者的判定机制。

### 真正含义

验证工程要求：

- AC 可执行；
- 测试先于实现；
- 真实运行结果被保留；
- 约束能够机械检查；
- 失败不能通过降低标准消失；
- Evidence Bundle 映射目标、约束和证据；
- 人类基于证据裁决高影响行动。

### 不意味着什么

- 不意味着探索阶段不能 Vibe Coding；
- 不意味着所有输出都必须形式化证明；
- 不意味着测试全绿即可无条件上线；
- 不意味着人工经验毫无价值；
- 不意味着为低风险任务引入重型治理。

验证强度应与风险、可逆性和影响范围匹配。

### 如何落地

从最小闭环开始：

```text
意图契约
→ 约束矩阵
→ TDD Red
→ 最小实现
→ TDD Green
→ 全量验证
→ Evidence Bundle
→ 人类裁决
→ Telemetry
```

### 费用报销案例

AI 可以在几秒内写出 `amount >= 5000`，也可以为它生成一个恰好通过的测试。验证工程要求从契约边界出发，独立检查 5000.00 和 5000.01，并保留先红后绿的证据。只有这样，团队才能发现实现是否真正符合“严格大于”的业务规则。

### 四维转型中的冲突

企业突围项目可以在一天内完成真实增量，这证明机器速度能够转化为工程结果；但如果为了展示速度而让生成者自己定义标准、自己验证、自己宣布完成，演示越成功，组织越容易高估可复制能力。反过来，把所有任务都要求为重型审计，也会让验证工程成为新的流程负担。

宣言要求验证强度与风险相称：低风险探索保持轻量和可丢弃，正式交付建立契约、约束和独立证据，高风险任务增加职责隔离与有权者裁决。工具应自动完成大部分机械验证，人把时间放在证据矛盾、剩余风险和价值判断上。可信与速度不是二选一，验证系统本身也必须被设计成高吞吐能力。

### 常见误区

- 让生成代码的同一提示同时生成所有测试，并假设两者独立；
- 测试只覆盖正常路径；
- 用 shell grep 代替运行时行为验证；
- 把模型自评当成最终证据；
- Evidence Bundle 在发布后补写。

### 价值观检查

> 如果删除模型对自己工作的解释，只保留工件和运行结果，第三方还能判断是否完成吗？

## 4.6 五条宣言如何共同工作

五条宣言不是五个平行口号，而是一条递进链：

```text
意图锚定
确保方向正确
    ↓
涌现协作
获得足够执行能力
    ↓
算法规则与韧性
限制执行边界
    ↓
实时遥测与闭环
持续发现偏差
    ↓
验证工程
用证据支持最终裁决
```

缺少任何一条都会失衡：只有意图没有验证，目标仍可能被错误实现；只有验证没有意图，系统可能高质量地完成错误任务；只有多 Agent 没有约束，协作会放大风险；只有门禁没有遥测，组织无法判断治理是否改善。

从四维观察，这条链同样不能被拆开：意图为人员和组织提供共同方向，涌现协作重组能力网络，算法规则和韧性进入流程与工具，实时遥测把运行事实反馈给组织，验证工程则让人能够基于证据承担最终裁决。宣言不是操作系统的五个模块，而是贯穿四维设计的五条优先级规则。

## 4.7 组织级价值观冲突练习

假设公司要求一个季度内“AI 生成代码占比达到 50%，所有研发团队接入统一 Agent 平台”，并承诺研发效能提升 30%。不要先争论目标激进还是保守，选择一条真实价值流，用五条宣言依次重写这项要求：

1. **意图锚定**：30% 具体改善什么业务结果、端到端周期或总成本？哪些质量与风险不能恶化？
2. **涌现协作**：哪些任务交给 Agent，哪些判断留给人，如何组合能力而不稀释责任？
3. **规则与韧性**：哪些边界可以机械执行，哪些例外和不可逆动作必须保留人类裁决？
4. **遥测与闭环**：怎样证明提效没有转移为返工、审核、风险和员工监控？
5. **验证工程**：首个真实切片需要什么证据，才能决定扩大、调整或停止？

练习的结果不应是另一份原则声明，而应是一份可签署的转型假设：业务结果、四维改变、护栏、证据和裁决条件同时成立。价值观的作用，就是在压力和冲突中提供一致的取舍顺序。
