# 第八章｜三大自治机制与 Harness：让 Agent 获得有边界的执行权

## 8.1 三大自治机制

这里的“自治”不是把责任整体交给 AI，而是让 Agent 在已签署意图、明确权限和可验证边界内获得执行权。三大机制回答三个连续问题：**任务从哪里获得确定目标，执行偏差怎样被纠正，机器不能决定时由谁接管。** 如果没有这三个机制，Agent 即使拥有很强的编码能力，也只是在一个缺少方向盘、刹车和驾驶责任人的系统里高速行驶。

### 机制一：意图注入与对话到契约——给自治执行一个稳定起点

“意图注入”听起来像一个技术动作，很容易被理解为把一段 Prompt 发给 Agent。它真正要解决的是：探索阶段充满讨论、假设和变化，而执行阶段需要一份稳定、可判定、经过授权的任务基准。两者如果混在一起，Agent 可能把一句试探性意见当成最终决定，也可能在对话后半段忘记前面的关键限制。

意图注入通常经过四步：

1. IO 提出目标或问题，不要求第一句话已经完整；
2. OA 通过批判性思维和 Grill-Me 揭示歧义、冲突与风险；
3. OA 把已经确认的决定整理成 Intent Contract；
4. IO 审阅完整契约并显式签署，系统再把任务所需上下文、约束和 AC 注入 AS。

以“超过 5000 元的报销增加总监审批”为例，真正注入 Agent 的不只是这句话，而应包括金额口径、边界值、适用组织、非目标、异常路径、权限限制以及可以证明完成的 AC。于是 Agent 面对的不是一个需要自行猜测的愿望，而是一项获得授权的工程任务。

意图注入的核心价值是建立“探索—承诺”的分界线。契约签署前可以充分讨论；签署后，AS 不能静默改变目标。如果执行中出现新事实，需要判断它属于实现细节，还是已经改变契约。后者必须暂停并重新签署。

常见误解有三个：一是把全部会议纪要都塞进上下文，导致噪声大于信息；二是把 IO 的第一句话直接视为意图，跳过校准；三是由 OA 或 Agent 自动写上“已签署”，让授权变成形式。真正的意图注入不是“信息越多越好”，而是“进入执行的信息已经过筛选、确认和授权”。

### 机制二：高频对抗与自净化——让偏差在小范围内尽早暴露

“对抗”并不是让多个 Agent 互相争吵，而是用测试、规则、独立检查和反例不断挑战当前结果。传统交付常在开发末尾才集中测试；Agent 的执行速度更快，如果反馈仍然滞后，错误会在几分钟内跨越多个文件和模块。高频对抗的目的，是把反馈嵌入执行过程，使错误尚未扩散时就被发现。

一次最小对抗循环包括：

```text
提出候选结果
→ 用 AC、测试和约束挑战
→ 记录失败类型与原始证据
→ 判断是否在授权范围内可修复
→ 最小修复并重跑原检查
→ 收敛或停止升级
```

例如测试发现 5000.00 元也进入总监审批。系统先保存输入、期望、实际结果和规则版本，再判断这是普通实现错误、规格冲突、环境问题还是约束违规。如果只是比较符号写错，AS 可以在限定次数内修复；如果财务制度与已签署规则冲突，AS 就没有权力“选择更合理的一边”，必须升级。

“自净化”也不等于自动修到成功为止。每次循环都需要预算、最大次数、允许修改范围和停止条件。连续三次出现不同失败、修复需要降低测试强度、必须扩大权限、或错误根因无法解释时，都应停止。无限自修复只会隐藏系统没有收敛的事实，并消耗更多时间与 Token。

高频对抗的结果不只是一份全绿报告。失败分类、修复次数、被触发的约束、人工介入点和最终残余风险，首先应进入当前任务的 Evidence Bundle，支持本次裁决；其中具有跨任务分析价值的运行事实，再按 Measurement Contract 汇入 Telemetry。这样组织才能判断 Agent 是一次做对，还是经过大量试错勉强通过。

### 机制三：人类异常裁决与证据包验收——把机器不该决定的事情交还责任主体

HITL（Human in the Loop）常被翻译为“人在回路中”。很多团队据此在每一步增加人工审批，最后既没有自治，也没有效率。另一种极端是只在上线前让人点一下同意，使人类成为无法真正审查的橡皮图章。

Agentic Agile 中的人类介入按任务性质触发，而不是按固定流程节点机械出现。至少四类事项应交给人类：

- **不可逆操作**：删除生产数据、对外发布、资金支付、扩大生产权限；
- **价值判断**：范围取舍、风险偏好、用户体验与成本冲突；
- **不确定验证**：证据互相矛盾、语义依赖业务背景、自动测试无法覆盖；
- **例外授权**：临时放宽约束、接受已知风险、改变签署目标。

异常升级时，系统不应只抛出一句“请决定”。OA 要把问题整理为可裁决包：发生了什么、违反了哪条规则、有哪些原始证据、继续或停止各有什么影响、推荐选项和理由是什么。人类作出决定后，决定本身也要进入契约、例外记录或证据包，形成可追溯责任链。

因此，好的 HITL 不是人越多越安全，而是**正确的人在正确的信息基础上，对机器不应决定的事情负责**。如果人类经常被迫处理可自动化的重复问题，说明 Harness 不成熟；如果重大价值和不可逆操作从不触发人类，说明自治已经越界。

### 三大机制如何连成一条运行链

意图注入提供目标与授权，高频对抗持续检查执行是否偏离，人类异常裁决处理机器边界之外的决定。三者不是三个孤立功能，而是一条从“可以开始”到“可以继续”再到“必须停下”的控制链：

```text
意图已校准并签署？——否→继续澄清
        │是
        ↓
AS 在边界内执行，并接受高频挑战
        │
        ├─ 可修复偏差→有限自净化→重新验证
        └─ 越权/冲突/不可逆→停止→人类裁决
                                  │
                         更新契约、约束或行动决定
```

读者可以用一个问题检查自己的流程：**Agent 在什么时候获得执行授权，什么失败允许它自行修复，出现什么信号时它必须停下？** 如果三个答案都不清楚，就还没有形成自治机制。

## 8.2 从三大自治机制到 Harness 工程承载

三大自治机制定义的是治理逻辑：任务怎样获得授权，偏差怎样被纠正，机器不能决定时怎样交还人类。但如果这些逻辑只存在于制度、培训或 Prompt 提醒中，Agent 仍然可以因为上下文错误、权限过大、状态丢失或门禁可跳过而失控。自治机制必须由能够运行的工程环境承载，这个环境就是广义 Harness。

可以用四个层级理解本章与下一章的关系：

| 层级 | 回答的问题 | 本书中的内容 |
|---|---|---|
| 三大自治机制 | 自治系统必须完成什么治理动作？ | 获得意图、纠正偏差、异常交还人类 |
| Harness 六大支柱 | 为支撑自治，系统必须具备什么能力？ | 上下文、工具、编排、状态记忆、评估观测、约束恢复 |
| 四类工程方法 | 六种能力具体怎样建设？ | Context、Graph、Loop、Harness Engineering |
| SCOPE-V | 这些机制在一次任务中何时运行？ | S、C、O、P⇄E、V 与 Telemetry |

因此，三大机制不是六大支柱的上位替代品，六大支柱也不是另一套 3-4-3。前者描述运行逻辑，后者描述能力结构；四类工程提供实现路径，SCOPE-V 再把它们放入运行时控制回路。

三大机制与六大支柱也不是一一对应。一项机制往往需要多根支柱共同支撑：

| 自治机制 | 主要依赖的 Harness 能力 |
|---|---|
| 意图注入与对话到契约 | 上下文管理、状态与记忆、约束与恢复 |
| 高频对抗与自净化 | 评估与观测、执行编排、状态与记忆、约束与恢复 |
| 人类异常裁决与证据包验收 | 评估与观测、工具系统、状态与记忆、约束与恢复 |

下面先固定唯一的一套六大能力支柱，再说明它们怎样通过四类工程方法落地。

## 8.3 Harness 的六大能力支柱

Harness 原意是“挽具”或“安全带”：它不替代马匹、车辆或驾驶者，却把力量约束在可控制方向上。在 AI Coding 中，广义 Harness 不是某一个脚本，也不是一套额外平台，而是包裹 Agent 的完整工程控制环境。六大支柱分别解决信息、能力、顺序、连续性、判断和安全恢复问题。它们是六种能力域，不是六套必须分别采购的平台。

### 支柱一：上下文管理——让 Agent 看到“足够且正确”的信息

模型并不会因为读到更多文件就必然理解得更好。无关材料会挤占注意力，过期文档会提供错误规则，敏感信息会扩大泄露风险。上下文管理因此不是简单扩充上下文窗口，而是持续回答：当前任务必须知道什么、可以不知道什么、哪些信息不能看到、信息是否仍然有效。

3-4-3 使用分层注入：意图图谱提供全局导航，约束和编码规范提供跨任务边界，当前契约和代码切片提供任务上下文。费用报销 Agent 需要看到金额规则、审批接口和相关测试，不需要读取整套薪酬数据、所有历史会议记录和生产凭证。

上下文支柱失效时，常见表现包括 Agent 反复询问已存在信息、引用旧接口、修改无关代码、不同 Agent 对同一术语理解不一致。改进它时，重点不是继续添加文档，而是建立来源、新鲜度、裁剪规则和任务完成后的回写。

### 支柱二：工具系统——区分“知道什么”与“能够做什么”

Agent 知道数据库结构，不等于它应该获得生产数据库写权限；它知道发布命令，也不等于可以自行发布。Tools Manifest 像一份机器员工的岗位授权书，声明允许调用哪些工具、访问哪些目录和网络域、执行哪些操作，以及哪些动作必须取得人工批准。

权限应遵循最小必要原则，并同时限制“工具”和“作用范围”。只允许 Git 并不够，还要区分只读、创建分支、提交、推送和合并；允许数据库工具也要区分测试环境查询、生产只读与生产写入。工具调用应留下审计记录，越权请求应被阻断而不是仅告警。

工具系统的典型失败，是为了减少中断给 Agent 一个过大的万能权限。短期看执行更顺畅，长期却让一次 Prompt 注入、错误路径或模型误判获得真实破坏能力。

### 支柱三：执行编排——把复杂任务从聊天顺序变成工作关系

一个复杂任务往往包含需求澄清、测试、实现、接口适配、安全检查和证据汇总。仅靠 Agent 在对话中自行决定下一步，依赖关系很容易丢失。Work Graph 用 DAG（有向无环图）表达“什么必须先发生、什么可以并行、什么结果是下一步的输入”。

DAG 可以先理解成一张带箭头的任务图：箭头表示依赖，节点表示可验证工作。测试节点完成可信 Red 后，实现节点才能开始；实现和回退准备可以在边界清晰时并行；所有检查结束后，证据汇总节点才有资格运行。

成熟编排不仅描述成功路径，还描述超时、失败、重试、回滚和升级。它追求的不是让最多 Agent 同时工作，而是减少等待、冲突和无效交接，让系统始终知道“现在在哪、为什么停、接下来由谁做”。

### 支柱四：状态与记忆——让跨步骤、跨会话的执行保持连续

模型会话结束后，临时推理不会自然变成组织知识。状态用于记录当前任务进行到哪里，记忆用于保存经过验证、未来可能复用的事实与教训。两者混在一起，会把临时猜测永久化；两者都不保存，则每次执行都从头开始。

Loop Memory 可以记录节点状态、关键决定、失败与恢复；Intent Graph 保存稳定的业务关系和经过验证的知识；反思日志记录某次任务值得复用的模式。每条记忆都应有来源、适用范围、版本、责任人和失效条件。

例如“外币报销必须先折算为本位币”来自一次真实缺陷，可以进入业务规则；“某接口可能很慢”只是一次观察，需要更多证据，不应直接升级为全局事实。记忆支柱的质量，不看保存了多少，而看下次是否能在正确场景被正确使用。

### 支柱五：评估与观测——既判断结果，也看见过程

评估回答“做得对不对”，观测回答“系统正在怎样做”。只有最终测试结果，团队看不到 Agent 是否越权、重试多少次、花费多少 Token、在哪个环节偏离；只有过程日志，又无法证明业务目标完成。

因此这一支柱同时包含 AC 验证、测试、证据审计、图谱—契约—约束一致性、NFR 检查和遥测。它要把目标命中、质量、成本、异常、人类介入与学习联系起来。

“测试全绿”只是一个信号，不是完整结论。若测试没有覆盖关键 AC，或者测试与错误实现来自同一误解，全绿仍然可能无效。评估必须能追溯到签署意图，观测必须保留真实来源，二者共同支撑发布裁决。

### 支柱六：约束与恢复——给高速执行装上护栏、刹车和逃生通道

约束说明 Agent 不能做什么、做到什么程度必须停止；恢复说明失败以后怎样回到安全状态。只有约束没有恢复，系统一出错就只能人工救火；只有恢复没有约束，错误会反复发生并不断扩大影响。

可执行约束可以限制文件范围、依赖、权限、性能、安全、Token 预算和发布条件。恢复策略则定义自动修复次数、功能降级、事务回滚、数据补偿、人工接管和事故记录。

以生产发布为例，约束可以规定 Agent 无权直接持有生产凭证；恢复要求功能开关已经验证、回退命令可用、监控阈值和负责人明确。安全不是“希望不出问题”，而是即使出问题，影响也能被限制并且系统能恢复。

### 六大支柱的木桶效应

六大支柱并非各自打分后求平均。某一根明显缺失，就可能成为整个自治系统的失效点：上下文正确但工具权限过大，Agent 会准确地做出未经授权的操作；约束严格但不可观测，团队不知道门禁是否真正运行；证据充分但没有恢复，发布后仍无法控制事故。

因此建设 Harness 时应先寻找“最危险的短板”，而不是平均铺开六个平台。读者可以逐项回答：信息是否可信、权限是否最小、依赖是否显式、状态是否连续、结果是否可证、失败是否可恢复。回答不出的地方，就是下一项建设重点。

## 8.4 六大支柱如何通过四类工程方法落地

六大支柱描述广义 Harness 需要具备哪些能力，四类工程方法则描述这些能力如何被建设、装配并在一次任务中协同运行。Context Engineering、Graph Engineering、Loop Engineering、Harness Engineering 不是四个流行术语的拼盘，也不是四套互相独立的平台。它们分别治理 Agent 的认知输入、协作拓扑、反馈收敛和行动边界。

```text
Context Engineering：让正确的 Agent，在正确时刻，只获得完成当前任务所需的可信信息
Graph Engineering：把目标、依赖、角色、并行与汇合点变成可执行的工作拓扑
Loop Engineering：把失败、评价和遥测变成有预算、有终点的纠偏回路
Harness Engineering：把组织规则变成执行前、执行中和执行后的可运行护栏
```

如果把 SCOPE-V 比作整套治理系统的控制回路，那么四类工程就是支撑这条回路运行的工程方法；如果把六大 Harness 支柱比作系统所需的能力部件，那么四类工程就是把这些部件装配、运行和校验起来的方法。三者不是竞争关系：SCOPE-V 回答“控制如何流转”，六大支柱回答“系统要具备什么”，四类工程回答“这些能力怎样落地”。这里的四类工程也不同于人员、组织、流程、工具四维转型：前者是工具与运行环境的工程方法，后者是企业转型的观察与设计维度。

### 8.4.1 Context Engineering：从写好 Prompt 到治理 Agent 的认知环境

Prompt Engineering 关注“这一句话怎样写得更清楚”，Context Engineering 关注的范围更大：模型在当前时刻能看到哪些目标、规则、代码、历史、工具说明和证据；这些信息从哪里来、是否最新、彼此是否冲突；哪些内容必须隔离；任务阶段变化以后，又应当替换哪些内容。

这一区别在 AI Coding 中很关键。人类开发者拥有持续的项目记忆，会主动翻代码、问同事并识别过期资料；Agent 的一次会话却可能同时面对几万行代码、多个版本的文档和相互矛盾的聊天记录。把更多内容塞进上下文并不等于理解更准确。无关信息会争夺注意力，陈旧信息会制造规格漂移，敏感信息的过度注入还会扩大数据泄露和越权风险。

因此，Context Engineering 的目标不是“上下文越长越好”，而是让上下文具备五种质量：

- **相关**：只包含当前节点真正需要的信息；
- **可信**：能追溯到已签署契约、权威代码或有效证据；
- **新鲜**：带有版本和时间，过期内容能够失效；
- **隔离**：不能让一个节点看到无权访问的数据和凭证；
- **可压缩**：在不丢失关键语义的前提下减少噪声和 Token 成本。

#### 四层上下文，而不是一个巨型提示词

3-4-3 可以把上下文组织成四个层次：

1. **L1：任务意图层**。来自 Intent Graph 和当前 Intent Contract，说明为什么做、为谁做、成功如何判定、明确不做什么。
2. **L2：组织约束层**。来自 Constraint Matrix、Tools Manifest 和合规规则，说明哪些边界不可突破。
3. **L2+：工程惯例层**。包括代码结构、接口约定、测试方式、命名规范和仓库级 AI Coding Guide，说明在这个系统里应怎样工作。
4. **L3：节点切片层**。只为当前 Work Graph 节点裁剪所需文件、相邻接口、AC、测试和上游产物。

L1 和 L2 保证方向与底线稳定，L2+ 提供团队的工程常识，L3 随节点快速变化。测试 Agent 与实现 Agent 即使服务于同一个契约，L1 和 L2 可以相同，L3 也不应相同：前者需要边界样例和验收口径，后者需要失败测试、受影响代码和允许修改的文件范围。

#### 一条可运行的上下文流水线

Context Engineering 至少包含六个连续动作：

```text
发现候选信息
→ 判断来源、版本和权限
→ 按当前节点裁剪
→ 检查冲突、过期与敏感信息
→ 注入 Agent 会话
→ 在阶段切换或事实变化时刷新
```

“发现”可以通过代码索引、Intent Graph 和依赖关系定位材料；“裁剪”不是随意摘要，而是保留当前 AC、约束、输入输出和相邻接口；“隔离检查”要证明未注入禁止目录、生产数据或无关客户信息；“刷新”则防止 Agent 在契约已更新后继续使用旧目标。

上下文也必须接受评估。除了压缩率和 Token 数量，团队还应观察关键事实召回率、过期内容命中率、冲突数量、敏感信息泄露次数，以及由于上下文缺失造成的返工。压缩到原来的 30% 却删掉一个 MUST 约束，不是优化；上下文翻倍却没有提高任务命中率，也不是工程进步。

#### 报销案例：同一任务为什么需要不同上下文

“单笔报销不得超过 5000 元”的测试节点，需要看到金额边界、币种处理、AC-001、禁止修改生产数据等内容，却不需要整个财务系统源码。实现节点在接到可信 Red 后，需要看到失败测试、金额校验函数、异常返回规范和允许修改的文件列表，但不需要员工薪资数据。证据节点则主要需要契约版本、检查命令、退出码、测试报告和代码差异。

Context Engineering 在 SCOPE-V 中主要支撑 S、C 和 O，并在 P、E、V 每次交接时重新裁剪输入。它与“上下文管理”支柱关系最直接，同时依赖状态与记忆、约束、评估和工具系统。它不是一次准备动作，而是贯穿控制回路的认知供给系统。

常见误区包括：把整个仓库一次性塞给模型；用旧聊天记录代替签署契约；只有摘要没有来源；所有 Agent 共用同一份上下文；只计算 Token 节省，不验证关键信息是否保留。

### 8.4.2 Graph Engineering：从任务清单到可计算的协作拓扑

Graph Engineering 不是把待办事项画成一张漂亮流程图，也不只是传统项目计划的可视化。它要把目标、任务、角色、依赖、输入输出、并行关系、汇合点、失败分支和停止条件表示为机器可以查询和调度的图结构。

AI Coding 放大了 Graph 的必要性。一个人类团队按日协调时，很多依赖可以靠口头默契补足；多个 Agent 在分钟级并行执行时，一个模糊依赖会迅速变成冲突写入、基于旧结果继续工作、重复修复和错误汇合。Agent 越多，并不天然越快；只有工作能够被正确分解、隔离和重新汇合，并行才会转化为吞吐量。

#### 两张图：组织能力图与任务工作图

Graph Engineering 通常包含两类图：

- **Org Graph** 描述有哪些人、Agent、Skill、工具和权限，谁能够承担哪类任务，谁拥有批准权和责任；
- **Work Graph** 描述当前任务怎样拆分，节点之间如何依赖，哪些可以并行，何时汇合，失败后回到哪里。

Org Graph 回答“谁有能力且有权做”，Work Graph 回答“这一次谁在何时做什么”。如果只有 Work Graph 而没有 Org Graph，调度器可能把安全审计交给没有权限或能力的 Agent；如果只有 Org Graph 而没有 Work Graph，团队知道有哪些角色，却无法治理一次具体协作。

#### 一个节点需要的不只是任务名称

可执行节点至少应包含：

- 节点目标和对应的 Intent Contract、AC；
- 前置依赖、输入产物与可信来源；
- 负责人、执行 Agent 和必要的 HITL 角色；
- 允许使用的工具与可修改范围；
- 预期输出、完成条件和证据要求；
- 时间、Token、并发和重试预算；
- 失败分支、回滚方式与升级条件。

边也不只是“先做 A，再做 B”。它可以表示数据依赖、审批依赖、互斥写入、证据汇合和失败路由。Graph Engine 因此应能回答：当前瓶颈在哪里，哪些节点真正可并行，关键路径是什么，一个上游产物失效会影响哪些下游，以及哪个节点需要重新调度。

#### 报销案例：并行不是同时开四个 Agent

费用规则任务可以先并行生成金额边界测试、分析审批规则影响、检查权限约束和准备证据结构；这些节点只读共享契约，在各自隔离范围内产生输出。实现节点必须等待边界测试形成可信 Red，并在规则影响分析完成后启动。集成验证等待实现和安全检查汇合，Evidence Bundle 又必须等待全部规定检查完成。

如果金额测试与实现节点同时修改同一个测试文件，看起来是并行，实际是在制造争用；如果证据节点在集成验证前就宣告完成，图上的顺序正确但语义依赖错误。Graph Engineering 的价值，是把这些隐含关系变成可检查的结构。

Graph Engineering 在 SCOPE-V 中最直接地实现 O，但图中的节点可以覆盖 S、C、P、E 和 V。Intent Graph 负责保持“为什么”的结构，Work Graph 负责组织“怎样执行”的结构，Evidence Bundle 则记录图上关键节点是否真实完成。它主要调动编排、工具、状态记忆和评估支柱。

常见误区包括：把任务列表误称为 DAG；只画成功路径，不画失败和恢复；按角色并行，却忽略文件写冲突；节点只有标题，没有输入输出契约；认为多 Agent 数量越多，系统能力就越强。

### 8.4.3 Loop Engineering：从机械重试到有证据的自我纠偏

Loop Engineering 解决的不是“让 Agent 多试几次”，而是“系统收到偏差信号后，如何定位原因、采取获准的最小纠正、用同一个判据复验，并在正确时刻停止”。无限重试会消耗 Token、掩盖根因，甚至让 Agent 为追求全绿而削弱测试；可治理的 Loop 必须有输入信号、纠偏策略、预算、退出条件和升级路径。

一个完整反馈环至少包含六步：

```text
接收真实信号
→ 对失败分类
→ 定位契约、约束、实现或环境原因
→ 执行最小且获授权的修复
→ 重跑原始检查
→ 收敛、停止或升级人工
```

“重跑原始检查”非常重要。若第一次因性能阈值失败，修复后却换成一个更宽松的阈值，系统并没有收敛，只是移动了球门。Loop 还要保存失败、尝试、退出码和最终结果，使“自愈”能够被复盘，而不是只留下一个全绿截图。

#### 三层 Loop：任务内自检、失败后反思、组织级学习

3-4-3 可将 Loop 分成三层：

1. **LOOP-1 Self-Consistency**：发生在 O 之后、正式 P 之前。Agent 复述目标、范围、约束和计划，检查自身理解是否一致。它用低成本阻止方向性错误进入高成本执行。
2. **LOOP-2 Reflection**：发生在 P 暴露测试失败、错误或约束拦截之后。Agent 在当前上下文内诊断原因，完成修复或重构 E，再回到 P 取证。这就是 SCOPE-V 的 P⇄E 快内环。
3. **LOOP-3 Feedback-to-Graph**：发生在 V 的人工裁决或生产遥测之后。经过确认的教训被反馈到 Intent Graph、约束、上下文规则、Skill 或路由策略，影响下一轮 S/C/O。这形成跨任务的慢外环。

三层 Loop 的时间尺度不同。LOOP-1 可能只需几十秒，LOOP-2 在一个任务内循环数次，LOOP-3 则跨发布和跨任务积累。把三者混成一个“让 Agent 自己反思”的按钮，会失去不同层级的责任边界。

#### 为什么 Evolution 位于 Verification 之前

P 产生机器事实，E 依据这些事实快速诊断和修复，二者形成高频内环；当任务达到退出条件后，V 才对契约、约束、证据和新鲜度进行独立裁决。V 不负责替 Agent 生产证据，而负责审查证据是否足以放行。上线后的遥测再把成本、质量摩擦和价值偏差反馈到下一轮规划，形成慢外环。

这与传统“开发—测试—修复—再测试”的表面顺序相似，但控制目标不同：Loop 不是固定部门间的阶段回退，而是围绕每个微课题的高频自治收敛；同时它又明确限制自治预算，并保留独立 V 和人类价值裁决。

#### 报销案例：一次失败怎样成为受控回路

5000.00 元边界测试失败后，Loop 先判断是实现使用了 `<` 而非 `<=`，而不是契约含糊或测试环境损坏；E 只修改金额比较逻辑，不得删除测试、修改 AC 或扩大文件范围；P 重跑同一边界测试和相关回归。若连续两次仍失败、触发安全约束，或发现人民币与外币规则冲突，系统停止自动修复并升级 OA/HITL，而不是继续猜测。

Loop 的健康度可以通过首轮成功率、平均收敛轮次、重复失败率、无效重试 Token、人工接管率，以及进入组织记忆后同类问题的复发率来观察。它主要连接评估观测、状态记忆、编排和恢复支柱。

常见误区包括：把“再生成一次”称为反思；没有最大重试次数；允许 Agent 修改判据以获得成功；由产生实现的同一主体单独宣布验证通过；失败得到修复，却没有沉淀可复用的规则。

### 8.4.4 Harness Engineering：把原则变成 Agent 无法绕过的运行时护栏

这里的 Harness Engineering 使用狭义含义，是四类工程方法之一，重点把约束、工具权限、门禁和恢复动作变成不可绕过的运行时控制。它服务于广义 Harness，但不等于全部六大支柱。Harness 在传统软件语境中有时指测试支架或工具框架；Agentic Agile 更关注它怎样包围概率性执行者并形成工程控制环境。它把意图、约束、工具权限、门禁、观测和恢复编织成可执行机制，使 Agent 知道可以做什么、必须证明什么、何时应当停止，以及失败后怎样安全返回。

它与写一份治理制度的根本差别在于“能否运行”。文档写着“不得读取生产数据”，但 Agent 仍持有生产凭证，这不是 Harness；规则写着“必须通过安全检查”，但流水线可以跳过检查直接发布，也不是 Harness。真正的护栏应尽可能进入 Policy as Code、工具白名单、沙箱、CI/CD 门禁和可验证的恢复动作。

#### Harness 同时作用于行动前、行动中和行动后

- **行动前**：校验契约状态、权限、上下文隔离、允许工具和资源预算；
- **行动中**：监控文件范围、命令、依赖变化、超时、Token 和约束命中，必要时阻断或降级；
- **行动后**：执行测试与门禁，聚合 Evidence Bundle，验证回退能力，并把真实遥测送入 Dashboard。

一条可执行约束至少应说明检查什么、何时检查、失败怎样处理、谁负责，以及证据存在哪里。例如：

```yaml
- id: C-SEC-003
  rule: "Agent 不得读取或输出生产凭证"
  level: MUST
  gate: pre_action
  check: "python scripts/check_secret_access.py"
  watch_paths: ["config/**", ".env*"]
  on_failure: block_and_escalate
  owner: Security Owner
  evidence: "evidence/security/secret-access.json"
```

`on_failure` 不能统一写成“报错”。不同风险可以选择自动修复、阻断、回滚、降级、隔离或升级人工；例外必须有批准人、原因和到期时间。Harness 还需要恢复演练，否则“可以回滚”只是一项未经验证的愿望。

#### 从约束到五道门

在 SCOPE-V 中，Harness 应把约束分布到控制回路，而不是只在最后检查：前置门确认契约、签署、约束和 AC 已准备；编码门确认测试先写并产生可信 Red；验证门检查测试、AC、构建、NFR 与证据；收尾门审计 Evidence Bundle、单任务遥测、Dashboard 和图谱回写；Bug 回溯门在完成事实被生产缺陷推翻时修正证据、度量与组织记忆。V 是独立裁决点，但 V 所审查的证据由此前运行与门禁真实产生。五道门裁决控制状态转换，不是五个额外阶段。

报销案例中，Harness 可以强制金额 AC 在前置门存在，限制实现 Agent 只能修改规则模块，禁止删除边界测试，监视新依赖和敏感数据访问，规定最多两轮自动修复，并要求发布前同时具备回归报告、性能结果、代码差异和回退证明。即使 Agent 判断“代码看起来没问题”，也无法绕过这些条件自行上线。

Harness Engineering 贯穿整个 SCOPE-V，并综合六大支柱：它不仅是“约束与恢复”这一根支柱，还要借助上下文、工具、编排、状态记忆和评估观测，才能形成真正的执行环境。

常见误区包括：只有规则文档没有自动检查；只在 CI 最后设门，执行过程完全不可见；工具白名单允许任意 shell 和任意路径；每种失败都无限自动重试；例外永久有效；检查通过却没有保存真实输出和来源。

### 8.4.5 四类工程与六大支柱的对应关系

四类工程不是另外四根支柱，也不是四套独立平台。每类工程都有主要建设对象，同时会调用其他支柱形成闭环：

| 工程方法 | 主要建设的支柱 | 需要协同的支柱 | 典型产物 |
|---|---|---|---|
| Context Engineering | 上下文管理 | 状态与记忆、约束与恢复 | 上下文切片、来源与版本、新鲜度和隔离检查 |
| Graph Engineering | 执行编排 | 工具系统、状态与记忆、评估与观测 | Work Graph、节点契约、资源关系和失败路由 |
| Loop Engineering | 评估与观测、状态与记忆 | 执行编排、约束与恢复 | 失败分类、重证记录、预算、停止与反馈入图 |
| Harness Engineering（狭义） | 约束与恢复、工具系统 | 上下文管理、执行编排、评估与观测 | Policy as Code、Tools Manifest、Gate、Recovery 与审计证据 |

广义 Harness 是六大支柱共同形成的完整控制环境；狭义 Harness Engineering 是其中一种建设方法。Context、Graph 和 Loop 负责让信息、协作与反馈可治理，狭义 Harness Engineering 负责把关键边界落实成机器不能静默绕过的控制。

## 8.5 一个任务中的四类工程接力

仍以报销规则为例，四类工程的协同可以展开为一条完整链路：

1. Context Engineering 从签署契约、约束和代码库中，为测试节点裁剪金额边界、币种规则与允许范围。
2. Graph Engineering 确认测试节点先行，安全分析可以并行，实现节点必须等待可信 Red，集成与证据节点在后方汇合。
3. Harness Engineering 在节点启动前检查上下文隔离、工具权限和预算；在执行中阻止越权文件修改与删除测试。
4. Loop Engineering 根据 Red 和约束信号进入 P⇄E，完成最小修复，重跑同一检查，并在超预算或目标冲突时升级人工。
5. Graph 根据节点状态释放集成验证；Context 随之切换为代码差异、测试结果、NFR 与发布约束。
6. Harness 聚合各门证据，V 独立审查契约命中、约束、新鲜度和恢复条件；人类作出上线裁决。
7. 生产遥测进入契约级和全局 Dashboard，经 LOOP-3 反馈到下一轮 Intent Graph、约束、路由和上下文策略。

四类工程的职责边界可以概括如下：

| 工程方法 | 核心问题 | SCOPE-V 主要落点 | 关键工件或机制 | 缺失后的典型风险 |
|---|---|---|---|---|
| Context Engineering | Agent 此刻应知道什么 | S/C/O，并在 P/E/V 交接时刷新 | 上下文切片、来源与版本、隔离检查 | 用错目标、过期资料、信息泄露 |
| Graph Engineering | 谁在何时依赖谁完成什么 | 以 O 为中心，覆盖全环 | Org Graph、Work Graph、节点契约、关键路径 | 冲突并行、错误汇合、责任不清 |
| Loop Engineering | 偏差如何收敛并停止 | LOOP-1、P⇄E、Telemetry 外环 | 失败分类、反思记录、重试预算、反馈入图 | 无限重试、移动判据、问题复发 |
| Harness Engineering | 哪些动作获准，怎样证明与恢复 | 贯穿 SCOPE-V，各门实施 | 约束即代码、Tools Manifest、Gate、Evidence、Recovery | 文档护栏被绕过、越权、无法回退 |

可以用一句话记忆：**Context 决定 Agent 能看见什么，Graph 决定工作怎样流动，Loop 决定偏差怎样收敛，Harness 决定系统允许发生什么。**

## 8.6 轻量模式与完整模式：按风险裁剪

不是所有项目都需要相同治理重量。

单人单模块项目也应保留四大动态工件的语义，但不必部署复杂平台：用一份最小 Intent Graph 或项目上下文索引提供方向，以意图契约、约束矩阵和 Evidence Bundle 管理当前任务。多人、多工具、多模块项目再增加 Protocol、模块治理、跨模块契约、集成 DAG 和证据聚合。

治理复杂度应与以下因素匹配：

- 变更影响范围；
- 数据敏感度；
- 操作可逆性；
- 业务关键性；
- 参与者和模块数量；
- 自动化验证能力；
- 当前团队成熟度。

## 8.7 风险驱动的最小建设路径：先闭环，再扩大自治

团队不应同时建设六大支柱的所有高级能力。推荐顺序：

```text
契约与核心约束
→ 可执行 AC 和测试
→ Evidence Bundle
→ 上下文与工具权限
→ Work Graph 和多 Agent
→ 遥测与组织级价值效能视图
```

先建立完成闭环，再扩大自治范围。没有证据基础时引入更多 Agent，只会增加不可见复杂度。

上面的顺序是通用起点，不是所有团队必须照搬的成熟度阶梯。实际优先级应由能力缺口和风险决定：

不同团队的第一短板并不相同。可以用四个问题判断优先级：

1. 团队最常在哪个阶段发现错误？越晚发现，越应优先前移相应门禁。
2. 哪类错误代价最高？高代价风险优先于高频但低影响的摩擦。
3. 哪项证据最难获得？缺失证据往往揭示系统不可观测区。
4. 哪个环节最依赖某个“知道所有事情的人”？这通常是尚未资产化的隐性治理能力。

例如，一个需求经常反复变更的团队，应先强化 Specify 和签署，而不是急于增加 Agent 并发；一个发布后事故多、测试却常常全绿的团队，应优先检查 AC、测试独立性与 Evidence Bundle；一个多人协作频繁冲突的团队，应先建设 Work Graph、所有权和 Handoff 协议。

## 8.8 常见概念混淆与机制反模式

本章最容易出现的不是工具不足，而是概念层级混用：

- **六大支柱不是六套平台。** 它们是六种能力域，可以由同一仓库、现有 CI/CD、YAML 与少量脚本共同实现。
- **四类工程不是四根新支柱。** 它们是建设和组合六大能力的方法。
- **狭义 Harness Engineering 不等于广义 Harness。** 前者重点建设约束、工具、门禁与恢复，后者是六大支柱形成的完整环境。
- **证据和遥测不是第二套支柱。** 它们主要属于评估与观测能力，并贯穿其他能力域。
- **Graph 不是额外支柱。** Work Graph 是执行编排的核心工程载体，Intent Graph 则服务于意图与系统对齐。
- **SCOPE-V 不是第五套架构。** 它是三大机制、六大能力和四类工程在任务运行时的控制回路。

常见实施反模式包括：

- 把意图注入理解为复制一段超长 Prompt；
- 允许 Agent 无限自我修复；
- 失败只记录最终结果，不保留原始信号与修复过程；
- HITL 没有预设触发条件，完全依赖人临时观察；
- 六大支柱各自建设，彼此没有任务 ID 和证据映射；
- 只有治理文档，没有机器门禁、权限隔离和恢复演练；
- 为展示多 Agent 而增加不必要节点，导致成本和协调债上升；
- 单人小项目照搬多模块企业治理，使治理成本高于任务风险。

识别这些反模式的共同问题：系统讲得出流程，却无法用真实工件和机器输出证明流程确实运行。

## 8.9 管理者如何判断 Harness 是否有效

管理者不必审阅每条 Prompt，却应要求系统回答五个问题：

- 本次任务的价值目标和非目标是什么？
- 哪些风险被机器门禁阻断，哪些仍由人承担？
- 当前绿色状态由哪些独立证据支持？
- 发生异常时是否可停止、可恢复、可追责？
- 这次执行给下一次留下了什么可复用资产？

如果系统只能展示生成代码量、调用次数和节省工时，就还没有证明治理有效。Harness 的价值不是让 Agent 看起来更忙，而是让团队能够在更大自治范围内保持判断力。

## 8.10 本章小结：从最后一个“3”走向 SCOPE-V

3-4-3 的最后一个“3”定义了自治系统必须完成的三项治理动作：从探索中获得经过授权的意图，在执行中通过高频对抗纠正偏差，并在机器不应决定时把问题与证据交还责任主体。

三大机制要真正运行，必须由广义 Harness 承载。唯一正式的六大支柱定义完整 Harness 所需的能力结构；Context、Graph、Loop 与狭义 Harness Engineering 提供建设这些能力的四类工程方法；下一章的 SCOPE-V 则进一步说明它们怎样在一次任务中流转、回环、停止并形成遥测反馈。

**本章最小实践**：选择一个真实任务，分别写出三大自治机制的当前实现、六大支柱的最危险短板，以及优先补强的一项工程能力。  
**完成证据**：一张“机制—支柱—工程方法”映射图和一个最小改进动作。  
**延伸实践**：推荐学习《Agentic Agile 3-4-3 基础课：跑通第一次受控自治》，在受控任务中练习 Context、Harness、Loop 与异常升级。
